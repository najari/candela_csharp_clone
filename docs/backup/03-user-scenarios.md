# 사용자 시나리오

[목차](README.md) · [요구사항](02-product-requirements.md) · [화면](04-ui-specification.md)

## 공통 조건과 자체 예제

아래 예제는 테스트용 신규 데이터이며 원본 CANdelaStudio 예제의 내용이라고 주장하지 않는다. ECU는 DemoECU, 기본 변형은 Base, 파생 변형은 High, DID는 0x1234 Temperature다. 데이터 타입은 unsigned 16비트, big-endian, 선형식 physical = raw × 0.1 − 40, 단위 °C다. raw 650 → 25.0°C → 바이트 02 8A다. 읽기 요청은 22 12 34, 긍정 응답 예시는 62 12 34 02 8A다. 이는 오프라인 미리보기이며 ECU로 전송하지 않는다.

공통 사전 조건: 앱이 실행되어 있고 사용자는 로컬 파일을 읽고 쓸 수 있다. 승인된 셀 편집은 작업 DB에 커밋되지만 Ctrl+S 전까지 원래 프로젝트 파일은 바뀌지 않는다. 취소는 아직 적용하지 않은 변경을 남기지 않는다.

## UC-01 — 새 프로젝트 생성·재열기

- 역할/목적: 진단 설계자가 ECU 정의의 시작점을 만든다.
- 사전 조건: UI-02에 열기/새 프로젝트 선택지가 있다.
- 입력: DemoECU, qualifier DemoECU, 언어 ko-KR, 자체 고정 UDS 프로파일.
1. 새 프로젝트를 선택하고 이름·ECU·언어를 입력한다.
2. 기본 변형 Base와 기본 프로파일을 미리 확인한다.
3. 생성을 확정한다. 프로젝트·ECU·기본 변형이 한 트랜잭션으로 생성된다.
4. Ctrl+S로 Demo.diagproj를 저장한다.
5. 닫고 재열어 이름·기본 변형·버전을 확인한다.
- 예외: 빈 이름은 해당 필드에서 차단한다. 생성 취소 시 복구 대상도 만들지 않는다. 기존 파일 열기에서 미래 스키마는 편집하지 않는다.
- 저장 결과: ECU 1개, 기본 변형 1개, 자체 스키마 버전과 프로젝트 UUID 유지.
- 인수: FR-001, FR-002, FR-005, FR-023 / TC-001, TC-002, TC-006, TC-027.

## UC-02 — CDD 가져오기

- 역할/목적: ECU 개발자가 기존 정의를 활용한다.
- 사전 조건: 입력 원본을 읽을 수 있다. 가져오기는 새 프로젝트를 만들며 기존 열린 프로젝트와 병합하지 않는다.
- 입력: ABS_ESP-Example.cdd 또는 Multilingual-Example.cdd.
1. 파일을 선택하면 해시·dtdvers·언어와 임시 분석 결과를 표시한다.
2. 지원·미지원·오류 객체 수와 원본 경로를 확인한다.
3. 구조를 해석할 수 없는 치명 오류가 없으면 부분집합 가져오기를 확정한다.
4. 객체와 원본 매핑을 한 번에 작업 DB로 반영한다.
5. 읽기 전용 미지원 노드와 출력 가능 범위를 검토한다.
6. 자체 프로젝트로 저장하고 언어·참조 관계를 재확인한다.
- 예외: 참조 해석 실패는 보고서에 남긴다. 미지원 의미가 포함된 노드를 정상 편집 가능으로 표시하지 않는다. 분석 취소 시 DB 무변경이다.
- 저장 결과: 원본 바이트·해시, 객체 매핑, 진단 결과가 보존된다. CDD는 덮어쓰지 않는다.
- 인수: FR-018, FR-020, FR-022 / TC-022, TC-023, TC-026.

## UC-03 — DID와 읽기 서비스 생성

- 역할/목적: 설계자가 하나의 측정 데이터를 정의한다.
- 사전 조건: Base 변형과 공통 예제 데이터 타입이 존재한다.
1. UI-05에서 DID 0x1234와 Temperature를 입력한다.
2. 데이터 객체 TemperatureValue에 데이터 타입을 연결한다.
3. 읽기 서비스 생성 명령으로 0x22 인스턴스와 DID 데이터 참조를 만든다.
4. raw 650을 입력하여 요청·응답 바이트를 확인한다.
5. DID 번호를 바꾸면 연결 서비스의 식별자 부분도 같은 명령 안에서 갱신되는지 확인한다.
- 예외: 같은 변형·범위에 같은 DID 번호가 있으면 확정하지 않는다. 필수 타입이 없으면 초안 오류를 표시하고 출력은 차단한다.
- 저장 결과: DID 정의와 서비스가 복제된 데이터 대신 참조로 연결된다.
- 인수: FR-008, FR-010, FR-011 / TC-010, TC-013, TC-014.

## UC-04 — 데이터 타입·변환 작성

- 역할/목적: ECU 개발자가 원시값 해석을 정한다.
- 사전 조건: UI-06에서 새 타입 생성이 가능하다.
1. unsigned, 16비트, big-endian과 factor 0.1, offset -40을 입력한다.
2. raw 650 → physical 25.0, physical 25.0 → raw 650을 확인한다.
3. 별도 unsigned 64비트 타입에서 18446744073709551615를 저장·재열기한다.
4. 공유 타입의 변경 영향 목록을 확인한 후 전체 사용처 변경 또는 새 타입 복사를 선택한다.
- 예외: 0인 factor, 겹치는 열거 범위, 범위 밖 raw, 역변환 결과가 정수가 아닌 값은 자동 반올림하지 않고 오류로 처리한다.
- 저장 결과: 계수·오프셋·큰 정수 문자열이 유지된다.
- 인수: FR-009 / TC-011, TC-012.

## UC-05 — 루틴과 실행 조건 작성

- 역할/목적: 설계자가 0x31 루틴의 고정 입출력을 정의한다.
- 입력: routine ID 0x0201, subfunction 0x01, 고정 입력 1바이트, 결과 2바이트.
1. UI-07에서 루틴과 데이터 구조를 만든다.
2. Extended Session과 Unlocked 상태에서만 허용하도록 행렬을 설정한다.
3. 각 그룹 중 하나라도 차단이면 전체 차단인 것을 미리보기한다.
4. 상태 전이가 필요하면 출발 상태마다 도착 상태 하나를 지정한다.
- 예외: 존재하지 않는 상태, 같은 출발 상태에 복수 도착 상태, 차단된 상태에 전이를 지정하면 확정하지 않는다.
- 저장 결과: 조건·전이가 상태 객체를 참조한다. 보안 키 계산이나 실행은 하지 않는다.
- 인수: FR-011, FR-012 / TC-014, TC-015.

## UC-06 — DTC 일괄 등록·수정

- 역할/목적: 검토자가 목록을 일괄 반영한다.
- 입력: code, qualifier, name, description 열을 가진 UTF-8 CSV.
1. 대상 변형을 선택하고 파일·열 매핑을 지정한다.
2. 예제 코드 0x123456의 24비트 범위를 확인한다.
3. 정상·중복·누락 행을 미리보고 적용 가능한 행만 선택한다.
4. 적용하면 선택한 모든 행을 한 트랜잭션으로 반영한다.
5. 여러 DTC의 설명을 일괄 변경하고 한 번의 Undo로 복원한다.
6. CSV로 출력해 코드·이름·설명이 유지되는지 확인한다.
- 예외: 기존 코드와의 병합은 자동 수행하지 않는다. 기본은 충돌 행 제외다. 숫자로 보이는 빈 셀을 0으로 바꾸지 않는다.
- 저장 결과: DTC 정의와 변형 연결, 변경 기록이 함께 커밋된다.
- 인수: FR-013, FR-014, FR-024 / TC-016, TC-017, TC-018, TC-028.

## UC-07 — High 변형만 수정

- 역할/목적: 설계자가 다른 장비 구성을 만든다.
- 사전 조건: Base에서 DID 0x1234와 읽기 서비스가 사용 중이다.
1. Base를 기준으로 High를 생성한다. 초기 DID·인스턴스는 공유된다.
2. High에서 Temperature의 '이 변형에서만 수정'을 선택한다.
3. DID를 사용하는 공유 인스턴스와 소유 서비스·데이터의 복사 범위를 미리본다.
4. 필요 객체 복사와 High의 연결 교체를 한 번에 적용한다.
5. High의 데이터 구조를 바꾸고 Base의 값·길이·ID가 유지되는지 확인한다.
6. Undo로 새 객체와 연결 교체를 원상복구한다.
- 예외: 잠긴 변형이나 미지원 객체는 분리 편집을 차단한다. 구조 변경에 타입 변경도 필요하면 타입도 복사한다.
- 저장 결과: 변경한 객체만 독립 ID를 가지며 공통 타입 등 영향 없는 참조는 유지된다.
- 인수: FR-006, FR-007, FR-015 / TC-007, TC-008, TC-019.

## UC-08 — 사용 중인 객체 삭제

- 역할/목적: 설계자가 불필요한 데이터를 제거한다.
1. 사용 중인 타입 또는 DID를 선택하고 삭제한다.
2. 참조 인스턴스·변형·서비스를 영향 목록으로 확인한다.
3. 참조가 남아 있으면 삭제는 실행되지 않는다.
4. 먼저 연결을 명시적으로 해제하거나 대체한 뒤 삭제한다.
- 예외: 확인창을 승인했더라도 작업 시작 revision이 바뀌었으면 영향을 다시 산정한다. 기본 변형·단일 ECU 직접 삭제는 금지한다.
- 저장 결과: 고아 참조가 생기지 않고 Undo가 ID까지 복원한다.
- 인수: FR-021 / TC-009.

## UC-09 — 오류 탐색·수정

- 역할/목적: 검토자가 출력 차단 원인을 해소한다.
1. 전체 검증을 실행하고 revision과 처리 범위를 확인한다.
2. 결과를 선택하면 숨겨진 필터를 일시 해제하고 문제 필드를 강조한다.
3. 오류를 수정하면 해당 결과를 오래된 상태로 표시한다.
4. 재검증 후 최신 revision의 오류만 출력 가능 여부에 사용한다.
- 예외: 검증 중 추가 편집이 있으면 결과를 최신 문서의 확정 결과로 적용하지 않는다.
- 저장 결과: 규칙 ID·객체·원인이 재현 가능하다.
- 인수: FR-016, FR-017 / TC-020, TC-021, TC-029.

## UC-10 — ODX 출력

- 역할/목적: 설계자가 다른 도구에 데이터를 전달한다.
1. 변형·출력 언어·출력 위치를 선택한다.
2. 의존 객체와 차단 오류를 확인한다.
3. 고정된 revision 스냅샷에서 임시 ODX를 생성한다.
4. 공식 2.2.0 XSD 및 별도 의미 검사를 통과한 경우에만 결과 파일을 교체한다.
5. 외부 도구로 재열어 DID·서비스·DTC·변환·조건을 대조한다.
- 예외: 스키마 미확보, 미지원 의존성, 매핑 불가 조건이 있으면 검증 완료 출력으로 제공하지 않는다. 취소·실패 시 기존 파일을 유지한다.
- 저장 결과: ODX와 입력 revision·프로파일·경고를 담은 보고서가 생성된다.
- 인수: FR-019, FR-020 / TC-023, TC-024, TC-025, TC-034.

## UC-11 — 저장·저장하지 않고 닫기

- 역할/목적: 사용자가 저장 시점을 통제한다.
1. 저장한 프로젝트를 수정하면 제목에 미저장 표시가 나타난다.
2. Ctrl+S 성공 후 표시가 사라진다. Undo로 저장된 체크포인트를 벗어나면 다시 표시한다.
3. 다시 편집한 뒤 닫기에서 '저장하지 않음'을 선택한다.
4. 재열기하면 마지막 Ctrl+S 내용만 나타난다.
- 예외: 저장 실패 시 미저장 표시를 유지하고 닫기를 완료하지 않는다. '취소'는 문서를 그대로 연다.
- 인수: FR-003, FR-015 / TC-003, TC-004, TC-019, TC-038.

## UC-12 — 중단 작업 복구

- 역할/목적: 사용자가 명시 저장 이후의 작업을 되찾는다.
1. 앱 재실행 시 종료 표시가 없는 작업 세션을 탐지한다.
2. 원본 경로·마지막 저장 시각·마지막 작업 시각을 비교한다.
3. 무결성이 확인된 작업본을 새 세션으로 연다.
4. 원본 파일이 외부에서 변경되었으면 다른 이름으로 저장한다.
- 예외: 손상본은 자동 삭제하지 않고 격리 경로와 오류만 보여준다. 사용자가 폐기를 확정한 작업본은 다시 복구 후보로 표시하지 않는다.
- 인수: FR-004 / TC-005, TC-037, TC-038.
