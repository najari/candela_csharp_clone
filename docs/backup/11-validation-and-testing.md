# 검증 규칙과 테스트 명세

[목차](README.md) · [요구사항](02-product-requirements.md) · [추적표](14-traceability-and-decisions.md)

## 판정 계약

ValidationIssue는 severity(info/warning/error)와 blocks_export를 독립적으로 가진다. DB 구조 오류는 편집 커밋/저장을 막는다. 편집 가능한 불완전 초안은 자체 저장 가능하지만 ODX 출력은 막는다. 검증 결과에는 project_id, revision, rules_version, scope를 붙인다.

지역 검증은 명령 적용 전후에 실행하고, 전체 검증은 사용자 요청·ODX 출력 전 실행한다. SQLite integrity_check/foreign_key_check는 진단 의미 검사를 대체하지 않는다. UI 입력 검증도 DB 및 도메인 검증을 대체하지 않는다.

## 테스트 데이터 전략

- 자체 최소 fixture: DemoECU, Base/High, DID 0x1234, 선형 온도 타입, 읽기/쓰기·루틴, DTC 2개.
- 경계 fixture: 1/7/8/16/32/64비트, signed 최소·최대, u64 최대, 앞뒤 비트 필드·padding, Decimal 역변환 오류.
- 원본 corpus: 01 문서의 해시가 있는 설치 예제. 실제 파일은 외부 corpus 경로에서 읽고 저장소에 원문을 무단 복제하지 않는다.
- 비정상 fixture: 끊어진 참조, 같은 변형 중복, 순환, 잘못된 XML, 외부 엔터티, 미지원 버전, 미래 자체 스키마.
- 대량 fixture: 10,000 DID + 10,000 DTC + 5 variants, DID마다 데이터 객체 2개, 공유·독립 혼합. 첨부 BLOB 10MiB를 포함하고 실제 DB 크기를 기록한다.

## 성능 측정 계약

기준은 Windows 11 x64, RAM16GB·SSD다. CPU 모델·앱/SQLite/Qt 버전·DB 크기·BLOB 크기·전원 모드를 기록한다. warm run 20회 p95와 cold open 5회 개별 결과를 함께 보고한다.

검색은 debounce 종료부터 첫 화면 표시까지 500ms, 열기는 사용자 요청부터 첫 표 조작 가능까지 5초, 저장은 요청부터 디스크 사본 교체·확인까지 5초를 목표로 한다. 전체 검증·CDD 변환·ODX XSD 검사에는 임의 5초 기준을 적용하지 않고 처리량·최대 메모리·취소 지연을 별도로 보고한다.

기준 초과는 DB query plan, UI model 호출 횟수, Python CPU profile 순서로 조사한다. 네이티브 라이브러리 자체가 빠른지 추정하지 않고 프로세스 전체 비용을 측정한다.

## 출시 증거

테스트 결과에는 입력 해시, 버전, 실행 시각, 결과, 로그/스크린샷/출력 해시를 연결한다. TC-025의 검증 도구가 사용 불가능하면 상호운용 게이트는 미통과로 남긴다. TC-036은 Rust 미도입 시 적용 제외로 명시한다. 다른 P0 테스트를 적용 제외로 바꾸어 출시 조건을 낮추지 않는다.
