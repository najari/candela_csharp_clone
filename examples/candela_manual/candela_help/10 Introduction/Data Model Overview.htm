Template and Document

CANdelaStudio supports a template concept like Microsoft Word: a document is based on a template which implements diagnostic protocol and manufacturer specific information.

See Document Template.

Variants

Variants in CANdelaStudio

CANdela data supports multiple variants in a single document, each may describe either a feature variation, or development progress over time.

See the Variant feature.

Protocol Services

Diagnostics is about services: sending a request and receiving a positive or negative response.

Different diagnostic protocols define different services with specific byte sequences.

UDS (Unified Diagnostic Services; ISO 14229) is widely spread and a recommended basis for new diagnostic projects.

Protocol Services in CANdelaStudio

In the CANdela data model, the specifics of the diagnostic protocol are described in a Protocol Service in the document template.

A document describing a concrete ECU does not allow to modify the basic protocol information, it only allows to describe services, filling in the variable parts defined in the Protocol Service.

See the Protocol Service feature.

See also UDS 2013 for differences in ProtocolServices between UDS versions of 2005 and 2013.

Diagnostic Classes

A tester would typically list all services (CANdela: protocol services) that may be sent to the ECU in a flat list. UDS provides some structure: it groups services by “functional units”:

  • Diagnostic and Communication Management
  • Data Transmission
  • Stored Data Transmission
  • InputOutput Control
  • Remove Activation of Routine
  • Upload Download

Diagnostic Class Templates in CANdelaStudio Tree

A CANdela diagnostic class template typically represents a diagnostic use-case, like Fault Memory, Live Data, Stored Data, ECU Reset etc.

It combines a subset of protocol services (from UDS or any other protocol) with the data for the “proxy components” (entry points for payload data) from these ProtocolServices.

The diagnostic class template is predefined in the document template.

Its counterpart in a document is the diagnostic class within a variant.

See the Diagnostic Class Template feature with the Diagnostic Use-Cases.

Diagnostic Instances

CANdelaStudio Tree and Diagnostic Instance in Right Side

A diagnostic instance combines

  • services (to be executed, e.g. “Start” on top in the screenshot) with...
  • data (to be transported, e.g. list with “P2”, “P2Ex” at the bottom in the screenshot)

You can reuse a diagnostic instance in multiple variants.

A diagnostic instance may be included in a variant only once (ECU Reset) or more than once (Reading data by Identifier: 0x22 0xF120 vs. 0x22 0xF121).

See the Diagnostic Instance feature.

Services

In CANdela, most aspects of e.g. a UDS service are predefined in the template in a protocol service, like “(0x10) DiagnosticSessionControl” (see screenshot above).

The service in the diagnostic instance (e.g. “Start”) has only few properties which can be modified in a property dialog.

The slots for data are filled in separate lists (e.g. “zz”, “rc” in the screenshot above), as described in the following chapter.

See the Service feature.

Data

The data lists in a diagnostic instance (see screenshot above) are the central place to describe the diagnostic behaviour of an ECU. They are called „telegram table“ in CANdelaStudio.

In the user interface, they are identified by a two-character abbreviation (like “zz”). The abbreviation has no meaning in itself; it only indicates the place of the data in the request or response (there are a few special abbreviations, like “rc” for response code, “fd” for data fixed in the template already).

The telegram table can contain different kinds of data:

  • a Data object (named piece of data with a data type, i.e. conversion),
  • a bit field (may contain bit-size objects) and
  • reserved data objects (unnamed objects without conversion) bit length.

Byte and bit positions of data always results from the relative position within the list; there are no explicit properties to set a position.

Only byte-sized data objects starting at byte positions can be positioned directly in the list. Other data must be put into a bit-field.

See the Telegram Table and Data Object features.

DTCs

A DTC (Diagnostic Trouble Code) represents an event or malfunction detected by the ECU. The ECU typically stores snapshot data and statistical data for a DTC.

See the Fault Memory Introduction and the user interface DTC List.

Data Types

Data Type Property Dialog

A data object references a data type.

Constant and default value are specified at the data object, not at the data type.

A simple datatype describes the length and conversion of a raw value (transferred via the CAN/LIN/MOST… bus) to a physical value, or vice versa.

Example

    Byte 0x20 on bus => Conversion "Temperature (1Byte)" => t = 16°C.

A complex datatype contains data objects (each of which references either a complex or simple data type):

  • packet data type
  • multiplexer
  • iteration.

See the Data Type feature.

Jobs

A job is a program (macro, sequence) to be executed by a tester (not in the ECU).

See the Jobs feature.
