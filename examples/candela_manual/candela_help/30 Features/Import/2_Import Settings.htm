Import Settings

CANdelaStudio provides multiple settings to adapt the behaviour of the ODX Import to the specific requirements of the user.

CANdelaStudio Import Options

The CANdelaStudio Import Options can be specified inside the CANdelaStudio.ini file, some of them are also accessible over the Import Options dialog.

CANdelaStudio.ini option GUI option Description
LogDetails Write detailed information (DiagComm oriented) in log file Controls whether to log DiagComm oriented or not. This options is only provided for "Full ODX ECU description"
LogPerformance Not available Dump performance statistics (time and memory consumption) for each imported DIAG-LAYER to log
StrictNegResponse Negative Responses Specify whether NEG-RESPONSE of ODX DIAG-SERVICE shall be considered during Import or not
HandleDataTypeMergeInCaseOfRangeDifferences Data Type:
"use existing" (0)
"create new" (1)
"use existing if modifiable"		 On importing a complete ECU, decide how to handle DataTypes having a different specification but the same Qualifier.
SupportStableOIDs Not available The CANdela data model supports OIDs. By default OIDs are either imported from data source (if existing), or generated anew.

In some specific use cases it makes sense that "generated" OIDs ('cos the data source does not provide OIDs) are always generated using a hierarchical approach. (SHORT-NAME of LAYER + SN of DIAG-SERVICE + ...)
ImportRequiredAndMissingNrcs Not available For OEM specific use cases (but not in general), it makes sense to update/enhance the existing list of NRCs by numbers which are required by the ODX model.
RunImportPostProcessorPlugin Not available For specific inter OEM cooperation (e.g. VAG/PAG), there exist process specific Plugins. Some of these Plugins are executed right after completing the ODX-Import to ensure data consistency.

In certain use cases it makes sense not to execute the process specific Plugin at the end of an ODX-Import.
DeactivateInstances Not available This setting enhances controlling the deactivation of diagnostic instances (CDS-22911) before doing the ODX-Import. The standard way to deactivate diagnostic instances is via the import wizard setting "Deactivate all CANdela diagnostic instances and job containers which are not part of the ODX data (as far as they can be deactivated)".

In order to ensure specific process steps at OEMs side, it is strongly required to deactivate existing diagnostic instances "all the time" on importing from ODX. (Regardless of the UI-Wizard setting)
ForVariantWizardMapBaseVariantElementId Not available In case of running an ODX-Import of kind "Variants with selection of services/jobs" (and only in this case), it is possible to specify, if the ECU related information like name, qualifier and description shall get updated from ODX or not. (CDS-14115).
SkipImportOfVehicleInfoSpec Not available By default, the ODX Import integrates the VEHICLE-INFO-SPEC as library into the CANdela document. As a result the VIS gets exported on running the ODX export.
In specific cases, the imported and re-exported VIS might have different BASE-VARIANT CANIds, SHORT-NAMES, .... IN those cases it might be useful to skip the import of the VEHICLE-INFO-SPEC (CDS-24970).
UniqueLocalIdDuringImport Not available On every newly created diagnostic instance, the import checks if the identifier of an instance conflicts with any diagnostic instance already existing are already imported during this run of an ODX-Import (CDS-26930).
AllowDuplicateServicePrefixInDifferentDiagClasses Not available From ECU's diagnostic implementation point of view, it might not make sense to support duplicate service prefixes in a CANdela document. Therefore, the ODX-Import always skips duplicate service prefixes and provides an according message to the console. (The only work around is to disable the check for unique identifiers [CIU-R020].

For specific uses cases, it is required to import a service prefix with two or more with different data parameter into different (not the same) diagnostic class. (CDS-24970)
DID2DiagClassMapping Not available For some specific OEM use cases, it makes sense to predefine the mapping of DID ranges to according CANdelaStudio diagnostic class qualifiers. E.g. DIDs of the range 0xF1090 - 0xF19F shall get stored in a diagnostic class having the qualifier "Identifications_Global", while the DIDs of the range 0x2000 - 0x20FF shall get stored in the diagnostic class "LocalIdents".
ODXImportCacheLimitationInMB Not available While importing from ODX, the import component makes use of additional memory as cache to increase the import performance. As this cache memory consumption can get very huge, a limitation might be required. This is supported in the setting of below's table.

Example Import Options in CANdelaStudio.ini

[OdxImport]
LogDetails=1
StrictNegResponse=0
ImportRequiredAndMissingNrcs=0
HandleDataTypeMergeInCaseOfRangeDifferences=0
SkipImportOfVehicleInfoSpec=0

Import related attributes

Attributes are document-specific settings, which modify the behaviour of the ODX Import for certain elements of the document on which they are set.

ECU attributes

Units

ODX Import adds to an ECU attribute "units" that provides a set of units, used in data type dialogs.

Keep deactivation even if imported from ODX

Specific use cases require configuring of a list of SHORT-NAMEs representing "superset" libraries (ECU-SHARED-DATAs). In case a deactivated diagnostic instance gets re-imported from out of one of these "superset" libraries, it shall remain deactivated.

In order to achieve this behavior, the user can configure the ECU attribute "Superset_Libraries".

Diagnostic class template attributes

Mapping of TABLEs to diagnostic classes

By default, the ODX-Import maps the instances automatically (FUNCT-CLASS, matching services, ...). At OEMs it makes sense to import Identifications/Measurements of VW into specific diagnostic classes in Porsche's CANdela document.

In order to apply this behavior, you can configure the diagnostic class template attribute "VWODXTableShortName".

Diagnostic instance attribute

Lock primary/Secondary properties of diagnostic instance

By default, the ODX-Import modifies the primary and secondary properties of an existing diagnostic instance as specified in its setting. In specific use cases and for process reasons, it is not possible to remove the primary and/or secondary properties modifiable flag. The user still needs to modify the properties inside the GUI of CANdelaStudio.

On the other side, the ODX-Import must not modify any of those primary/secondary properties.

In order to achieve this behavior, you can configure the diagnostic instance attribute "DoNotModifyPrimaryAndSecondaryPropertiesByImport" (CDS-12326).

Job attribute

Configurable job deactivation

The ODX-Import deactivates all jobs inside the CANdela document before starting the ODX-Import.

  • In case a job in CANdela is represented by an according SINGLE-ECU-JOB in ODX, it will get activated again,
  • otherwise it will remain deactivated.

In order to keep a job activated, even if it is not present in the imported ODX, you can configure a job attribute that lets ODX Import skip the initial deactivation at this job.

See the job attribute "SkipDeactivationOfJobDuringODXImport" (CDS-26949).

  • First prepare the template or document in Expert View: add the job attribute
  • Then set the attribute value to 1 (e.g. "Yes") for each job in the template or document you want to keep activated during ODX import.
