Import of DIAG-SERVICEs

This section describes how DIAG-SERVICEs are imported as CANdelaStudio Services. The structural mapping (the meaning of this is described in the next chapter "Mapping of DIAG-SERVICE to CANdelaStudio Service") of a DIAG-SERVICE to a CANdelaStudio Service is described in the next chapter. Restrictions for a CANdelaStudio Service which are defined by the ProtocolService on which the Service is based are always fulfilled. The Import does never change these restrictions. ProtocolServices belong to the Template definition. And data defining the Template are never changed by the Import.

Preliminary note

  • ODX 2.0.1 supports no modeling for ECU states resp. state transitions for DiagServices. Hence, states and state transitions are not imported.

Import in which CANdelaStudio DiagInstance resp. Service ?

In CANdelaStudio a Service only exists within a DiagInstance. Therefore, the ODX Import has to determine in which DiagClass/DiagInstance a DIAG-SERVICE is imported as Service. There are several properties which are checked for the DIAG-SERVICE to make that decision.

The following subsections describe alternatives in which DiagInstances a DiagService can be imported. These alternatives are ordered, i.e. the first successful alternative is decisive.

If a DiagClass is a singleton the Services are imported into the DiagClass. For non-singleton DiagClasses new DiagInstances are created if necessary, e.g. if a DiagInstance with a StaticValue exists and the DIAG-SERVICE has the same value at the byte position where the CANdelaStudio StaticValue is positioned the DIAG-SERVICE is imported into the existing DiagInstance else a new DiagInstance is created in the DiagClass. The building of qualifiers and names of new DiagInstances created by the Import is described in 4.1.3.

Determine CANdelaStudio DiagClass by FUNCT-CLASS

If a DIAG-SERVICE references a FUNCT-CLASS and the SHORT-NAME of the FUNCT-CLASS is equal to the QUALIFIER of a CANdelaStudio DiagClass which is not a singleton the DIAG-SERVICE is imported into a DiagInstance of the DiagClass. For DIAG-SERVICEs which have to be imported as Services into a singleton DiagClass because of the corresponding structure and values the FUNCT-CLASS-REFs are neglected.

Recommendation: Always use ODX data which have FUNCT-CLASS-REFs fulfilling these conditions to make the import result unique.

Determine CANdelaStudio DiagClass by DIAG-SERVICE structure

If the structure of a DIAG-SERVICE corresponds to the given structure of a CANdelaStudio Service within a potential DiagInstance the DIAG-SERVICE can be imported as a Service into that DiagInstance.

Qualifier and Name of new DiagInstances created by the Import

The DIAG-SERVICEs which are imported as Services into one DiagInstance are checked for the following properties to determine qualifier and name of the new DiagInstance. The properties are checked in the following order:

  • If a DIAG-SERVICE uses a TABLE-ROW the SHORT-NAME of the TABLE-ROW is used as qualifier of the DiagInstance and the LONG-NAME of the TABLE-ROW is used as name. If the LONG-NAME is not available the SHORT-NAME is used as name as well.

  • If a DIAG-SERVICE specifies its SUB-FUNCTIONs within a TEXT-TABLE the SHORT-NAME of the COMPU-SCALE is used as qualifier and name of the DiagInstance.

  • (Will be implemented with CDS-6794:) If a DIAG-SERVICE has the following SDG structure the content of SD with SI="DiagInstanceQualifier" is used as DiagInstance qualifier and the content of SD with SI="DiagInstanceName" is used as DiagInstance name.


<SDG>
  <SDG-CAPTION ID="xyz">
    <SHORT-NAME>CANdelaServiceInformation</SHORT-NAME>
  </SDG-CAPTION>
  <SD SI="DiagInstanceQualifier">Diag_Instance_Qualifier</SD>
  <SD SI="DiagInstanceName">Diag Instance Name</SD>
</SDG>
  • Else the CANdelaStudio DiagClass qualifer is used as DiagInstance qualifier (Note: DiagInstance qualifiers are made unique afterwards). If all DIAG-SERVICEs which are imported into the DiagInstance have a common prefix in their LONG-NAMEs which has more than 10 characters this prefix is used as DiagInstance name.

Note: In a post step all DiagInstance qualifiers within a DiagClass are made unique by adding suffixes if necessary.

Recommendation: Specify CANdelaStudio DiagInstance Name and Qualifier with the SDG structure at DIAG-SERVICE as it is mentioned above.

Import of SINGLE-ECU-JOBs

Detecting the right CANdelaStudio Job container

To detect the right CANdelaStudio job container, the SINGLE-ECU-JOBs are inspected together inside a BASE-VARIANT or ECU-VARIANT.

Generating groups SINGLE-ECU-JOBs

SINGLE-ECU-JOBs are subsumed if they have the following properties:

  1. The SINGLE-ECU-JOB/SEMANTIC are equal
  2. The FUNCTIONAL-CLASS-REFs are the same.
  3. The AUDIENCEs are the same.
  4. If SDGs exist,
    • They refer to the Same JobContainer Qualifier / Name

Creating a CANdelaStudio JobContainer

Each group of SINGLE-ECU-JOBs is imported as a job container in CANdela. For SEMANTIC='FLASHJOB" a Flash container is used.

The SHORT-NAME-prefix is selected as the QUALIFIER of the SINGLE-ECU-JOB group. The LONG-NAME-prefix is selected as the Name of the SINGLE-ECU-JOB group.

The CANdelaStudio names/qualifiers are taken out of SDGs as provided by the ODX export (CDS-7072), if they exist

If no Prefixes could be identified, a generic algorithm selects them.

Note:
No CANdelaStudio internal authoring rules are necessary to provide import of exported ODX.

Audiences of job container

As given in 4.2.1.1, all AUDIENCEs of a group of SINGLE-ECU-JOBs are the same. As a result, the target groups of the CANdelaStudio job container are set as given in CDS-6360 (Audiences of DIAG-SERVCEs)

Jobs in group of Jobs

Each member of the group of SINGLE-ECU-JOBs is imported as a job in the job container. (see 4.2.2

Jobs in job container

Qualifier and Name of a Job

  • As a result of 4.2.1.1, each SINGLE-ECU-JOB has a SHORT-NAME-suffix defining the job qualifier inside the job container. (If the SHORT-NAME-SUFFIX is empty the whole SINGLE-ECU-JOB SHORT-NAME is taken as Qualifier.)

  • Each SINGLE-ECU-JOB has a LONG-NAME-SUFFIX defining the job name inside the job container. (If the LONG-NAME-SUFFIX is empty the whole SINGLE-ECU-JOB LONG-NAME is taken as Name.)

Note:

If no suffix is detected the complete SHORT-NAME of the SINGLE-ECU-JOB is taken as qualifier.

Input parameters

The sequence of SINGLE-ECU-JOB/INPUT-PARAMETERs is added to the input parameter list of the CANdelaStudio job. If a single INPUT-PARAMETER is not importable (referenced DOP is not importable), the complete job is skipped.

Output parameters

The sequence of SINGLE-ECU-JOB/OUTPUT-PARAMETERs is added to the output parameter list of the CANdelaStudio job. If a single OUTPUT-PARAMETER is not importable (referenced DOP is not importable), the complete job is skipped.

NEG-OUTPUT-PARAMs

All NEG-OUTPUT-PARAMs are ignored. A warning will be presented.

Functions in a job

Each PROG-CODE is appended to the functions of the job.

ENTRYPOINT

The PROG-CODE/ENTRYPOINT is imported as CANdelaStudio entry point.

SYNTAX

The PROG-CODE/SYNTAX is imported as CANdelaStudio function syntax.

VERSION

The PROG-CODE/REVISION is imported as CANdelaStudio function version.

ENCRYPTION

The PROG-CODE/ENCRYPTION is imported as CANdelaStudio encryption.
