Communication Parameter

Introduction

In a data driven test system, communication parameters are not hard-coded but taken from the CANdela document. Therefore a communication parameter typically parameterizes the communication between an ECU and a test system, e.g.

  • Bus type: "CAN"
  • CAN-ID: 0x0700
  • P2 Client: 150ms

Communication parameters have the same types as CANdela attributes [ATTR-R020].

List

The list of communication parameters is defined in the CANdela template in Expert View, see [CPUI-R050].

  • some of them may control the behavior of a specific tool only,
  • typically to support an OEM specific process.

Values

You can edit the values of communication parameters (e.g. the CAN-ID) in Standard View in a CANdela document.

Use

A data driven test system...

  • typically uses the communication parameter values from a CANdela document
  • ... but may also allow modifying them directly in the test system.

Meaning of Communication Parameters

For some protocol standards (e.g. UDSonCAN), the communication parameters and their meaning are standardized in the D-PDU API (see below [CP-R060]). E.g. the ODX standard specifies communication parameters by referencing the D-PDU API.

For communication parameters created with the CANdelaStudio wizard, the description column contains the available information about the meaning and use of the communication parameter.

A CANdela template may contain any user-defined communication parameters, therefore CANdelaStudio does not provide further information beyond the description given in the template.

Category

[CP-R020] The category roughly classifies the use of a communication parameter in the network stack. CANdelaStudio provides the categories...

  • Communication
  • Timing
  • Initialization

... but more can be defined for specific purposes in the CANdela template.

Vector tools do not rely on the category, since the standardized qualifier already defines how a communication parameter is to be used. The category may be used in other tools, or for documentation purposes.

Symbol

[CP-R030] A communication parameter of type "Enum" (enumeration) contains a list of symbols (strings). One of these symbols gets selected as default and optionally as overriding value, respectively.

  • The list of symbols can be defined freely in the CANdela template.
    • For restrictions, see [CPUI-R070].

Display

[CP-R040] Depending on the type of communication parameter, the "Display" property...

  • describes the numeric format (decimal, hexadecimal, binary)
  • describes the sort order of enumeration symbols.

Default Value

[CP-R050 Default Value] The default value of a communication parameter is defined in the CANdela template.

  • [CP-R050-OverridingValue] In a CANdela document in Standard View, you can optionally specify an overriding value.
    • [DOC-R710] "Convert document to template" drops it.
    • Loading a template drops it (CDS-38382 8.2 SP3)
  • [CP-R050-Default] As long as there is no overriding value, the default value takes effect.

Is Standard (D-PDU) (CDS-32611 8.2)

[CP-R060] The qualifier of the communication parameter can be classified whether it corresponds with the D-PDU API standard, and whether the Vector diagnostic toolchain can handle it:

  • [CP-R060-yes]: yes - the qualifier is one of the qualifiers defined in the D-PDU API

  • [CP-R060-mapped]: Mapped by Alias - the qualifier is not one of the qualifiers defined in the D-PDU API, but the Vector diagnostic toolchain knows how to map it to such a standardized qualifier.
    • This typically applies if a qualifier cannot be changed to the standardized qualifier without breaking an existing OEM specific toolchain.
    • This especially holds for interfaces where the D-PDU API does not define communication parameters (e.g. ISO 10681 FlexRay).
    • It also holds for special non-standard communication parameters (see next chapter).

  • [CP-R060-no]: no the qualifier does not correspond with the D-PDU API and will not be handled by the Vector diagnostic toolchain.

This information is displayed in the communication parameter list in Expert view.

Unit

A CANdela communication parameter does not have a "Unit" property.

Recommended practice: describe the unit in the description field.

The ODX Export supports a convention, see [ODXE-R900].

The CANdela toolchain assumes the unit (e.g. for P3) as milliseconds (ms).

Special Non-Standard Communication Parameters

The communication parameters

  • Bus type (CAN)
  • Max Length of TP Message (4095)
  • Transport Protocol Type (ISO15765)

have no direct representation in the D-PDU API.

In an ODX document, they are defined implicitly by the use of a PHYSICAL-LINK-TYPE and PROTOCOL-TYPE.

Templates (such as the Vector UDS template) may nonetheless define these communication parameters, in order to make the information more explicit. The Vector toolchain evaluates these communication parameters. Consequently, CANdelaStudio shows them as "Mapped by Alias".
