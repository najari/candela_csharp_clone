Packet Data Type (3.0)

A Packet data type contains data objects, like a telegram table in a diagnostic instance.

You can use a packet data type if you want to reuse the same set of data objects in multiple diagnostic instances.

See also the dialog.

Properties

  • the Packet data type is handled like Identity data type as much as possible.

  • The maximum size of the Packet is derived from the maximum size of all data objects which are in the Packet.

  • Minimum size equals maximum size (“field fix”) always.

  • Coded and phys value types have equal property values.

  • a packet data type can contain data objects that again reference a packet data type ("nesting"; 6.0, CDS-10035), controlled by a document option set in the template (in menu File | Properties | Data Type Authorization)

  • data objects, gaps and bit fields are always allowed
  • but no data objects that reference a field with minsize != maxsize (see CDS-3641/CDS-4035)

  • recursion is not allowed (referencing the same packet data type)

History

When a document >= 6.0 with nested packet data types is saved in the format of a previous version (5.5, 5.0...), the packet data types contained in a packet data type are all unpacked. This means that the data objects are copied to the uppermost packet data type when saving in that format.

Until 4.0, a packet contained an optional DID number.

In 5.0, DIDs were defined via a special semantics in the diagnostic class template instead (CDS-5338).

Packet Semantics

The contents of the packet data type is not substituted tracelessly into a telegram that references the telegram. Rather, the packet data type defines an own level in the CANdela data model. Therefore, it constitutes a namespace, and the default for exports is to preserve the structure if it is supported in the target model.

Visible as structure in diagnostic application (ODX: IS-VISIBLE) (CDS-14214 6.5)

  • The bool property defines whether...
    • the Packet itself shall be shown in a diagnostic application,
    • or just its contents (i.e. the packet is only meant to group / reuse data in authoring)
  • default: true.
  • The property corresponds with the ODX property "IS-VISIBLE".
  • the property has no effect on display in authoring tools
  • RTF report could evaluate the flag = provide a test system oriented view. This seems no use-case, since the report is authoring oriented ("specification") (cf. CDS-7574)
