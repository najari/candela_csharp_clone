Encoding

See the Data Type Feature.

[DTENC-R100] The Encoding of a Data Type specifies the type...

  • of the value (for an atomic data type)
  • of a single element (for a field data type: unsigned or character)

The encoding describes how a given coded or physical value is interpreted.

For the dependency of Encoding and Length, see [DTDEP-R100].

Encoding Description
Unsigned unsigned number
Signed two’s complement (e.g. for length 8 bits, all bits set = 0xFF represents -1)
BCD (= packed BCD) 4 bits represent 1 digit, see below [DTENC-R050]
Unsigned (64 Bit) unsigned number with 64 bit length (see below [DTENC-R200])
Signed (64 Bit) signed number with 64 bit length
BCD (64 Bit) BCD number with 64 bit length (i.e. 16 digits)
Float IEEE 754 single precision, 1 + 23 + 8 bits, sign + mantissa + exponent; see below [DTENC-R150]
Double IEEE 754 double precision, 1 + 52 + 11 bits, sign + mantissa + exponent
Ascii 1 byte character, see below [DTENC-R110]
Unicode 2 byte character

Ascii

[DTENC-R110] The character set allowed for Values of encoding ASCII (atomic or field) is as follows (cf. CDS-2214):

  • the CANdela loader checks > 0xff
  • up to v2.0: Ascii ValueTypes were confined to characters < 0x80

Float

[DTENC-R150] CANdelaStudio does not show float values in exponential notation.

64-Bit

[DTENC-R200] CANdelaStudio supports 64-Bit integers (CDS-26911 8.2 SP2).

[DTENC-R210] The feature must be enabled in File | Properties Property Page Data Type Authorization.

[DT-R510] Bitmask is not supported for 64-Bit integers.

BCD

[DTENC-R050 BCD] CANdelaStudio supports BCD values (Binary Coded Decimal).

There are different variations of "BCD" encodings, CANdelaStudio supports Packed BCD: each decimal digit is coded in the upper or lower 4 bits ("nibble") of a byte.

Examples:

  • the lowest invalid day in month 32 as 1 byte BCD is binary %00110001 = 0x32 (this number written as not binary decimal is 50 which sometimes leads to confusion);
  • the date 31st of December 2016 20161231 as 4 byte BCD is 0x20161231.

See [VALUI-R050] for editing of BCD Values.

As a result, ...

  • the BCD values have been interpreted differently in CANdelaStudio ODX import/export vs. other Vector tools (see below).

Normalization: Up Migration from before 8.5 SP2

Assumption: the user entered a BCD value in CANdelaStudio < 8.5 SP2 using the default editing format "BCD" as if he entered hex digits, i.e. input string 32 meant 0x32.

[DTENC-R055 BCD Migration 8.5 SP2] When loading a file with CDD version < 8.5 SP2, for each value V of a data type with encoding BCD, bit length N...

  • [DTENC-R055-nn] ... if V <= max (max = maximum decimal value with N/4 digits),
    and "nn" is the decimal notation of V, CANdelaStudio shall...
    convert V to the hexadecimal value "0xnn", e.g.
    convert 1 byte 0x20 with N = 8, max = 99, nn = "32" to 0x32;
    convert 2 bytes 0x2063 with N = 16, max = 9999, nn = "8291" to 0x8291.

  • [DTENC-R055-nnn] ... otherwise, i.e. V > max,
    leave the value unchanged, e.g.
    leave 1 byte 0xA0 with N = 8, max = 99, nn = "160" unchanged as 0xA0,
    leave 1 bytes 0xA000 with N = 16, max = 9999, nn = "40960" unchanged as 0xA000,
    with a warning in log (V shown as hex with "0x" prefix):

      BCD value 0xA0 at "npath:/Base Variant/Dynamic Data/Supply Voltage ECU/Data/Supply Voltage ECU" is invalid - please correct it. See DTENC-R055 in CANdelaStudio online help.
  • [DTENC-R055-multi] This also applies to BCD data types with quantity "atom" and length more than 1 byte.

  • [DTENC-R055-field] This also applies to BCD data types with quantity "field".

De-Normalization: Down Migration to before 8.5 SP2

[DTENC-R057 BCD Migration from 8.5 SP2] when saving to a file with CDD version < 8.5 SP2, for each value V of a data type with encoding BCD, ...

  • [DTENC-R057-nn] if each hex digit n < 0xA, CANdelaStudio shall...
    convert "0xnn" to the decimal value "nn" (= the inverse of [DTENC-R055-nn] above), e.g.
    convert 1 byte 0x32 to 0x20 = dec 32,
    convert 2 byte 0x8291 to 0x2063 = dec 8291.

  • [DTENC-R057-xx] otherwise, i.e. any hex digit X >= 0xA,
    leave the value unchanged, e.g.
    leave 1 byte 0xA0 unchanged as 0xA0,
    with a debug info in log (V shown as hex with "0x" prefix):

      BCD value 0xA0 at "npath:/Base Variant/Dynamic Data/Supply Voltage ECU/Data/Supply Voltage ECU" is invalid - please correct it. See DTENC-R057 in CANdelaStudio online help.
  • [DTENC-R057-multi] this also applies to BCD data types with quantity "atom" and length more than 1 byte.

  • [DTENC-R057-field] this also applies to BCD data types with quantity "field".

Incompatibilities

  1. If a file has been migrated to 8.5 SP2, do not open it again in CANdelaStudio 8.5 Release: this does not trigger any migration, therefore CANdelaStudio 8.5 Release...

    • interpretes the data migrated to 8.5 SP2 (e.g. BCD 32 = 0x32)...
    • in the pre 8.5 SP2 way (e.g. as 0x32 = dec 50 = BCD 50).

  2. The migration assumes BCD values in a pre 8.5 SP2 file have been specified using the "BCD" editing format (the default in the user interface).

    Values specified using the "hex" editing format (maybe as a workaround to get the correct values in Vector tools) will have an undesired value after migration to 8.5 SP2 and must be corrected manually.

    • E.g. 0x20 edited before 8.5 SP2 to specify BCD 20...
    • results in 0x32 = BCD 32 after migration to 8.5 SP2.

Consistency Check

[DTENC-R058 BCD Consistency Check] (CDS-39560 8.5 SP2)

  • for a data type with encoding BCD (either atomic or field),
  • if a data object or an identifying pattern references the data type,
  • and a byte has a value with a nibble > 9,
  • CANdelaStudio shall report a warning (with a link to the object; do not prevent from export).

Note: nibble = the number given by the upper / the lower 4 bits of a byte.

E.g. show the warning iff. byte >= 0xA0 or (byte & 0x0F) >= 0x0A.

See Consistency Check.
