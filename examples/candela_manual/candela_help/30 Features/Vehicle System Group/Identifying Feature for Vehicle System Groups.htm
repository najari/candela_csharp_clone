Identifying Feature for Vehicle System Group (Optional Subsystem) (CDS-3619 4.0)

Introduction

ECU Options

  • An ECU software may be configured by multiple options (data values).
    • Typically there may be dozens of these options in an engine ECU.
  • Each combination of options is a (build) configuration of the ECU.
    • For 10 options, there are 2^10 = 1024 possible configurations.
    • For 20 options, there are 2^20 = over a million possible configurations.
    • The real number of different configurations may run into the hundreds.
  • You can use a CANdela variant to describe a configuration.
    • The contents of the variant defines the diagnostic features of the configuration.
    • The contents is defined at the time of authoring in CANdelaStudio.
    • This is practical for a small number of options (and configurations).
    • For a large number of options, using variants may be impractical to define in CANdelaStudio.
    • At runtime, a test system will detect the variant (configuration) using Identifying Features.
  • As an alternative, you can use Vehicle System Groups, also called Optional Subsystems in this context.

Solution: Optional Subsystems

Identifying Feature for Vehicle System Groups

  • A data object represents the option in the ECU and on the line,
    • e.g. "Fog Lamps Front".
  • An Identifying Feature [VSG-R150] (at Vehicle System Groups, not at variants) references the data object.
    • for the variant of the data object see [VSG-R150].
  • A Vehicle System Group (Optional Subsystem) specifies a value (Identifying Pattern) for the Identifying Feature,
    • e.g. "Fog Lamps Front" == 1.
  • A diagnostic instance, e.g. "Front Fog Lamp Relay", associated with the Vehicle System Group is only available in an implemented ECU if the ECU actually returns the value (Identifying Pattern) defined for the data object.

Effect

  • Using Optional Subsystems is practical even for a large number of options.
  • The contents of the configuration...
    • need not be known at authoring time in CANdelaStudio,
    • but may be known only during a build for a specific customer order, to be detected at runtime.
  • A single variant can support all of the build options.
  • The feature does not allow changing the definition of any diagnostic instance within a variant.
  • All that can change is which diagnostic instances are optionally supported by any implemented instance of a variant.
  • The feature does not affect the mechanism of code generation.
    • The code of the diagnostic instances is present in the ECU,
    • but is not available for communication.

Semantics

For a VSG without Identifying Feature, the semantics of associating it a e.g. with diagnostic instance is straightforward: when filtering for the VSG, the diagnostic instance either qualifies, or not.

This is different for a VSG with Identifying Feature (an optional subsystem), which describes whether the services of the diagnostic instance are actually implemented:

  • If a diagnostic instance is not associated with any optional subsystem, it is treated as implemented

  • If a diagnostic instance is associated with at least one optional subsystem, it is treated as implemented only iff. at least one of the optional subsystems is identified at runtime.

Identifying Feature

[VSG-R150] The Identifying Feature of a Vehicle System Group may reference a data object in any variant (CDS-30215 9.1; before: base variant only).

Consistency Condition: Existence of Specified Path

[VSG-R160 Specified Path]

Existence of Specified Path

  • The Identifying Feature must reference an existing service and data object.
  • i.e. the paths of the Identifying Feature must...
    • denote an existing variant, and
    • be resolvable in that Variant.

Notes:

  • "Specified Path" = the path as selected in the "New Feature" and "Change Path" dialog.
  • The Specified Path must be valid even if the Variant is not available [VSG-R080] for any VSG.
  • As of 9.1, when you rename the data object or delete its diagnostic instance, CANdelaStudio does not automatically update the reference at the Identifying Feature but renders it "not usable" so that you can control how to set the new value.

Consistency Condition: Existence of Resolved Path in Variants

[VSG-R170 Resolved Path]

Existence of Resolved Path in Variants

  • If any VSG is available for a variant V,
  • then the service and data object of the Identifying Feature must exist in V.
  • i.e. the paths of the Identifying Feature must be resolvable in V.

Notes:

  • "Resolved Path in Variant V" = path as specified by the user, with variant part replaced.
  • It does not matter whether the VSG has an Identifying Pattern for the Identifying Feature or not.
  • Some operations that may lead to a violation:
    • set VSG available for Variant
    • delete diagnostic instance
    • rename data object
