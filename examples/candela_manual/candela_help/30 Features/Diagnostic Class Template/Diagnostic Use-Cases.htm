Diagnostic Use-Cases

A CANdela diagnostic class template typically represents a diagnostic use-case, like Fault Memory, Live Data, Stored Data, ECU Reset etc.

Session

While a test system communicates with an ECU, it can switch between multiple sessions. A session restricts the available ECU services. If the test system sends a request of a service not available in the current session, the ECU responds with a negative response.

Examples

    Default Session, Programming Session, End-of-Line Session

Security

Some diagnostic functionality is relevant for security and may be performed only by authorized persons. Therefore this functionality is protected by access authorization. There can even be multiple levels of security.

To acquire access to the protected functionality, a test system gets a “seed” value from the ECU, computes the matching key and sends it back to the ECU.

Identification

An ECU typically contains several data objects that describe the development or equipment version of the ECU. A test system requests and evaluates these data objects to identify the ECU version.

Examples

    Hardware Version, Software Version, Serial Number

Dynamic Data

An ECU provides different kinds of data to a test system: dynamic measurements, dynamically computed values, or static information. The ECU typically provides the data in packets guided by ECU functionality or by the needs of a specific tester application.

One such data packet can be seen as a “Freeze Frame” – the information is a copy of the internal ECU data at a given point in time.

Examples

    Supply Voltage, Wheel Speed, Break Pressure

Fault Memory

The nonvolatile memory of the ECU records information about errors in the ECU. The ECU detects and tracks such errors without a trigger from outside (on-board diagnosis). In the ECU implementation, the errors are handled as “events”. An event is reported to the test system via a “diagnostic trouble code” (DTC).

In addition to the event (diagnostic trouble code), the ECU records data from the environment. The data reflect the situation at a specific point in time of the error detection algorithm, e.g. at the first occurrence or at the last occurrence.

Examples

    DTC: C003713 (0x403713) Wheel Speed Sensor – Circuit Open
    Environment data: Odometer Value, Wheel Speed

I/O Control

An ECU lets a test system control the connected actors or manipulate internal values. This manipulation enables a check of individual internal components.

Typically, the manipulated units are combined to groups that are modified together. This avoids inconsistent values of related switches.

There are different types of I/O Controls:

Type Description Example
Push button (unary) Pressing the button triggers an action once. The action terminates without further intervention. Start the movement test of a speedometer pointer.
Control the valve of a brake system for some time span.
Switch (binary) A switch can be toggled between two states. The most frequent meaning is on/off, but there are switches with other meanings. Move a window lift up and down,
Turn an air blower on and off
Open and close a valve in the brake system
Switch (selection) Switch with more than two states. Select the language for the instrument cluster
Select a stored seat position
Setting (continuous) Modify a value within a range of valid values (e.g. using a continuous control dial) Set the throttle valve to a specified angle

UDS 0x2F InputOutputControlByIdentifier

  • The UDS request parameter controlOptionRecord...
    • defines 1..n data objects,
    • each data object may have any length,
    • each data object represents an individual ECU parameter to control (input or output overwrite).
  • The optional UDS request parameter controlEnableMaskRecord...
    • according with UDS, shall only be supported if the controlOptionRecord contains more than one data object,
    • contains 1 bit for each data object in the controlOptionRecord.
    • The first data object corresponds with bit 7 (most significant bit) of the first byte in the controlOptionRecord,
    • the second data object corresponds with bit 6, etc.
    • E.g. the 16th data object corresponds with bit 0 in the second byte in the controlOptionRecord.

Caveat:

  • you need a bitfield to describe the individual bits of the controlOptionRecord.
  • In a typical configuration,
    • CANdelaStudio shows bit 0 on top,
    • but that bit corresponds with the 8th data object!
    • Cf. option "Display most Significant Bit on Top" [DOC-R500]

Example:

  • For 3 data objects
    • LED_R
    • LED_G
    • LED_B
  • ... you need a 1-byte bitfield with elements like:
    • Bits 0-4: (reserved 5 bits)
    • Bit 5: LED_B_Mask
    • Bit 6: LED_G_Mask
    • Bit 7: LED_R_Mask

Parameterization

The nonvolatile memory of the ECU stores calibration values and parameters. These are input for control systems. Some of the values can be changed over the diagnostic interface (even while driving). In development this feature is often used to investigate how different configurations impact the functionality of the ECU. Like for I/C Control, typically multiple single parameters are combined to groups to save memory.

There are different types of parameters, like for I/O Control: binary switch, selection and continuous setting.

Examples

Type Example
Switch (binary) Turn automatic fan control on/off
Switch (selection) Activate a set of parameter values
Setting (continuous) Adapt a calibration value of tyre pressure control

Variant Coding

Often an ECU is used in different model types and vehicle configurations. Typically, a diagnostic tester configures the ECU at end-of-line – it writes software switches and parameters into the nonvolatile ECU memory.

Variant coding works much like Parameterization, there are the same types of parameters.

Examples

Type Example
Switch (binary) Extra equipment „cruise control“ included?
Right-hand / left-hand driven?
Switch (selection) Country: US, Europe, Japan, ...
Mounted tire size
Setting (continuous) Breakaway point for the speed regulation

Routine

Some ECUs allow the start of routines over the diagnostic interface. A function is a routine that returns a result; a procedure is a routine that does not return a result.

There are two types of routines:

Type Description Example
self-terminating The routine terminates without external activity Trigger an ECU Reset
Start calibration of the gearbox, returns the calibration value
not self-terminating The test system has to terminate the routine -

Data Transfer (Upload, Download)

Some ECUs allow transfer of bulk data between test system and the ECU:

  • Upload: from the ECU to the test system;
  • Download: from the test system to the ECU.
