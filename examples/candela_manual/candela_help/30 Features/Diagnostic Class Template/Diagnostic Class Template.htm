Diagnostic Class Template

UDS: Functional Units

UDS groups services by “functional units”, like

  • Diagnostic and Communication Management (services 0x10, 0x11, 0x27, 0x28…)
  • Data Transmission (services 0x22, 0x23, …)
  • Stored Data Transmission (services (0x14, 0x19)
  • InputOutput Control (service 0x2F)
  • Remove Activation of Routine (service 0x31), and
  • Upload Download (services 0x34 .. 0x37).

Diagnostic Use-Case

Likewise, a CANdela diagnostic class template typically represents a diagnostic use-case, like Fault Memory, Live Data, Stored Data, ECU Reset etc.

See the description of Diagnostic Use-Cases.

While from a diagnostic point of view, these use-cases are rather different, the CANdela data model handles them in a uniform, generic way.

Object Orientation

A Diagnostic Class Template combines...

  • a subset of protocol services (from UDS or any other protocol) with
  • the data for the “proxy components” (entry points for payload data) from these ProtocolServices.

This is an instance of object orientation:

  • A class is a blue-print for instances
  • An instance combines
    • methods (to be executed) with...
    • data (to be operated on by methods)
Object Orientation CANdela Data Model
Class Diagnostic Class Template
Object Instance Diagnostic Instance ("instance" of a diagnostic class (template))
Method Service
Data Data Objects

The "Class" (diagnostic class template) properties relate with the "Object Instance" (diagnostic instance) properties as follows

Diagnostic Class Template Diagnostic Instance
Used Protocol Services Services
Combined Components Identifier, telegram tables

Diagnostic Class Template in CANdela

The Diagnostic Class Template is predefined in the document template, typically by an OEM. It can be modified in Expert View only.

It can require data from multiple Protocol Services to be identical (shared), typically for a read (UDS 0x22) and write (UDS 0x2E) service, see Combined Component.

It can be configured to occur only once, see below.

See also the diagnostic class and diagnostic instance features and the Diagnostic Class Template Dialog.

Used Protocol Service

[DCLT-R160] A Diagnostic Class Template contains Used Protocol Services [DCLT-R305]:

  • [DCLT-R160-UsedPS] with Class Type != "Jobs"/"Flash jobs", it must contain 1..n Used Protocol Services;
  • [DCLT-R160-NoUsedPS] only with Class Type "Jobs"/"Flash jobs" [DCLT-R210], it may contain no Used Protocol Service.

Occurs only once per Variant (Singleton)

[DCLT-R150] The diagnostic class template controls the number of diagnostic instances in a variant:

  • [DCLT-R150-singleton] only one diagnostic instance ("singleton"),
    • e.g. for Fault Memory
    • the CANdelaStudio tree shows such a diagnostic instance directly in the chapter "Supported diagnostic classes" of the variant.
    • this holds if the Used Protocol Services contain a Variable Value Component.
  • [DCLT-R150-multiple] multiple diagnostic instances within a diagnostic class,
    • distinguished by the Identifier
    • e.g. for Stored Data
    • the CANdelaStudio tree shows these diagnostic instance below the diagnostic class.

For an overview, see the Protocol Service page.

Class Type

[DCLT-R200] A diagnostic class template has a property "Class Type" that specifies the type (aspect, use-case) of diagnostics handled by the services of the diagnostic class.

CANdelaStudio, import/export and tools that consume CANdela data may rely on this property to handle the different diagnostic use-cases in a special way (beyond the generic transport of "service + data").

Class Type Description
Communication Communication management of the ECU.
Session Session management.
Security Control access to security-critical data of the ECU, e.g. switch the ECU into programming mode if the correct key was transmitted.
Identification Services to identify the concrete variant of the ECU.
Fault Memory Describe DTCs, snapshot data, extended data records, Events [EV-R020-Type].
Variant Coding Services that modify ECU functionality.
Current Data Read current data (live data), e.g. the data of a temperature sensor or a potentiometer.
Stored Data Read and write stored data in the ECU, e.g. the model state and serial number of the vehicle or ECU.
Memory Directly access individual memory ranges - read or write them.
Control Input/output control (IO control) of the ECU.
Calibration Calibrate sensors connected to the ECU.
Routine Execute routines of the ECU and read out the results of the routines.
Function Particular functions of the ECU, e.g. reset of the ECU to the activated state ("ECU Reset").
Download Read data from the ECU's flash ROM
Upload Write data to the ECU's flash ROM.
Jobs [DCLT-R210] Job containers.
Flash jobs [DCLT-R210] Flash job containers.
Tester Present Services to signal the presence of a test system.

Class Type "Jobs"/"Flash jobs"

[DCLT-R210] A Diagnostic Class Template with Class Type "Jobs" or "Flash jobs"...

  • [DCLT-R160-NoUsedPS] ... is allowed to have no Used ProtocolService [DCLT-R305],
    • therefore the associated Diagnostic Classes cannot have diagnostic instances and services [JCNR-R110]
  • [DCLT-R210-Singleton] ... must be a singleton [DCLT-R150-singleton],
    • which makes it a top-level Job Container [JCNR-R110]
  • [DCLT-R210-Jobs] ... may contain Jobs without being restricted by existing services.
  • Note: CANdelaStudio represents an instance of the "Documentation" class as such a Job Container [DCLT-D010].

Fault Memory

  • [DCLTOP-R200] When you modify the class type from "Fault Memory" to another value, CANdelaStudio...
    • [DCLTOP-R200-Events] deletes all Events
    • [DCLTOP-R200-SR] deletes all Snapshot Records in AUTOSAR Fault Memory
    • [DCLTOP-R200-EDR] deletes all Extended Data Records in AUTOSAR Fault Memory
    • cf. the corrections on loading [LOAD-R200].

Order of Diagnostic Class Templates

Recommendation: sort the diagnostic class templates according with the functional areas described in UDS ISO/DIS 14230-3:

  1. Diagnostic management
  2. Data transmission
  3. Stored data transmission
  4. Input/Output control
  5. Remote activation of routine
  6. Upload/Download

Note: you can adjust the sequence of the diagnostic class templates with the commands Edit | "Move up" or Edit | "Move down".

Default Target Groups (CDS-7885 6.0)

A diagnostic class template has a set of of default target groups.

CANdelaStudio assigns this set of target groups to new diagnostic instances, services and job containers.

Documentation Diagnostic Class (Ford CDS-12812 6.0)

[DCLT-D001]: if the following special attribute exists at a diagnostic class template D:

  • Type: unsigned, overwritten value = 1 (true), default value = 0
  • Name, qualifier: “Documentation”
  • Attribute category: “Editor”
  • Visibility: Standard view: no, Editable: no, Report to specification: no

then D is considered to be a “documentation” class. The default attribute must be added by Expert users or by a plug-in delivered separately.

[DCLT-D010] CANdelaStudio represents an instance of the "Documentation" class as a Job Container [JCNR-R110].

Requirements Support

[DCLT-R300] Diagnostic Class Template "Supports Requirements" A Diagnostic Class Template has the information whether the Diagnostic Classes based on it support requirements (since 8.0, CDS-27397).

The property can be edited in expert mode...

  • in the diagnostic class template property page and
  • in the settings of the requirements dialog [RQUI-R100-DiagnosticClasses].

  • It is also shown read-only in the diagnostic class property dialog.

  • [DCLT-R300-Update] The property defines a "weak" convention for algorithms: if false, in Diagnostic Classes based on this Diagnostic Class Template, CANdelaStudio does not generate or update requirements or update diagnostic objects.

But the property is not a hard condition for data: if false, diagnostic objects may still refer to requirements, and the user may interactively paste data objects (having requirements) from the import pool, without restriction.

Diagnostic Classes Relevant for DIDs

A Diagnostic Class is relevant for DIDs if it contains a signature described in Identifiers in UDS and OBD Services.

Examples:

  • diagnostic class “Stored Data” with positive response 0x62 <2 byte ID> zz and 0x6E <2 byte ID> zz is relevant for DIDs due to 0x22 and 0x2E.
  • diagnostic class “Periodic Data” with positive response 0x62 F2 <1 byte ID> zz and 0x6A 0x01 <1 byte ID> zz is relevant for DIDs due to service 0x22.
  • diagnostic class “PIDs” with positive response 0x41 <1 byte ID> zz is relevant for DIDs due to service 0x01.
  • diagnostic class “Memory” with positive response 0x63 zz is not relevant for DIDs.
