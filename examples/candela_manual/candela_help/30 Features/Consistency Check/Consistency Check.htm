Functional Request on CAN (CDS-16347 6.5 SP2)

[CCSVC-D010] "document supports CAN" :=

  • there is at least one activated interface...
  • which contains a ComParam with (normalized) qualifier "BusType" set to value "CAN",
  • or "BusType" is not defined at all.

[CCSVC-D020] "supports extended or mixed addressing" :=

  • there is at least one activated interface...
  • which contains a ComParam with (normalized) qualifier "AddressingSchemeFunc" which is set to "Extended" or "Mixed",
  • or which does not contain this ComParam but a ComParam "AddressingScheme" exists with these values.

[CCSVC-R010] The constraints check shows a warning for a service (allows exports and loading in tools) if...

  • the document property "Diagnostics based on" [DOC-R110] is "Daimler" (CDS-21248 7.1),
  • the "document supports CAN" [CCSVC-D010],
  • and the service supports a functional request,
  • and...
    • the request length of the service is > 7 bytes;
    • or: at least one activated interface "supports functional extended or mixed addressing" [CCSVC-D020],
    • ... and the request length of the service is > 6 bytes.
  • and the existing data, i.e. the minimum size of the request, actually break the limit (CDS-19984 7.0 SP2),
    • e.g. no warning if a proxy component in the template has unlimited maximum size, which potentially allows a violation of the length limit, but does not violate it in itself;
    • e.g. no warning if an iteration data type allows zero repetions but potentially exceeds the limit with one repetition.

Discussion

This check has been discussed controversially, because it restricts the application layer (UDS) based on a specific network layer (CAN):

  • ISO diagnostic specifications are based upon the OSI 7 layer model
  • ISO 14229 (UDS) requires the application layer, if the ECU supports functional addressing, to support functional addressing for all services;
  • lower layers may prevent a request greater than a certain length to be passed up to the application
    • e.g. ISO 15765-2 network layer - UDS on CAN

Example: service 0x34 (requestDownload)

  • an application may support the service regardless of whether the request is addressed physically or functionally;
    • a request valid for the application may e.g. be 11 bytes;
  • but the CAN network layer allows only 7 bytes;
  • therefore an 11 byte request...
    • cannot be sent functionally on the CAN network layer,
    • but is valid for the application;
  • ... but a 1 byte request...
    • can be sent functionally on the CAN network layer
    • ... and will be processed by the application and handled as invalid (NRC 0x13 - invalid length).
  • ... but after moving...
    • to a different physical layer,
    • that application might allow functional requests greater than 10 bytes.

Benefit of omitting the check:

  • keep the restriction of the network layer out of the CANdela (UDS application) description, i.e. describe the service being sent functionally, anyway;
  • check the network layer details e.g. in CANoe.DiVa.;
  • by this, avoid a conflict describing an ECU that supports diagnostics on multiple connections where...
    • the service can be sent functionally on the one (e.g. DoIP)
    • ... but not on the other (e.g. CAN).

    • [EV-R610-Qualified] Indicator Name and Qualifier must be unique in the list [EV-R600]

Same Diagnostic Instance

[CCEV-R100] For violations of the condition "must be in the same diagnostic instance", ...

  • consistency check writes an error
  • ... and leaves the data unchanged (it is a read-only check)
  • The next loading will reset the reference with an error message.
  • By construction, the inconsistency should never occur.
