Introduction

Fault Memory in System Context

In a Fault Memory implementation,

  • a Monitor (routine) watches for failure of a hardware component, communication or algorithm.
  • A Monitor identifies a specific fault type (e.g. short to ground).
  • A Monitor reports an Event if it detects a failure,
    • the status of the Event represents the monitor result: Boolean FAILED.
  • The Event Kind represents the location of the Monitor:
    • SWC: in a Software Component (reported via RTE SetEventStatus), or
    • BSW: in a Basis Software module (via C-API Dem_SetEventStatus).
  • The AUTOSAR Diagnostic Event Manager (DEM) receives and processes these Events.
  • A Monitor may debounce internally
    • call the DEM only when the result changes,
    • i.e. when there is a qualified result (passed or failed),
    • otherwise it calls the DEM for every test result, even if unchanged.
  • Based on the Event result, the DEM manages the UDS Status Byte [FMUDS-D050].
  • When requested over a diagnostic protocol like UDS,
    • ... a DTC represents one or multiple Events.
  • A DTC is either...
    • a UDS DTC (non OBD-relevant)
    • an OBDII DTC (OBD-relevant)
  • A UDS DTC directly represents Events,
    • an OBDII DTC is associated with one or multiple UDS DTCs, not directly with Events.
  • The DTC significance is either...
    • fault: a failure of the component/ECU itself
    • occurrence: indicates additional information, maybe a condition outside the ECU

The relationship of Events and DTCs can be...

  • 1:1 - each Event is directly represented by a DTC;
  • n:1 - multiple Events are combined to one DTC
  • 1:0 - an internal Event has no DTC representation.
  • 1:n - one Event is represented by multiple DTCs
    • Note: the CANdela data model does not support this cardinality.

In AUTOSAR, ...

  • the Diagnostic Event Manager (DEM) module handles Events as an atomic unit;
  • the Diagnostic Extract (DEXT) specification describes a format to exchange a description of Events.

Diagnostic formats to describe Events:

  • According with the DEXT specification, other formats are not well suited:
  • "ODX lacks in fault memory details and ECU-C (which was never designed for becoming the vehicle for data exchange between different organizations) has a very generic nature that renders the enforcement of a strict model formalization very difficult."
  • [ODXE-D115] describes this for ODX export.
  • [MENU-R160] describes this for MDX export.

Events in CANdelaStudio before v12: Based on DTCs

From the beginning, the CANdela data model...

  • described DTCs with a set of properties (DTC Columns) defined in the OEM specific template,
    • like "Enable Conditions", "Operation Cycle", "Self-Healing Counter", "DTC Failed Threshold"
  • but did not describe Events as separate objects, because they are not directly represented in the diagnostic protocol.

In the past, in typical templates some DTC properties actually represented Event properties.

The DEXT export implements heuristics for a fixed set of known OEM templates to derive AUTOSAR Events from properties of DTCs.

Events in CANdelaStudio 12

Starting with CANdelaStudio 12, ...

  • the CANdela data model represents Events as separate objects.
  • This clarifies the distinction between Event properties and DTC properties,
  • ... allows Event Combination (n Events for 1 DTC)
  • ... and (in the future) will support direct exchange of Event descriptions via DEXT.

Events are part of a Fault Memory diagnostic instance (like DTCs and Snapshot Data).

Events, DTCs and Protocol

  • You can describe Events independently of DTCs.
  • Optionally, an Event may reference a DTC.
  • Unlike DTCs, Events are not available in the DTC Pool on document level.
  • Since Events are a topic of the ECU implementation, they are independent of the diagnostic protocol
    • Therefore Events can be defined for any value of the Protocol Standard [DOCUI-R120] in a CANdela document [EV-R020-Protocol].
    • But note: Events are not allowed in an OBDII Fault Memory Diagnostic Instance [EV-R020-OBDII].

Events and Variants

When using variants in a CANdela document, ...

  • the Fault Memory including its Events can be referenced [DI-D010] in multiple variants, to keep them identical.
  • If you want to modify one variant only, e.g. ...
    • add an Event,
    • modify an Event Property or
    • map the Event with a different DTC,
  • ... you must first perform "Replace Reference with Copy" [DIOP-R040] on the diagnostic instance.

Using Events in Documents Created before v12

For consistency of existing CANdela documents, DEXT export...

  • as a default still derives DEXT Events from CANdela DTCs,
  • ignoring Events described in the CANdela document.
  • You can explore the Events feature and describe Events, but using them for DEXT export needs an explicit setup step [DOCUI-R600] in the CANdela document.
    • In this case, you should review the existing DTC columns, some may become obsolete.
    • See [VUDS-D410] for this step done in the Vector UDS Template.
  • CANdelaStudio does not automatically migrate DTC column values [EV-R250-DTC] to Event properties, since DTC columns vary from template to template.
  • For migrating data of a given template, Vector may support you on basis of a service project.
  • See also the migration chapter [EV-R250].

Using Events in New Documents (v12)

  • In templates based on CANdelaStudio 12 or newer, you can enable the use of Events [DOCUI-R600] right away.
  • You may consider removing all DTC columns that actually represent Event properties.
  • See also the migration chapter [EV-R250].

Events in Report

Events are not contained in the Report, see [RP-R320].
