Events Data Model in CANdela

The following specifies the details of the Events data model in a CANdela document or template.

The initial CANdela Events data model in v12 corresponds with the Events data model in AUTOSAR 4.4 DEXT, with minor deviations [EV-D100] (below).

For the meaning of the "Cardinality" information, see chapter "Legend: Cardinality" below.

Supports Events

[EV-R010] A CANdela document has a Boolean flag Supports Events.

  • Boolean
  • mandatory
  • [EV-R010-Default] default: false.
    • This is the value set after loading a file with version < 12 [EV-R250-Supp].
  • If false:
    • CANdelaStudio shows all Event dialogs.
      • Motivation: you may explore the feature.
    • But you cannot create Events.
    • You may create Event Master Data [EV-D040].
    • Data oriented exports, mainly DEXT Export [DEXT-R308], still use DTC properties for Events.
    • CANdelaStudio shows a hint above the Event list [EVUI-R030].
    • [EV-R010-NonEmpty] If the flag is false, the Event lists [EV-R020] must be empty.
  • If true:
    • You may create Events.
    • Data oriented exports do not use DTC properties, they use the Event list (even if it is empty).
  • You can modify the flag...
    • in File | Properties | Document Info [DOCUI-R600]
    • in Expert view only [EVOP-R010]
    • based on the operation [EVOP-R010]
  • See also
    • Paste [DIOP-R010-Events] of a Diagnostic Instance eventually skips Events
    • Paste as Reference [DIOP-D030-Events] of a Diagnostic Instance: dito.
    • [EVUI-R232] Modifying Operations in the DTC Events Mapping page are insensitive:
      • [EVUI-R244] "Create / Map Events"

Event List

[EV-R020] A Fault Memory Diagnostic Instance contains 0..n Events.

  • [EV-R020-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Events
  • [EV-R020-Type] Events are not allowed in a Diagnostic Instance of a type [DCLT-R200] other than "Fault Memory".
    • cf. modification of the class type [DCLTOP-R200-Events] and the correction on loading [LOAD-R200-Events].
  • [EV-R020-OBDII] Events are not allowed in an OBDII Fault Memory Diagnostic Instance.
    • An OBDII DTC is associated with one or multiple UDS DTCs, not directly with Events.
    • See [EV-R230-OBDII] for the Event to DTC reference.
  • [EV-R020-Protocol] Events are allowed without restriction by the Protocol Standard [DOCUI-R120]
    • except for OBDII DTCs (see previous item)
    • as noted in the introduction
    • Note: export to DEXT supports only J1939, UDS, UDS/WWH-OBD (not OBDII, KWP2000, other).
  • [EV-R020-UserDef] Events are allowed in a Fault Memory diagnostic instance of any Fault Memory Type: Primary or User Defined Memory [UDFM-D100].

[EV-R030] The Events have no persistent sort order.

  • Assumption: the user interface sorts them ascending by Name.
  • Accepted consequence: if an ECU implementation accesses Events by a numeric index, and you define a new Event, the numeric index of existing Events may change.

Event Properties

This chapter describes all properties (e.g. "Kind") and relationships (e.g. "references Operation Cycle") of an Event. Details for the related objects themselves (e.g. an Operation Cycle) are described in the following chapters.

[EV-R100] An Event has Name, Qualifier, Description.

  • [EV-R100-Qualified] Name and Qualifier must be unique in the list [EV-R020].

[ATTR-R050-Event] An Event has Default Attributes.

[EV-R110] Kind The Event kind describes which object triggers the Event:

  • Software Component (SWC) in the application
  • Basis Software (BSW)
  • Default: "Software Component"
  • Both kinds of Events can reference a DTC, see [EV-R230-Kind].

[EV-R120] Operation Cycle

  • defines the Operation Cycle used for qualifying of the Event
  • optional reference to an Operation Cycle [EV-R500]
  • Cardinality: Events 0..n -- 0..1 Operation Cycle
  • Default: none
  • The Event and the referenced Operation Cycle must both exist within the same diagnostic instance.
  • Related:
    • DEXT: [TPS_DEXT_01086] DiagnosticEventToOperationCycleMapping
    • DEXT: [TPS_DEXT_01087] Qualifying
    • DEXT Export: [DEXT-R3120]

[EV-R130] Failure Cycle Counter Threshold

  • also called...
    • "Trip Counter"
    • "Number of Trips - Active" (in the Vector UDS Template before v2.5.0)
  • The threshold defines...
    • the number of Operation Cycles (as specified by [EV-R120] above) having failures,
    • needed to confirm the DTC (i.e. needed to set UDS status bit 3 "ConfirmedDTC", turning MIL on)
  • Value 0:
    • the standard UDS behavior for confirming an Event
    • UDS status bit ConfirmedDTC will be set with the first qualified FAILED Event status
  • Value 1:
    • UDS status bit ConfirmedDTC will be set when the Event fails again in the next Operation Cycle.
  • Larger values n specify setting ConfirmedDTC in the n-th next Operation Cycle.
  • optional property
  • typical values: 0 (UDS), 2 or 3 (OBD)
  • unsigned integer (32 bit),
    • value range: <= 255
    • intentionally no constraint in CANdela, since in the future, bigger values may be required
  • Default: 0
  • Related:
    • in DEM, this is a mandatory property
    • DEXT: [TPS_DEXT_01083] eventFailureCycleCounterThreshold
    • DEM: [SWS_Dem_00391] status bit transition for UDS status bit 3 ConfirmedDTC
    • DEM: [SWS_Dem_00773] increment counter when Operation Cycle ends
    • German: "Schwellwert Fehler-Betriebszyklen"

[EV-R140] Indicator Connections: An Event in status "failed" may optionally be indicated to the driver, using one or more connected Indicators (like the MIL).

  • In the data model, an Event has a list of Indicator Connections [EV-R300].
    • [EV-R140-noSort] the list has no persistent sort order (the user interface should sort it by the Indicator name).
  • One Indicator Connection associates...
    • an Indicator and
    • an Operation Cycle
    • with the Event.
  • [EV-R140-unique] A given Indicator can be used only once for the same Event ("primary key").
  • [EV-R140-Card] Cardinality: Events 1 -- 0..n Indicator Connection
  • Default: none
  • Having no Indicator connected means the Event will not be visible to the driver.
  • Related:
    • DEXT Export: [DEXT-R3140]

[EV-R150] Freeze Frame Prestored ("Prestore Freeze Frame")

  • defines whether the Event uses a prestored freeze frame
    • (using the operations PrestoreFreezeFrame and ClearPrestoredFreezeFrame),
    • and in which memory the freeze frame shall be pre-stored.
  • Boolean
    • false The Freeze Frame shall not be prestored for the Event.
    • true The Freeze Frame shall be prestored for the Event, see the next property [EV-R155] for the type of memory.
  • mandatory
  • Default: false
  • Related:
    • DEXT: [TPS_DEXT_03011] prestorageFreezeFrame.

[EV-R155] Freeze Frame Prestored nonvolatile ("... in Memory"):

  • If the Freeze Frame is prestored [EV-R150], this property defines the type of memory:
  • Boolean
    • undefined The Freeze Frame...
      • shall not be prestored, or
      • shall be prestored, either in volatile or nonvolatile memory, but the author in CANdelaStudio does not yet decide in which one.
    • false The Freeze Frame shall be prestored in volatile memory, can be lost at shutdown.
    • true The Freeze Frame shall be prestored in nonvolatile memory, preserved at shutdown.
  • mandatory
  • [EV-D155] Note: if the Freeze Frame is not prestored [EV-R150], this property should be undefined. The data model does not enforce this - a consuming client must first check the "Freeze Frame Prestored" property, anyway.
  • Default "undefined"
  • Related:
    • DEXT: [TPS_DEXT_03011] prestoredFreezeframeStoredInNvm (added in AUTOSAR 4.4).

[EV-R165] Clear Allowed

  • The Event can trigger clearing the Fault Memory,
    • i.e. deleting snapshot data and extended data and resetting the status byte (UDS: service 0x14, OBDII: service 0x04).
  • enumeration
  • mandatory
  • Default: always
  • defines how a clearing request for the Event will be handled (DEXT enum in parentheses):
    • always (always): a clearing request for the Event will be executed unconditionally.
    • requires callback execution (requiresCallbackExecution): a clearing request for an Event calls a callback to an SWC in order to allow or prohibit clearing, i.e. the developer of the SWC decides.
    • Note: AUTOSAR 4.2 had the value never (clearing is intentionally not possible for the Event), but later AUTOSAR versions no more support this value; CANdela doesn't support it, either.
  • Related:
    • DEXT: [TPS_DEXT_03011] eventClearAllowed, table 6.5 (as of AUTOSAR 4.4)

[EV-R170] Clear Behavior ("If Clear Denied")

  • In case the callback for a clearing request (see "Clear Allowed" [EV-R165] above) prohibits clearing, nevertheless the UDS DTC Status Byte can be adapted.
  • Enumeration predefined by AUTOSAR (DEXT enum in parentheses):
    • undefined (maybe Clear Allowed is false)
    • no status byte change (noStatusByteChange)
    • reset operation cycle and readiness (onlyThisCycleAndReadiness): the Operation Cycle and Readiness bits of the Status Byte are reset (bits 1/4-6), cf. UDS DTC Status Byte [FMUDS-D050].
  • mandatory
  • Default: "undefined"
  • Related:
    • DEXT: [TPS_DEXT_03011] clearEventBehavior, table 6.6 (as of AUTOSAR 4.4)
    • DEM: [SWS_Dem_00669] DemClearEventAllowed DEM_ONLY_THIS_CYCLE_AND_READINESS
    • Spelling: CANdela prefers the American English spelling "behavior" (also used in the DEXT spec) over the British English spelling "behaviour".

[EV-R190] Recoverable in Same Operation Cycle

  • If the Event is reported as "passed",
    • it may reset the indication of a failed test in the current operation cycle
    • (before clearing the Fault Memory would do it, anyway).
  • Boolean
    • undefined
    • false Event "passed" is ignored, does not reset the failed test ("DTC ledge" - the Event remains failed)
    • true Event "passed" resets the failed test
  • optional
  • Default: undefined
  • Related:
    • DEXT: [TPS_DEXT_03011] recoverableInSameOperationCycle

[EV-R200] Enable Conditions An Event may depend on Enable Conditions:

  • as long as the Enable Conditions are not fulfilled, ...
    • the monitor is still running and reporting Events as passed or failed,
    • but the Diagnostic Event Manager does not consider the Event being valid
    • and therefore does not accept it (i.e. ignores it, does not store data)
  • each Enable Condition...
    • represents a state of the ECU,
    • available as a port (using the Qualifier of the Enable Condition).
  • [EV-D210] Note: do not mix an Enable Condition with the typical DTC property "Set Condition":
    • an Enable Condition is a formal precondition in the ECU implementation for accepting an Event;
      • E.g. "Speed > 0 km/h"
    • a Set Condition is an informal description of the system conditions of a DTC (for a service technician);
      • E.g. "Current consumption of window lift motor is >10A for more than 2 seconds".
  • Data model: optional reference...
    • to a Condition [EV-R700]
    • or to a Condition Group [EV-R800]
  • Having no Enable Condition means the Event will always be accepted.
  • Default: reference not set.
  • Cardinality: Events 0..n -- 0..1 (Enable Condition or Enable Condition Group)
  • The Event and the referenced Enable Condition or Enable Condition Group must both exist within the same diagnostic instance.
  • Related:
    • DEXT: [TPS_DEXT_03001], [TPS_DEXT_03015]
    • DEXT Export: [DEXT-R3200]
    • German: "Aktivierungsbedingungen"

[EV-R210] Storage Conditions An Event may depend on Storage Conditions:

  • as long as the Storage Conditions are not fulfilled, the event...
    • may be accepted
    • but is not stored in the event memory.
  • An Event that has not been accepted cannot be stored.
  • Data model: optional reference...
    • to a Condition [EV-R700]
    • or to a Condition Group [EV-R800]
  • Having no Storage Condition means the Event - if accepted - will be stored in any case.
  • Default: reference not set.
  • The Event and the referenced Storage Condition or Storage Condition Group must both exist within the same diagnostic instance.
  • Related:
    • DEXT: [TPS_DEXT_03001]
    • German: "Speicherbedingungen"

[EV-R215] CANdelaStudio does not restrict references from a given Event to a given Condition:

  • a Condition may be referenced as Enable Condition [EV-R200], Storage Condition [EV-R210], or even both.
    • Typically, within a CANdela document, either Enable Conditions or Storage Conditions will be used.
  • a Condition may be referenced either directly, or indirectly via a Condition Group [EV-R800].

[EV-R220] Debounce Algorithm

  • Reaching the "failed" and "passed" state of the Event may be debounced by DEM.
  • optional reference to a Debounce Algorithm [EV-R1100]
  • If no reference specified, ...
    • the DEM does not provide debouncing for the Event,
    • so the application may manage debouncing itself (Monitor internal debouncing),
    • or the Event is not debounced at all.
  • Default: reference not specified
  • Cardinality: Events 0..n -- 0..1 Debounce Algorithm
  • The Event and the referenced Debounce Algorithm must both exist within the same diagnostic instance.
  • Related:
    • DEXT: [TPS_DEXT_03004] DiagnosticEventToDebounceAlgorithmMapping
    • DEXT Export: [DEXT-R3220]

An Event may reference a DTC, see [EV-R230] below.

Indicator Connection

  • An Event in status "failed" may optionally be indicated to the driver,
    • using one or more connected Indicators (like the MIL).
  • For each of the connected Indicators,
    • an Operation Cycle defines the switching off (healing) of the Indicator.
  • The further properties described in this chapter specific for the connection:
    • if two Events reference the same Operation Cycle,
    • the properties may vary between one Event and the other.

[EV-R300] An Indicator Connection (defined [EV-R140] at an Event) contains the following references and properties.

[ATTR-R050-IndConn] An Indicator Connection has Default Attributes (CDS-71547 v13).

[EV-R305] Indicator An Indicator Connection references an Indicator [EV-R600].

  • The reference is mandatory
  • The Event and the referenced Indicator must both exist within the same diagnostic instance.
  • Cardinality:
    • Indicator Connection 1 -- 1 Indicator;
    • (indirectly) Event 0..n -- 0..n Indicator, see [EV-R140-unique].

[EV-R310] Behavior

  • An Indicator Connection has a Behavior.
    • It describes the behavior of the Indicator when the Event has status "failed".
  • Enumeration predefined by AUTOSAR (DEXT enum in parentheses):
    • undefined
    • Continuous On Mode (continuousOnMode): Indicator is active
    • Blink Mode (blinkMode): Indicator blinks
    • Blink or Continuous On Mode (blinkOrContinuousOnMode): Indicator is active and blinks
    • Slow Flashing Mode (slowFlashingMode): for a Flash Indicator Lamp: "Slow Flash"
    • Fast Flashing Mode (fastFlashingMode): for a Flash Indicator Lamp: "Fast Flash"
  • Default: "Continuous On Mode"
  • The behavior is mandatory.
  • Related:
    • DEXT: table 6.8 (as of AUTOSAR 4.4)

[EV-R320] Healing Cycle

  • An Indicator Connection references a Healing Cycle,
    • i.e. the Operation Cycle [EV-R500] in which the Indicator will be switched off.
  • When this Operation Cycle has been entered the number of times defined by the Healing Cycle Counter Threshold [EV-R330], ...
    • the Event will be "healed",
    • so the Indicator will be de-activated (switched off).
    • Example:
      • turn on the MIL during fault confirmation,
      • turn off the MIL after 3 OBD driving cycles without test failed (healing)
  • Data model: the Indicator Connection has a reference to an Operation Cycle [EV-R500].
  • The reference is mandatory.
  • Cardinality: Indicator Connection 0..n -- 1 Operation Cycle;
  • The Event and the referenced Operation Cycle must both exist within the same diagnostic instance.
  • [EV-R320-OpCycle] The Healing Cycle is not related with the Operation Cycle [EV-R120] of the Event.
  • Related:
    • German: "Rücksetzen-Betriebszyklus"

[EV-R330] Healing Cycle Counter Threshold

  • An Indicator Connection has a Counter Threshold:
    • the number of Healing Cycles (Operation Cycles without failure) before the Indicator will be de-activated.
    • E.g. value 0 means the Indicator will be de-activated directly in the next occurrence of the referenced Operation Cycle.
  • unsigned integer
  • The threshold is mandatory.
  • Default: 0
  • Related:
    • DEXT describes the threshold as healingCycleCounterThreshold directly at the DiagnosticIndicator [TPS_DEXT_03022], which means the threshold would be the same for all Events.
    • German: "Schwellwert für Rücksetzen"

Related to Indicator Connection:

  • DEXT describes the Indicator Connection as attribute connectedIndicator of type DiagnosticConnectedIndicator.

Event Master Data

[EV-D040] Event Master Data are lists of objects contained in a diagnostic instance, referenced from Events (and in versions after v12 maybe also by DTCs).

[EV-R050] Consistency Condition:

  • If a Diagnostic Instance contains an Event,
  • and the Event references Event Master Data,
    • Operation Cycle [EV-R120]
    • Enable Condition [EV-R200]
    • Storage Condition [EV-R210]
    • Debounce Algorithm [EV-R220]
    • Indicator Connections [EV-R140]
  • the Event Master Data must also be contained in the Diagnostic Instance.

Operation Cycle

  • Operation Cycles provide a basis for time-related activities.
  • The DEM manages the state of an Operation Cycle: started / ended.
  • This information can also be modified by DEM API calls.

[EV-R500] A Fault Memory Diagnostic Instance contains 0..n Operation Cycles.

  • [EV-R500-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Operation Cycle

[EV-R505] These Operation Cycles have no persistent sort order.

An Operation Cycle is referenced by an Event...

  • as Operation Cycle [EV-R120], or as
  • as Healing Cycle [EV-R320].

[EV-R510] An Operation Cycle has Name, Qualifier, Description.

  • [EV-R510-Qualified] Name and Qualifier must be unique in the list [EV-R500].

  • Example Operation Cycles (from AUTOSAR 4.4 chapter 7.6):
    • Ignition on/off cycle
    • Power up/power down cycle
    • OBD driving cycle
    • Engine warm up cycle
    • Operation active/passive cycle
    • Accumulated operating time

[EV-R520] Type

  • [EV-R520-Types] AUTOSAR defines the following Types (further types can be specified as part of a DEM delivery; German term in parentheses):
    • undefined
    • Ignition: power ON / OFF cycle ("Zündung")
    • Warmup: OBD warm-up cycle ("Warmlauf")
    • Power ("Betrieb")
    • Time: a time-based operation cycle
    • OBD Driving Cycle ("OBD-Fahrzyklus")
    • Other
  • the Type is mandatory
  • Default: "undefined"

[EV-R530] Automatic Start (Autostart)

  • defines whether...
    • the DEM automatically considers the Operation Cycle (re-) started during Dem_PreInit.
    • If yes, BSW modules can report related Events even before Dem_Init.
  • Boolean
  • mandatory
  • Default: true
  • Related:
    • DEXT: [TPS_DEXT_01087] cycleAutostart
    • DEM: [SWS_Dem_00180]

[ATTR-R050-OpCyc] An Operation Cycle has Default Attributes (CDS-71547 v13).

Related to Operation Cycle:

  • DEXT: [TPS_DEXT_01087] DiagnosticOperationCycle
  • DEXT Export: [DEXT-R3120]
  • German: "Betriebszyklus"

Indicator

An Indicator describes a visible means to inform the driver vehicle about a failure, like the Malfunction Indicator Lamp (MIL), or a specific text message.

[EV-R600] A Fault Memory Diagnostic Instance contains 0..n Event Indicators.

  • [EV-R600-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Event Indicator

[EV-R605] These Indicators have no persistent sort order.

An Indicator is referenced by an Indicator Connection, see [EV-R305].

[EV-R610] An Indicator has Name, Qualifier, Description.

  • [EV-R610-Qualified] Name and Qualifier must be unique in the list [EV-R600].

[EV-R620] An Indicator has a Type.

  • [EV-R620-Types] AUTOSAR defines the following Types (DEXT enum and German term in parentheses):
    • undefined: the Type is not yet known, or none of the Types defined in AUTOSAR appropriately describes the Indicator.
    • Protect Lamp (protectLamp, "Funktionsschutzlampe")
    • Warning (warning)
    • Amber Warning Lamp (amberWarning, "Orange Warnlampe")
    • Malfunction Indicator Lamp (malfunction, "Funktionsstörung")
    • Red Stop Lamp (redStopLamp, "Rote Stoplampe")
  • Default: "undefined"

[ATTR-R050-Ind] An Indicator has Default Attributes (CDS-71547 v13).

Related to Indicator:

  • DEXT: [TPS_DEXT_03022] DiagnosticIndicator, Table 6.57 (as of AUTOSAR 4.4). In CANdela, the property healingCycleCounterThreshold is at the Indicator Connection [EV-R330], not at the Indicator.
  • DEXT Export: [DEXT-R3140]
  • German: "Indikator"

Conditions (Condition / Condition Group)

[EV-D700] A Condition or Condition Group defines checks (e.g. correct voltage range) before a reported event actually gets...

  • accepted (Enable Condition [EV-R200]) or
  • stored (Storage Condition [EV-R210]).

Condition

For an Enable Condition [EV-R200] that is false,

  • the monitor is running, but
  • the Diagnostic Event Manager discards the Events reported by the monitor.

In the AUTOSAR implementation, a Condition (see [SWS_Dem_01038]) is represented by...

  • a Boolean state
  • a port with the Condition qualifier in the port name.

[EV-R700] A Fault Memory Diagnostic Instance contains 0..n Conditions.

  • [EV-R700-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Condition

[EV-R705] These Conditions have no persistent sort order.

A Condition is referenced...

  • by an Event as Enable Condition, see [EV-R200],
  • by an Event as Storage Condition, see [EV-R210], or
  • by a Condition Group, see [EV-R830].
  • See [EV-R215] for more on possible references from Events.

[EV-R710] A Condition has Name, Qualifier, Description.

  • [EV-R720-Qualified] Name and Qualifier must be unique for Conditions and Condition Groups together, i.e. in the combined lists of [EV-R700] and [EV-R800] (neither another Condition nor another Condition Group may have the same name or qualifier than a given Condition or Condition Group).

[EV-R720] Initially Enabled: defines the initial status after power up (before the condition is reported for the first time) for acceptance or storage of an Event.

  • Boolean
    • true: acceptance or storage is initially enabled
    • false: acceptance or storage is initially disabled.
  • Mandatory
  • Default: false (i.e. Condition is initially disabled)
  • Related:
    • DEXT: initValue
    • German: "anfangs aktiv"

[ATTR-R050-EvCond] A Condition has Default Attributes (CDS-71547 v13).

Related to Condition:

  • DEXT: DiagnosticCondition
  • DEXT Export: [DEXT-R3200]
    • [EV-R720-Use] DEXT distinguishes enable vs. storage conditions by type [TPS_DEXT_03001], CANdela leaves this distinction to the use [EV-R200] and [EV-R210] of a condition at an Event.
    • [EV-R720-Condition] In DEXT, the Event references a Condition Group, not a Condition; see the following chapter.
  • German: "Bedingung"

Condition Group

Conditions may be grouped.

Example: Condition Group "Driving" with the Conditions

  • Speed > 0 km/h
  • Door 1 closed
  • Door 2 closed
  • Door 3 closed
  • Door 4 closed

[EV-R800] A Fault Memory Diagnostic Instance contains 0..n Condition Groups.

  • [EV-R800-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Condition Group

[EV-R805] These Condition Groups have no persistent sort order.

A Condition Group is referenced...

  • by an Event as Enable Condition, see [EV-R200],
  • by an Event as Storage Condition, see [EV-R210];
  • not by a Condition Group - there is no hierarchy.
  • See [EV-R215] for more on possible references from Events.

[EV-R810] A Condition Group has Name, Qualifier, Description.

  • Name and Qualifier must be unique for Conditions and Condition Groups together, see [EV-R720-Qualified] above.

[EV-R830] A Condition Group references 1..n Conditions [EV-R700].

  • Cardinality: Condition Group 0..n -- 1..n Condition, i.e.
  • [EV-R830-nonEmpty] A Condition Group must contain at least one Condition. CANdelaStudio ensures this via the consistency check only, not in the dialogs (avoid user interface complexity; it is an edge case, anyway).
  • [EV-D830] Semantics:
    • a Condition Group is fulfilled iff.
    • all its Conditions are fulfilled (conjunction).
  • [EV-R830-multiple] Multiple Condition Groups may reference the same Condition.
  • [EV-R830-unique] One Condition Group may reference a given Condition only once.
  • A Condition Group cannot reference a Condition Group (there is no hierarchy).

In DEXT, ...

  • an Event references...
    • 0 or 1 Enable Condition Groups, and
    • 0 or 1 Storage Condition Groups,
    • not multiple ones [constr_1361],
    • not an individual Condition [TPS_DEXT_03015];
  • the Condition Group is either...
    • a DiagnosticEnableConditionGroup or
    • a DiagnosticStorageConditionGroup,
    • such a group is a shorthand for referencing each individual Condition of the Condition Group.

In the CANdela data model, a Condition Group...

  • is a separate entity which references multiple Conditions
  • helps the diagnostic author to...
    • conveniently assign multiple Conditions to an Event at once
    • easily understand which conditions are assigned to an Event
  • can be used for Enable Conditions as well as for Storage Conditions.

Related to Condition Group:

  • DEXT Export: [DEXT-R3200]
  • German: "Bedingungsgruppe"

Debounce Algorithm

[EV-R1100] A Fault Memory Diagnostic Instance contains 0..n Debounce Algorithms.

  • [EV-R1100-Card] Cardinality: Diagnostic Instance 1..1 -- 0..n Debounce Algorithm

[EV-R1105] These Debounce Algorithms have no persistent sort order.

[EV-R1110] A Debounce Algorithm is either Counter-Based [EV-R1200] or Time-Based [EV-R1300] (described below).

A Debounce Algorithm is referenced by an Event, see [EV-R220].

[EV-R1120] A Debounce Algorithm has Name, Qualifier, Description.

  • [EV-R1110-Qualified] Name and Qualifier must be unique in the list [EV-R1100].
  • Note about algorithms in DEM:
    • an algorithm is internal to DEM, not available to the application
    • therefore in DEM, an algorithm is not a referenced, re-used object,
    • ... but the algorithm properties are located at the Event directly
    • In DEXT, algorithms are refenced.
    • So algorithm Name and Qualifier are helpful for authoring and DEXT, not used in DEM.

[EV-R1130] Behavior (if Event disabled): this property...

  • specifies handling of the internal counter while...
    • a referenced Enable Condition is not fulfilled,
    • or ControlDTCSetting of the Event is disabled.
    • After all Enable Conditions are fulfilled, and ControlDTCSetting is enabled, Event qualification will continue with the next valid Event report.
  • [EV-R1130-Types] AUTOSAR defines the following behavior types:
    • undefined: the behavior has not yet been defined
    • Freeze: the counter value is frozen (i.e. the counter will continue with that value);
    • Reset: the counter value is reset to the initial value (i.e. the counter will be restarted)
  • The Behavior property is mandatory.
  • Default: undefined
  • Related:
    • German: "Verhalten"

Counter-Based Debounce Algorithm

Counter-Based Debounce Algorithm Properties (with sample values)

[EV-R1200] A Counter-Based Debounce Algorithm...

  • has the general properties of a Debounce Algorithm [EV-R1100] (above),
  • has an internal signed integer counter value (16 bit in AUTOSAR as of 4.4),
    • Note: UDS service 0x19 0x14 reports this value as one byte (scaled from the internal range).
  • has an (upper) failed threshold...
  • and a (lower) passed threshold.
  • When the value goes up and reaches the failed threshold, the Event gets classified as failed.
  • When the value goes down and reaches the passed threshold, the Event gets classified as passed
  • The difference between failed and passed threshould defines the debouncing effect.
  • When the Event has state failed,
    • if Jump Up Allowed is activated,
    • and the Event had state "passed" previously
      • (the counting direction changes from decrementing to incrementing),
    • the counter "jumps" to the Jump Up Value (typically 0),
    • otherwise it gets incremented by the increment step size,
  • When the Event has state passed, ...
    • if Jump Down Allowed is activated,
    • and the Event had state "failed" previously
      • (the counting direction changes from incrementing to decrementing),
    • the counter "jumps" to the Jump Down Value (typically 0),
    • otherwise it gets decremented by the decrement step size,

In detail, a Counter-Based Debounce Algorithm has the following properties (in addition to those for a Debounce Algorithm in general, see above):

[EV-R1210] Increment Step Size

  • Value used to increment the internal debounce counter.
  • Unsigned integer > 0; not checked by CANdelaStudio.
  • Mandatory
  • Default: 1
  • Related:
    • DEXT: counterIncrementStepSize

[EV-R1220] Decrement Step Size

  • Value used to decrement the internal debounce counter.
  • Unsigned integer > 0; not checked by CANdelaStudio.
  • Mandatory
  • Default: 1
  • Related:
    • DEXT: counterDecrementStepSize

[EV-R1230] Failed Threshold

  • Upper threshold for the internal debounce counter that indicates the Event "failed" status.
  • Unsigned integer > 0; not checked by CANdelaStudio.
    • typically < 32K, but limit may vary across AUTOSAR versions, not checked by CANdelaStudio.
  • Mandatory
  • Default: +127
  • Related:
    • DEXT: counterFailedThreshold

[EV-R1240] Passed Threshold

  • Lower threshold for the internal debounce counter that indicates the Event "passed" status.
  • Signed integer, always < 0; not checked by CANdelaStudio.
  • Mandatory
  • Default: -128
  • Related:
    • DEXT: counterPassedThreshold

[EV-R1250] FDC Storage Threshold When the Fault Detection Counter (FDC) reaches this threshold, memory will be allocated, and the Freeze Frame (Snapshot Data, Environment Data) will be stored.

  • Unsigned integer
  • Specific values:
    • Value 0: DEM stores the Freeze Frame at once when the Event occurs
      • ... but the Event gets visible only when Failed Threshold has been reached.
    • Value same as Failed Threshold: DEM stores the Freeze Frame later, when the testFailed bit gets set.
      • The Freeze Frame data may have changed since the Event occurred.
  • optional
  • Default: undefined
  • Related:
    • DEXT: counterBasedFdcThresholdStorageValue

[EV-R1260] Jump Up Allowed

  • Boolean
    • true: the internal debounce counter may be set to the Jump Up Value, when the counting direction changes towards "failed"
    • false: the internal debounce counter may be incremented only by the regular Increment Step Size.
  • Mandatory
  • Default: true
  • Related:
    • DEXT: counterJumpUp

[EV-R1265] Jump Up Value

  • Value for the internal debounce counter if a "jump up" is triggered
  • To be used only if "Jump Up Allowed" is true
  • Mandatory (cf. CDS-71597)
  • Signed integer
  • Default: 1
  • [EV-D1265]Note: if "Jump Up Allowed" [EV-R1260] is false, this property should be undefined.
    • The v12 data model does not allow "undefined".
    • A consuming client must first check the "Jump Up Allowed" property, anyway.
  • CANdelaStudio does not check the numeric value.
  • Related:
    • DEXT: counterJumpUpValue

[EV-R1270] Jump Down Allowed

  • Boolean
    • true: the internal debounce counter may be set to the Jump Down Value, when the counting direction changes towards "passed"
    • false: the internal debounce counter may be decremented only by the regular Decrement Step Size.
  • Mandatory
  • Default: false
  • Related:
    • DEXT: counterJumpDown

[EV-R1275] Jump Down Value

  • Value for the internal debounce counter if a "jump down" is triggered
  • To be used only if "Jump Down Allowed" is true
  • Optional
  • Signed integer
  • Default: undefined
  • [EV-D1275] Note: if "Jump Down Allowed" [EV-R1270] is false, this property should be undefined.
    • The data model does not enforce this;
    • a consuming client must first check the "Jump Up Allowed" property, anyway.
  • CANdelaStudio does not check the numeric value.
  • Related:
    • DEXT: counterJumpDownValue

[EV-R1280] Counter Stored Nonvolatile

  • Boolean
    • undefined
    • false: debounce counter value stored volatile (non-persistent)
    • true: debounce counter value stored nonvolatile (persistent)
  • optional
  • Default: undefined
  • Related:
    • DEXT: debounceCounterStorage is a property at the DiagnosticDebounceAlgorithmProps base class, with the constraint [constr_1359] "the attribute... shall only exist if ... CounterBased". Therefore, the CANdela data model defines this property directly at the Counter-Based Debounce Algorithm.

Event and DTC

[EV-R230] An Event optionally references a UDS DTC.

  • [EV-R230-OBDII] An Event cannot reference an OBDII DTC.
    • Instead, an OBDII DTC optionally references UDS DTCs (in the Vector UDS Template: [VUDS-R480])
    • See [EV-R020-OBDII] for the Events list.
    • See [EVUI-R005-OBDII] for the user interface.
  • [EV-R230-Kind] This holds for Events of Kind [EV-R110] SWC as well as BSW.
  • [EV-R230-Internal] The reference is optional.
    • If the Event does not reference a DTC, the Event is called internal (used for DEM configuration only).
  • [EV-R230-Combination] A DTC may be referenced by multiple Events.
    • This is called Event combination.
    • The DTC is a Combined DTC.
    • For restrictions on references to SWCs, see [ASR-D050-Combination].
    • Purpose: adapt different monitor results to one fault evaluable in a service station.
  • [EV-R230-None] A DTC may be referenced by no Event.
  • Default: reference not set
  • Cardinality: Events 0..n -- 0..1 DTC
  • Cf. Operations [EVOP-R230] (add reference) and [EVOP-R240] (remove reference).

[EV-R240] The Event and the referenced DTC must both exist within the same diagnostic instance.

Deviations to AUTOSAR Terms

[EV-D200] The CANdela data model intentionally uses some other terms than the DEXT specification:

  • it removes redundancy
    • e.g. omits the class name used as prefix (e.g. counter in counterJumpUp, counterJumpDown etc.)
  • it strives for consistent and clear wording
    • e.g. counterJumpUp becomes Jump Up Allowed
    • e.g. Boolean prestorageFreezeFrame becomes "Freeze Frame Prestored"
    • e.g. counterJumpUp and counterJumpUpValue become Jump Up Allowed and Jump Up Value
  • it declares properties as mandatory, except where the process demands omitting the property in CANdela to define it later.
  • it moves a property to a subclass where AUTOSAR defines a textual constraint for this purpose: [constr_1359]

Legend: Cardinality

The "Cardinality" info above describes the cardinality of the relationship between two types of objects in terms of the Unified Modelling Language (UML).

Example: "Events 0..n -- 0..1 Operation Cycle" means:

  • a given Event optionally ("0..1") references an Operation Cycle
  • a given Operation Cycle may be referenced by no Event ("0"), or by multiple Events ("n")
