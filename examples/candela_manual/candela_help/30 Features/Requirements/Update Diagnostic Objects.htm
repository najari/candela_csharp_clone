Update Diagnostic Objects

[RQOP-R500] CANdelaStudio shall provide an operation to update diagnostic objects from requirements.

Since 8.0 SP2, the two operations “Generate” and “Update” have been combined into one.

This operation is also available in a combined operation [MENU-R270] via the ribbon tab Data Exchange.

[RQOP-R510] creation, modification or deletion of Diagnostic Objects shall not be possible in a locked variant in Standard View [VAR-R010].

Basic Conditions

  • [RQOP-R500-UpdateDiagObj]: the "Update diagnostic objects from requirements" operation in the requirements area shall apply to diagnostic objects in the selected library or variant [RQ-R093].

[RQ-R528.1]: in standard mode, create/modify diagnostic objects only if authorization and length restrictions of existing diagnostic objects permits.

Example: respect authorization of diagnostic instance for creation of data objects and DTCs, modification of diagnostic instance name/description.

R530.0: process only the current language of the CANdela document (as for manual editing by the user).

R531.1: provide execution for 1..n selected (“locally”) or for all requirements.

If executed locally: recursively process all requirements contained in the selected ones (even contained requirements that are not selected); generate and update diagnostic objects within the diagnostic object selected in the diagnostic object tree, or inform user if this is not possible (e.g. for data requirement and diagnostic class selected).

[RQ-R552]: in shared diagnostic instances, CANdelaStudio generates objects...

  • without confirmation
  • but possibly replaces the reference by a copy, see the next chapter [RQ-R520].

R554.0: the order of created diagnostic objects shall reflect the order of the requirements as far as possible.

[RQ-R534-a] CANdelaStudio shall...

  • for each new diagnostic object,
  • store the requirement ID in the property of [RQ-R100].

Handling of Referenced Diagnostic Instances (CDS-41683 v11)

[RQ-R520] The following applies to any object...

  • that must be modified
  • that is referenced in multiple variants or the DTC Pool
  • that may be modified (due to authorization).

[RQ-R520-Copy] If property "Update of Diagnostic Objects" is "Replace References with Copy" [RQ-R096-Copy], the "Update Diagnostic Objects" operation...

  • replaces the object with a copy in the selected variant (as of D001), i.e.
    • for referenced DIDs and diagnostic instances: replaces it with a copy;
    • for a DTC referencing into DTC pool:
      • replaces it with a copy,
      • additionally ensures the diagnostic instance is a copy.
  • then modifies the copy;

  • writes an info message with a hyperlink into the current variant, like

      Replacing DTC 0x123456 with a copy in variant "<variant name>".

  • skips (does not update) objects that are required as reference, with a message like

      Skipping DTC 0x123456 required as reference from DTC Pool.
  Skipping diagnostic instance "Temperature" required as reference.

[RQ-R520-UpdateRefs] If property "Update of Diagnostic Objects" is "Update References" [RQ-R096-UpdateRefs], the "Update Diagnostic Objects" operation...

  • keeps the referencing of diagnostic instances,
  • so updates may take effect in multiple variants.

Heading

[RQ-R530-Heading]: generate nothing for headings.

DiagInst Requirement

Overview of Updating from Diagnostic Instance Requirement

Algorithm: DiagInst Requirement for a Diagnostic Instance

Precondition: the requirement does not have the special DiagClass value of [RQ-R030-DID].

[RQ-R530-DiagInst] Update diagnostic objects from the requirement as follows:

  • If the requirement is linked with a DID
    • [RQ-R530-DID] inconsistent, skip it with a warning
  • If the requirement is not linked
    • [RQ-R536] Provide the diagnostic class:
      • determine the diagnostic class template
      • create a diagnostic class for the diagnostic class template
    • [RQ-R570] Check if a matching diagnostic instance exists
    • If no:
      • Check if the diagnostic class is "DID Enabled" [DCL-D001]
      • If yes:
        • [RQ-R575] Check if a matching DID exists
        • If yes:
          • do not update the properties of the DID (but only those of the diagnostic instance, below)
        • If no:
          • [RQ-R550] create a DID from the requirement
          • [RQ-R560] Set the DID properties
        • [RQ-R555] Create a diagnostic instance for the new or matching DID
      • If no:
        • [RQ-R558] Create a diagnostic instance (without DID)
    • Link the existing or new diagnostic instance with the requirement
  • [RQ-R560] Set the properties of the (originally or just now) linked diagnostic instance

Note: according with this algorithm, two Diagnostic Instance Requirements that have the same name will produce just one DID, due to [RQ-R575]. If this is not desired, the requirements must have different names.

Algorithm: DiagInst Requirement for a DID

Precondition: the requirement has the special DiagClass value of [RQ-R030-DID].

[RQ-R540] Update diagnostic objects from the requirement as follows:

  • If the requirement is linked with a diagnostic instance
    • [RQ-R540-DiagInst] skip it with a warning
  • If the requirement is not linked
    • [RQ-R575] Check if a matching DID exists
    • If no:
      • [RQ-R550] create a DID from the requirement
    • Link the existing or new DID with the requirement
  • [RQ-R560] Set the properties of the (originally or just now) linked DID

Warning: Link Conflict with DID

[RQ-R530-DID] For...

  • a DiagInst Requirement that does not have the special DiagClass value of [RQ-R030-DID],
  • if it is linked with a DID,
  • the diagnostic data (DID) is not consistent with the requirement,
  • CANdelaStudio shall report a warning and skip the requirement.

Note: CANdelaStudio does not try to make the data consistent (which would mean to probably delete the DID and create a diagnostic instance instead).

Warning: Link Conflict with Diagnostic Instance

[RQ-R540-DiagInst] For...

  • a DiagInst Requirement that does have the special DiagClass value of [RQ-R030-DID],
  • if it is linked with a diagnostic instance,
  • the diagnostic data (i.e. diagnostic instance) is not consistent with the requirement,
  • CANdelaStudio shall report a warning and skip the requirement.

Note: CANdelaStudio does not try to make the data consistent (which would mean to probably delete the diagnostic instance and create a DID instead).

Create a DID from a Requirement

[RQ-R550] CANdelaStudio shall...

  • create a DID [DID-R200] from the diagnostic instance requirement,
  • and,
    • if the "Identifier" property is non-empty,
    • and it does not violate a constraint (e.g. 3 byte value, or duplicate with existing identifier),
    • then [RQ-R550-UseIdentifier] use it for the DID Identifier,
    • otherwise use an available identifier, as when the user creates a new DID [DID-R200].

[RQ-R550-Format] The identifier number may be...

  • hexadecimal with leading "0x", like "0x0107", or
  • decimal like "263.

See also [RQ-R560-UpdateDIDIdentifier] for updating an existing DID.

Create a Diagnostic Instance for a DID

[RQ-R555] CANdelaStudio shall (CDS-39520 U040 8.5 SP2)...

  • create a diagnostic instance from the DID of [RQ-R550],
  • as specified in Diagnostic Instance Creation from DID [DI-R020].

Create a Diagnostic Instance without DID

[RQ-R558] CANdelaStudio shall...

  • create a new diagnostic instance [DI-R010] from the diagnostic instance requirement.

Identifier:

  • if the "Identifier" property [RQ-R030-Identifier] is non-empty,
  • then CANdelaStudio uses it for the diagnostic instance Identifier (or any other specification [PS-R400-Specification]) (CDS-39520 U030 8.5 SP2).
  • else if the diagnostic class type [DCLT-R200] is "routine",
    • [RQ-R558-Routine] then CANdelaStudio creates a routine identifier unique in the variant (CDC-43914 9.1 SP1);
    • for non-"routine", it creates an identifier unique in the diagnostic class.
    • Independent of the diagnostic class type, CANdelaStudio uses an identifier in a valid range of the text table configured for the diagnostic class [DCLT-R400].

Check if A Matching Diagnostic Instance Exists

[RQ-R570] A Diagnostic Instance matches a DiagInst Requirement, if...

  • the name of the diagnostic instance requirement equals the qualifier or name of a diagnostic instance
  • in this order
  • in the diagnostic class determined,
  • or on top-level for singletons.
  • Note: this condition intentionally does not consider whether the diagnostic instance is a "DID Definition" [DI-D110].

Check if A Matching DID Exists

[RQ-R575] A DID matches a DiagInst Requirement, if...

  • the name of the diagnostic instance requirement equals the qualifier or name of a DID
  • or [RQ-R575-MatchIdentifier] (CDS-39287 8.5 SP2) the "Identifier" property [RQ-R030-Identifier] is non-empty and matches the DID Identifier (CDS-39520 U020 8.5 SP2)
  • in this order.
    • Motivation: the DID name must be unique, but the DID identifier may be duplicate, depending on [DID-R008].

Note: in case duplicate DID identifiers are allowed in the document [DID-R008], there may be multiple matching DIDs. The algorithms above will use the first one (in the order the DIDs are stored in the document).

Provide the Diagnostic Class

[RQ-R536 Provide Diagnostic Class]

  1. determine the diagnostic class template
  2. create a diagnostic class for the diagnostic class template

Note: see [RQ-R546-DiagClass] for DiagClass at DTC Requirement.

[RQ-R536-L Determine Diagnostic Class] Determine the diagnostic class for a DiagInst Requirement as follows:

[RQ-R536-L1 Attribute "SourceRequirementHeadings"] Use-case: an external application puts requirements into headings with fixed names - specify at the CANdela diagnostic class template for which heading it applies:

  • If the requirement is contained in a Heading H,
  • and any diagnostic class template D that supports requirements [DCLT-R300] contains a string (not multi-language) attribute, qualifier "SourceRequirementHeadings”,
  • and the attribute contains the name of H (in a comma-separated list),
  • then CANdelaStudio shall create diagnostic objects in the first diagnostic class that refers to such a diagnostic class template D (CDS-28568 8.0 SP2).

[RQ-R536-L2] If the requirement is contained in a Heading which...

  • is linked to a diagnostic class, or
  • the name of the Heading equals the qualifier or name (in this order) of a diagnostic class template,
  • then use that diagnostic class.

[RQ-R536-L3] If the requirement property “DiagClass” denotes...

  • the qualifier or name of an existing diagnostic class, or
  • of an existing diagnostic class template (in that order),
  • then use that one.
  • Assumption: the special value of [RQ-R030-DID] does not represent any existing diagnostic class.

[RQ-R536-L4] Otherwise, ...

  • if the parent of the DiagInstRequirement is a Heading,
  • and the name of the heading denotes...
    • the qualifier or name of an existing diagnostic class,
    • or the qualifier or name of an existing diagnostic class template
    • in that order,
    then use that one.

[RQ-R536-L5] otherwise, determine the diagnostic class type from the requirements type as follows (if such a diagnostic class exists, use the first existing one, otherwise create one and use it):

Requirement type Diagnostic class type
Data DiagInst Requirement Stored Data (if the “Services” property [RQ-R030-Services] of the requirement refers to a service that has data in request)
Current Data (otherwise)
Note: no Identification, no Variant Coding (cf. CDS-29089)
FaultMemory DiagInst Requirement FaultMemory
Routine DiagInst Requirement Routine
IOControl DiagInst Requirement Control

Note: in CANdelaStudio, the diagnostic class qualifier and type are shown in the property dialog of a diagnostic class.

Data Requirement

Creation

R542.2: if for a data requirement no data object exists, and it is not contained in a diagnostic instance requirement, skip it. Inform the user about this.

[RQ-R544-Data.3 Create Data Requirement]: if for a data requirement no data object exists, and it is contained in a diagnostic instance requirement D, then

[RQ-R544-a] if D is linked with a DID, then create a data object in the DID that is linked with D (CDC-39298 8.5),

[RQ-R544-b] otherwise, create a data object in the diagnostic instance that is linked with D.

[RQ-R544-DataType] To determine the data type, use...

  • the default data type [RQ-R094], and the...
  • BitLen and...
  • DisplayFormat Data Requirement properties

as follows:

Data Requirement Use data type
no BitLen Default
BitLen, no DisplayFormat Use first data type with matching BitLen, prefer identity data type with quantity atom
BitLen and DisplayFormat Use first data type with matching BitLen and DisplayFormat (as previous constellation), otherwise use default

Note: specify the default data type in the Property Page "Settings".

Using Services

[RQ-R544-ServicesAtData] If the “Services” property of the requirement [RQ-R030-ServicesAtData]...

  • specifies an existing service, and
  • optionally even indicates a primitive in that service that has a telegram table for semantics "data" [CPC-R100],
  • then put the data object into that telegram table;
  • otherwise, put it into the first telegram table with semantics "data"
    • "first" = the order shown in CANdelaStudio.

Note: typically, the data read service contains only one telegram table (for a combined proxy component) in the positive response, in this case the “Services” string “Read” is sufficient in generating diagnostic objects, there is no need to specify “Read PR”.

Note: if the “Services” property denotes e.g. “Start” request, and that primitive does not contain a telegram table, then do not create a data object (even if the positive response contains a telegram table).

Note: mind the restrictions of [RQ-R528]!

Note: “first one” does not refer to the order of combined components in the DiagClassTemplate!

Setting isToDo

[RQ-R545 Set isToDo]: if a data object is created for a data requirement, then set “isTodo” of the data requirement [RQ-R160] to true.

Motivation: allow to find the data objects in order to select a different data type.

Moving Data Objects

R532.1 (new in 8.0 SP2): during update, after creating all links, ...

  • if a requirement P is linked to a diagnostic object DO,
  • and the parent of P is linked to a diagnostic object X that is not the parent of DO,
  • then move DO to be contained in X (at the end of the child list).

DTC Requirement

[RQ-R546.3 Creation of DTCs]

[RQ-R546-DTCPool] If ECU authorization allows creation of DTCs in pool only, create DTCs in the pool, link to them from the diagnostic instance as described in the following (note: the requirements GUI does not show info whether DTC is linked to pool or exists locally).

[RQ-R546-InDI] If for a DTC requirement no DTC exists, and it is contained in a FaultMemory DiagInst Requirement F, then create a DTC in the diagnostic instance that is mapped to F.

[RQ-R546-DiagClass] If the DTC requirement property “DiagClass” [RQ-R030-DiagClassDTC] denotes...

  • the qualifier or name (in that order) of an existing diagnostic class template with type Fault Memory,
  • then put the DTC in the existing diagnostic instance of the diagnostic class template, or create it.

[RQ-R546-InFM] Otherwise, if the DTC is not contained in a FaultMemory DiagInst Requirement, then create a DTC in Fault Memory.

[RQ-R546-InFMMultiple] If the document contains multiple fault memories, use the one with biggest DTC size (e.g. 3 bytes, not 2 bytes; 4 bytes, not 3 bytes).

Note: do this even if the DTC requirement is not contained in a FaultMemory DiagInst Requirement.

[RQ-R546-Code] If a DTC requirement has a code, it shall be stored in the code of the new DTC.

[RQ-R546-NewCode] Otherwise, a new DTC code shall be used (like e.g. in “Paste Contents”).

[RQ-R546-Empty] If a field in a DTC requirement is empty, the update fills the according field in the created DTC as if the DTC had been created by clicking on the magic line: it assigns the default value of the DTC Column (CDC-43842 9.1), with special handling for an empty default value. See [DTCC-R080].

[RQ-R546-Duplicate] If the Requirements list contains a duplicate DTC code, the "Update diagnostic objects" ignores the second one with a log message (like in 8.5).

Updating Diagnostic Object Properties

General Rules

[RQ-R560 Update Diagnostic Object Properties]: CANdelaStudio shall...

  • [RQ-R560-New] for a new diagnostic object:
    • initially set properties from the requirement properties,
  • [RQ-R560-Update] for a compatible [RQ-R105] already linked diagnostic object,
    • update properties from the requirement properties.

Note: do not update properties if diagnostic object and requirement are not compatible, e.g. do not modify the name of diagnostic objects associated with a heading or a text requirement.

[RQ-R560-SkipEmpty]: CANdelaStudio shall skip requirement properties that are empty.

Motivation: treat these properties as “unspecified”, not as “intentionally empty”.

Basic Properties

Note: for updating, the requirements ID is not relevant (since it is the basis for determining the linked diagnostic object).

[RQ-R560-Name] store the requirement name in the name and use it for the qualifier as in manual editing.

  • [RQ-R560-NameDTC] for a DTC Requirement, store the requirement name in the error text.

[RQ-R560-Description] store the requirement description in the description.

  • [RQ-R560-DescriptionDTC] for a DTC Requirement, store the requirement description in the DTC description, see [RQ-R020].

Attributes

[RQ-R560-Attribute] For a non-empty user-defined property for all requirement types [RQ-R040-ForType], store the property in an attribute ...

  • if the attribute is associated as described in [RQ-R100-Prop]
  • and the requirement property can be converted by a value conversion (see [CONV-R010]) to a value,
    • handling an int requirement as "unsigned",
    • then override the attribute with that value,
  • else do not change the attribute (if it is already overridden, do not reset to default!)
  • and write a warning to the log.
  • for DTC requirements see [RQ-R560-DTCUserDefined].

DID Properties

[RQ-R560-UpdateDIDIdentifier] If...

  • the requirement "Identifier" property [RQ-R030-Identifier] is non-empty,
  • and the operation [DID-R212] allows the update,
  • then CANdelaStudio shall update the DID Identifier from the "Identifier" property using that operation,
  • otherwise skip the property.

For the number format, see [RQ-R550-Format].

Diagnostic Instance Properties

[RQ-R560-UpdateDiagInstIdentifier] If...

  • the requirement "Identifier" property [RQ-R030-Identifier] is non-empty,
  • and constraints are not violated,
  • then CANdelaStudio shall update the diagnostic instance Identifier from the "Identifier" property.

[RQ-R560-Services] CANdelaStudio...

  • creates services in the diagnostic instance as specified by the “services” property [RQ-R030], ...
    • matching each part of the “services” property with the qualifier of the used ProtocolService in a CANdela diagnostic class.
    • For a new diagnostic instance, if no “services” are specified, it uses the default from the diagnostic class template (as in GUI).
  • [RQ-R560-DelService] deletes a service (CDS-72013 v13) if ...
    • the document is for manufacturer [DOC-R110] John Deere,
    • the "Services" requirements property is non-empty, and
    • the property value does not contain the service, and
    • the service is not mandatory [DCLT-R310]
    • and (in general) the diagnostic instance is modifiable.

upon Update from Requirements

  • Do not delete any service.

[RQ-R560-VehicleSystemGroups] CANdelaStudio shall...

  • if VehicleSystemGroups is an empty string, do nothing.
  • use the VehicleSystemGroups property to associate the created diagnostic instance with Vehicle System Groups (based on matching name).
    • if necessary, create a Vehicle System Group.
    • The Vehicle System Groups may have existed in the CANdela document before generating, or may have been created during generating.
  • If a Vehicle System Group is associated with the diagnostic instance but not contained in the Vehicle System Groups requirement property, then drop the association.
  • Do not delete any Vehicly System Group.
  • Fulfill e.g. length consistency conditions like when the user interactively creates a new diagnostic instance (e.g. add dummy data object, but only if there would be no data objects created from requirements.

DTC Properties

[RQ-R560-DTCCode] Do not update the DTC code.

Motivation: after the user changed these, they should not be automatically updated from requirements, the user should modify them intentionally. They will be shown as differing.

[RQ-R560-DTCUserDefined] Store non-empty user-defined properties of [RQ-R040]...

  • ... in the additional column of a CANdela DTC,
  • if the additional DTC column of CANdela is associated as described in [RQ-R100-DTCProp].

[RQ-R560-DTCVehicleSystemGroups] CANdelaStudio shall handle the Vehicle System Group Association at a DTC like for a diagnostic instance [RQ-R560-VehicleSystemGroups].

Data Object Properties

[RQ-R560-DataObject] CANdelaStudio shall not update the data type associated with data object (only use them for new data objects [RQ-R544-DataType]).

Motivation: after the user changed these, they should not be automatically updated from requirements, the user should modify them intentionally. They will be shown as differing.

Vehicle System Group

[RQ-R560-VSGSemantics]: if...

  • the Semantics property is non-empty,
  • then CANdelaStudio shell assign it to the Vehicle System Group semantics.
