Data Objects

Data Object base term for data transported over the line
Telegram sequence of data objects in a request or response
Telegram table GUI list control for a telegram

You create data objects in the telegram table by clicking the line "Please click here to create...", or using the context menu (right mouse).

Types of Parameters

[DO-R010] CANdela supports different types of parameters (also called parameters, signals, or simply "data objects" in a general sense):

  • Data Object [DO-R100] (in the exact sense)
  • Reserved Data Object [DO-R200]
  • Bit Field
  • DTC data object, related with a special dtc or obdDtc ProtocolService Proxy Component)
  • Group of DTC
  • DID Data Reference [DID-R160]
  • DID Reference [DID-R180]

Data Object

[DO-R100] A Data object describes a named piece of data transported over the line.

  • [DO-R100-DataType] A data object references a data type.
  • The data type specifies the
    • length,
    • structure,
    • encoding and
    • conversion between the “raw” value as transported on the line and the “physical” representation for the user (e.g. with a unit).
  • A typical data object has a data type whose length is divisible by 8 (i.e. bit lengths of 8, 16, 24, 32... bits).
  • [DO-R100-BitSized] A bit-sized data object (size not divisible by 8) must be wrapped in a bit field, see Bit Fields.
  • [DO-R100-BitPos] A data object not starting at a byte boundary must also be wrapped in a bit field (even if its length is divisible by 8).

Reserved Data Object (Gap)

[DO-R200 Reserved] A reserved data object (also called a gap) acts as a place holder for unnamed data objects that...

  • have yet to be defined,
  • or do not hold useful data, such as message padding.

A reserved data object

  • has a bit length
    • maximum size 65536 bytes (64KB) (CDS-9284 6.0)
  • does not reference a data type
  • may have a duplicate name within a telegram (typically (reserved))
  • must have a unique qualifier within a telegram (as usual)
  • does not have a defined constant value on the line
    • a reasonable assumption is to assume the value is zero,
    • but this is not a requirement (we've seen other values).
    • If you want to force a value zero on the line, use a data object with a const value instead!

See [DEXT-R210] for use of reserved data objects in the DEXT export.

Use in CANdesc

For reserved data objects

  • ... on byte-level, CANdesc does not set a constant value
  • dito in a bitfield where data objects do not have a constant value

Use in Vector Test Systems

For a reserved data object, Vector test systems...

  • in a request: initialize the value to 0 (zero)
  • in a positive response: assign the value from the line
  • usually just hide the object (or may show it as "reserved")
  • may provide programming access to the value as for regular data objects (with Identity data type)

Dynamic length (CDS-23099 7.5)

S010.1: It shall be possible to define a data object with deterministic variable length before the end of a telegram table (this includes defining multiple such data objects, and any kind of datatype, even complex ones).

This shall be possible in diagnostic instance, in a packet datatype, in the input and output parameters of jobs, in “fixed data” in a ProtocolService, in a case of a multiplexer and in iteration datatypes. Note: in import pool, there should be no such restrictions, anyway.

Note: as a consequence, the data objects following the first variable length data object no longer have a fixed byte position.

S110.0: in template and document, provide authorization on ECU level “allow variable length data objects before the end of the telegram”.

S120.0: in template and document, provide authorization on “Combined components” (within diagnostic class template) level “allow variable length data objects before the end of the telegram”.

S125.0: if user creates a new “combined component”, take the default for the setting of S120 from the value of the setting of S110.

S130.0: in consistency check of any telegram (e.g. within a diagnostic instance, Mux, complex datatype, fixed data component in a protocol service), report a telegram as “non-fatal, prevent exports” if it contains a data object with variable length (deterministic or non-deterministic) before the end of the telegram if

a) the property of S110 is false

S140.0: in consistency check of a telegram within a diagnostic instance or in a complex datatype referenced from a diagnostic instance, report a telegram as “non-fatal, prevent exports” if

a) the property of S110 is true (motivation: if it is false, the telegram is reported due to S130), and

b) the property of S120 of the referenced “Combined component” is false, and

c) the telegram contains a data object with variable length (deterministic or non-deterministic) before the end of the telegram.

S150.0: in consistency check of telegram length,

a) for minimum length requirement, check against maximum length of datatype;

b) for maximum length requirement, check against minimum length of datatype.

E.g. ProtocolService requires at most 10 bytes, datatype can have 5-20 bytes (string). This is ok – at runtime, the datatype may violate the condition (= if it is longer than 10 bytes), but the authoring system should not complain about this (cf. undesired warnings with functional CAN addressing length).

S280.0: for a bitfield itself or for its contents, a variable length datatype is not allowed.

Description

The description of a data object contains plain text only (not rich text with images etc. - e.g. tables in the specification report would be too big and confusing).

As an alternative, you may insert images in the description of the diagnostic instance or the job container.

Semantics

[DO-R150] The semantics of a data object specifies whether...

  • the data object has a fixed meaning
  • which is known to the test system.

The list of supported values is predefined in CANdelaStudio:

Semantics Meaning
(none) no specific semantics
Tester ID Info that identifies the tester against the ECU
Year Year current at runtime
Month Month current at runtime
Day Day current at runtime
Hour Hour current at runtime
Minutes Minutes current at runtime
Seconds Seconds current at runtime
User ID Info that identifies the user against the ECU
Version of Specification Version of the ISO / OEM / CANdela document

Constant Value

[DO-R300] The constant value specifies that the data object is transported over the line with a given fixed value. Depending on the toolchain, it may also describe the value in the ECU implementation.

The constant value belongs to the data object, not the datatype.

It is always specified as raw value by the user. In the property dialog of the data object, the resulting physically value is also shown.

Default Value

[DO-R350] The default value belongs to the data object, not the datatype.

It is always specified as raw value by the user. In the property dialog of the data object, the resulting physically value is also shown.

The default value is used as an optional default for a test system user interface.

Note: for the service "Reset to default" for IO Control in a code generation context, the default values are defined by the application.

Default Value in DCM

[DO-D360] In order to initialize the data in the ECU implementation, the AUTOSAR DCM uses...

  • a default value from a link to the software component
  • or (if no such link exists) the default value provided at the data object (see [DO-R350] above).

Default Value for Fixed Count Iteration in Tester (CDS-33749 8.2 SP2)

[DO-D365] The Vector diagnostic toolchain provides specific functionality for...

  • a data object that...
    • refers a Fixed Count Iteration Data Type [FCDT-R100]
    • and has a special attribute ImplementationDefault
      • Qualifier: "ImplementationDefault"
      • Type: String
      • Category: "SDG"
  • [DO-R365-ODX] ODX Export exports the attribute as a Special Data Group (SDG) (CDS-37658 after 8.5 Release).
  • [DO-D365-DTL] Vector Testers use the attribute as default value for the Fixed Count Iteration parameter (DTL-47557 2018).

Operations

[DOOP-R110] Move to New DID (CDS-36881 8.2 SP2)

Conditions (menu item not shown otherwise):

  • [DOOP-R110-Data] only in a "data telegram table", i.e. that references a combined component with semantics "data" [CPC-R100].
  • [DOOP-R110-NonSingleton] only in a non-singleton [DCLT-R150] diagnostic instance (note: no menu item in non-data telegram tables, or in a singleton diagnostic instance)
  • [DOOP-R110-DIDRef] only if the selection does not contain DID Reference [DID-R180] or DID Data Reference [DID-R160] (non-obvious)
  • [DOOP-R110-Bitfield] for bit-field only if bitfield and entire contents is selected
    • Note: this is consistent with "Copy To New Packet Data Type".
    • for more details: handle like in "Copy To New Packet Data Type"

Operation:

  • [DOOP-R110-DID] DID creation
    • take DID number (identifier) from diagnostic instance identifier.
    • take DID qualifier/name from qualifier/name of diagnostic instance.
    • if a DID with the qualifier or name already exists, prompt to copy with new qualifier / name or cancel.
    • does not preserve the name in the other languages
    • the new DID contains the selected data from the telegram table
      • preserves all properties: qualifier/name, attributes...
      • no need to preserve OID and template OID (even "move" within a telegram table does not preserve them)
  • [DOOP-R110-DIDDataRef] DID Data Reference creation
    • in the telegram table, CANdelaStudio replaces the selected data by a DID Data Reference [DID-R160] to the new DID,
    • the DID Data Reference has the same qualifier/name as the new DID in the current language, made unique if necessary.

Note: the functionality is intentionally not available in other telegram tables (Snapshot Data, Extended Data Records, Packet...).

For the user interface, see the data objects list [DOUI-R110].

See the related operation [DIOP-R070] for diagnostic instances.
