Telegram Table (List of Data Objects)

Typically a request or positive response contains a list of Data Objects. CANdelaStudio shows this list in a Telegram Table.

Note: this documentation uses the user interface term "Telegram Table" also for the list in the data model.

CANdelaStudio Telegram Table Showing Various Kinds of Data Objects

Positions

Data objects have no explicit byte and bit positions. The byte and bit position always results from the relative position within the list that contains them, based on the length of each data object (defined at the data type, or at a reserved data object directly).

Positions are relative within the telegram table and therefore always start with zero.

Only byte-sized data objects starting at byte positions can be positioned directly in the list. Other data must be put into a bit-field.

Usage

A telegram table may be contained...

  • in a Fixed Data Component in the template
  • directly in a diagnostic instance
  • in a multiplexer in a diagnostic instance
  • as input or output job parameter list
  • in Extended Data (v13)

If used within a diagnostic instance,

  • a telegram table must reference a combined proxy component that references Proxy Components in the Protocol Service;
  • a multiplexer must reference a combined proxy compoennt that references Mux Component in the Protocol Service.

See the Protocol Service Overview.

Namespace in telegram table

In a telegram table, top-level elements are in a namespace (with uniqueness of qualifiers and names).

Elements within a bitfield are in a namespace of their own. I.e. the following is ok:

DataObject “Object1”
Bitfield “Object2”
  DataObject “Object1” // == top-level object, == object within other bitfield!
  DataObject “Object2” // == top-level object (the parent bitfield itself)!
Bitfield “Object3”
  DataObject “Object1”
  DataObject “Object2”

Multiplexer

A multiplexer in a diagnostic instance contains

  • a list of telegram tables ("cases"), each one is selected by a selector number or range
  • a mandatory default telegram table which applies to selector values for which no case exists.

DID Semantics

Semantics “DID Data Reference”

[TT-R240.0 consistency condition]:

  • the telegram table of a Combined Component with semantics “DID Data Reference” [DID-R050-DIDDataReference]
  • shall contain exactly one DID Data Reference [DID-R160].
  • On violation, emit a warning, prevent from export.

[TT-R241.1]:

  • in the telegram table of a Combined Component with semantics “DID Data Reference” [DID-R050-DIDDataReference],
  • a constraints check shall report a warning (prevent from exports)
  • if the Identifier length of the diagnostic instance is > 1 Byte
  • and the Identifier is not equal to the DID number
  • (cf. similar check for DID Reference in [DID-R182]).

[TT-R242.0]: as a default, name and qualifier of the diagnostic instance shall be taken from the DID.

[TT-R244.0]: as a default, the “identifier” shall be taken from the DID number in an UDS Diagnostic Instance / shall be the low byte of the UDS DID Number in an OBDII Diagnostic Instance.

Note: no consistency condition for name, qualifier of a DID Definition Diagnostic Instance.

Semantics “DID Data References“

[TT-R310.1 consistency condition]:

  • a telegram for a Combined Component with semantics “DID Data References” [DID-R050-DIDDataReferences]
  • shall contain only DID Data References [DID-R180] or reserved data objects.
  • On violation, emit a warning, prevent from exports.

Semantics “DID References“

[TT-R315.0 consistency condition]:

  • a telegram for a Combined Component with semantics “DID References” [DID-R050-DIDReferences]
  • shall contain only DID References [DID-R180].
  • On violation, emit an error, prevent from exports.
