Dynamically Define Data Identifier

The UDS service 0x2C "allows the client to dynamically define in a server a data identifier that can be read via the ReadDataByIdentifier service at a later time" (UDS 2013 chapter 10.6.1). The service provides grouping of multiple data elements to read them in one mass operation.

The dynamically defined DIDs share the same identifier (number) space with statically defined DIDs.

The data elements in a dynamically defined DID can be specified in one or multiple requests to the server...

  • by reference to another DID (0x2C 0x01),
    • even to another dynamically defined DID (not recommended by UDS)
  • by memory address (0x2C 0x02)
  • multiple of these, even mixed

The server concatenates the data elements of subsequent requests for the same identifier. It keeps the definition until either

  • it receives 0x2C 0x03 (Clear), or
  • manufacturer specific: some event occurs, like a session transition.

References to another DID denote...

  • a complete DID, or
  • even individual data objects from within the DID (UDS: "composite block")

... by giving the position (starting with 1) and the length within that DID.

A dynamically defined DID can be used in the services

  • ReadDataByIdentifier (0x22): identifier range 0xF300 .. 0xF3FF
  • ReadDataByPeriodicDataIdentifier (0x2A); identifier range 0xF200 .. 0xF2FF (this holds whether the DID is defined statically or dynamically).

Use Cases

  • an ECU has been implemented including (static) DIDs e.g. one DID for wheel speed front left, one DID for front right etc. Manufacturing creates one combined dynamic DID to read all four wheel speed values, by referencing the objects in the existing static DIDs.
    • you may do this in a test system (if it supports creation of dynamically defined DIDs);
    • you may also want to do this comfortably in CANdelaStudio (if the ECU software is fixed, but the CDD can still be modified)
  • a tester user wants to optimize the bus traffic and combines multiple static DIDs into one.
  • (not recommended) reference the same DID multiple times in a dynamically defined DID, in order to get a higher sampling rate than by periodical reading.

Use in CANdela

The template must contain a Protocol Service to support the service 0x2C.

The CANdela data model...

  • supports references to entire DIDs using a DID Data Reference (excluding the identifier) or a DID Reference (including the identifier).
  • has no special mechanism to reference individual data objects being part of a DID, but you can manually enter the details for service 0x2C.

Define Dynamic DIDs in the Document

CANdelaStudio allows definition of DIDs at authoring time in the CANdela document.

  • to define DIDs in the document, setup a proxy component with semantics "Data" in the Protocol Service;
  • the references to the existing DIDs must then be specified manually in a telegram table in a diagnostic instance.

Define Dynamic DIDs in the Test System

Depending on the process, it may not make sense to define dynamic DIDs already in the static CANdela document.

  • to define DIDs only at runtime in the test system, setup a proxy component with semantics "Any" in the Protocol Service;
  • the document then contains no further details for this component, these must be specified in the test system at runtime.

Note: the Vector UDS Template v1.5 (as of CANdelaStudio 8.5) contains ProtocolServices for 0x2C that allow to define Dynamic DIDs in the test system.
