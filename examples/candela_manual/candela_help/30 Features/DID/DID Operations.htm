Note: for the term "obvious", see Commands/Menus.

DID

[DID-R200.1 New]: in a variant V, create a DID (not referenced).

Make the identifier unique, except if all identifiers are used in the variant, and “allow duplicate DIDs” is true (fulfill [DID-R030])

[DID-R200-BasedOn]: CANdelaStudio creates the new DID based on a "reference" DID R (CDS-68394 9.1),

  • as described in the Basic User Interface Rules [UI-R340]
    • object: DID
    • number: the DID identifier.
  • CANdelaStudio takes for Diagnostic Class...
    • none, if there is no Reference DID,
    • the Diagnostic Class of the Reference DID R,
      • if R has a single Diagnostic Class,
      • and no conflict arises,
    • otherwise none.

CANdelaStudio ensures name and qualifier are unique (fulfilling [DID-R030]).

[DID-R200-NoData] CANdelaStudio does not create a data object in the new DID (CDS-41535 9.1).

Do not allow this…

  • if the variant is locked.
  • if all identifiers are used in the variant, and “allow duplicate DIDs” is false

Note: it is not possible that a DID in the base variant with required “yes” or “in all variants” has the same qualifier as the new DID – for such a DID, a DID with the same qualifier must already exist in the variant V, and the new DID must get a different qualifier.

Note: a DID in the base variant may have the same qualifier, but modifiable [DID-R010] = false. The new DID will get the default modifiable = true, anyway, see [DID-D210].

See also Procedure "How to Create a DID".

[DID-R202.1 New in All Variants]: create a DID...

  • [DID-R202-AllVariants] referenced [DID-D005] in all variants
  • [DID-R202-Libraries] not referenced in any library (CDS-42589)

Make name and qualifier unique in all variants (fulfill [DID-R030]).

If there is a DID identifier value not used in any variant, set the identifier of the new DID to that value (fulfill [DID-R030]).

Otherwise, if “allow duplicate DIDs” is true, assign an identifier already used.

Do not allow this…

  • if there is a variant that is locked;
  • if there is no DID identifier value not used in any variant (= each possible identifier value is used in at least one variant), and “allow duplicate DIDs” is false.

[DID-R220 Delete]: in a variant, delete a DID:

  • delete the DID in the current variant (= break the sharing);
  • delete any reference to the DID
    • e.g. DID Data Reference in some service like 0x37,
    • uses of the DID on ECU level [DID-D001], e.g. the reference from a global Common Snapshot Data;
  • additionally delete a diagnostic instance in the current variant (CDS-40000 9.1) (i.e. break the sharing) if
    • the DID Semantics [DID-R050-DIDDataReference] is set,
    • or the diagnostic instance is in a "DID Enabled" [DCL-D001] diagnostic class and D is the single data object in a telegram [DCL-D001-b2]
    • e.g. not in an arbitrary diagnostic class with some service like 0x37 (i.e. not "DID enabled"), in that case, delete only the DID Data Reference.
    • Note: the former requirement [DID-R220-e] is now obsolete, it prohibited DID deletion due to Rule [DID-D020].
  • [DID-R220-Rq] in Expert View (CDS-70802 v12)...
    • if the DID is required in all variants “yes” or “as reference” [DID-R012],
    • the operation resets the property to "no".

Do not allow this…

  • [DID-R220-a] if the variant is locked.
  • [DID-R220-b] in Standard View if the DID is required in all variants “as reference” or “yes” [DID-R012]. Note: for Expert View, see [DID-R220-Rq] above.
  • [DID-R220-c] in Standard view if the DID is used by read-only Common Snapshot Data [DID-D001].
  • [DID-R220-d] in all views if the DID is used by fixed data (cf. [DID-D001] e+f). Note: even in Expert View, the data need "use by fixed data" must be fulfilled.
  • [DID-R220-f] if the DID is used in the variant by a DID Reference [DID-D001-c] in a diagnostic instance that does not allow to modify primary properties.
  • [DID-R220-g] if the DID is used in the variant by a DID Data Reference [DID-D001-d] in a diagnostic instance that does not allow to modify primary properties or is required [DIA-R020] (CDS-40000 9.1; before 9.1, DID deletion was not possible in this constellation).

[DID-R262.0 Paste Variant]: when pasting a variant from another document [VAR-R705], take over all DIDs from the other variant:

  • [DID-R262-RqAsRefName] If...

  • [DID-R262-Identifier] If...
    • the source document contains multiple DIDs with the same identifier,
    • but duplicate identifiers are not allowed [DID-R008] in the target,
    • ... then paste fails.

Migration 8.5

Background

In an 8.0 document, DIDs are packet data types.

In an 8.2 document, DIDs are on document level, qualifiers are unique, identifiers are not unique (motivation was: support multiple protocols).

Assumption:

  • most DIDs are equal in all variants,
  • only few DIDs differ between variants.

Migration Use-Cases

Use case 1: data originally created in 8.2, load in 8.5 – must handle non-unique identifiers.

Use case 2: data originally created in 8.5, saved to 8.2 – must handle local changes in a variant.

Use case 3: data loaded in 8.5 (use case 1), save to 8.2 again.

Use case 4: data saved to 8.2 (use case 2), load in 8.5 again.

Constellations in 8.2

  • “global DIDs”: all 8.2 DIDs have unique identifiers.
  • “local DIDs”: multiple 8.2 DIDs have the same identifiers, and they are used in different variants (not in a global object).
  • “conflicting DIDs”: multiple 8.2 DIDs have the same identifiers,
    • both are used in global objects, or
    • one is used in a global object, the other one in a variant, or
    • both are used in the same variant.

Note: there may be additional DIDs not used in an 8.2 variant.
