Jobs (CDS-590 1.4)

Introduction

Idea of Jobs

  • Scripting diagnostic operations executed by a diagnostic tester
  • Typically, there will be...
    • one job for reading and
    • one for writing/control,
    • potentially one for flashing.
  • The typical size of a job file is few KB.

Idea of Embedding Files

  • embed files of any format in a CANdela document
    • maybe "executables" (proprietary and standardized)
    • especially "job" scripts
  • transport them with the file:
    • originally with the CANdela file,
    • also in an exported ODX or Diogenes file
  • extract a job to provide it to a specific runtime environment.

Main Use

The idea of embedding job files has mainly been used...

  • with manufacturer specific testers and job files (.fm files, Diogenes Export)
  • with Java jobs in ODX files for an ASAM MCD 3D conforming tester
    • the use of standard Java is appealing but also has drawbacks (how to protect a script that contains sensitive information?)

Vector Tools

  • ... support rich scripting features,
  • but in general do not seamlessly extract embedded script files from the diagnostic description.
    • This means you can transport a script in a CDD file as a Job,
    • but a Vector tester will not in general provide the script in its user interface.
    • As a tester user, you can always use CANdelaStudio to manually export the script from the CDD file, and integrate it in the tester.

For details, see Jobs in Test Systems.

Services vs. Jobs

A test system allows the execution of...

  • a service
    • to access functionality of the ECU
    • e.g. UDS service 0x27 "Security Access".
  • a job used like a service:
    • for functionality of the tester or the tester library
    • e.g. a complex key algorithm.
    • Jobs are not executed by the ECU.
  • a job used for value conversion.

Jobs in CANdela

Overview of Job-related Objects in CANdela

  • Job container [JCNR-R110]:

    • a list of jobs
    • it is handled like a diagnostic instance
      • you can reference a job container in multiple variants
      • it has has attributes, activation, audience (same range as for diagnostic instances) and authorization.

  • Job [JOB-R200]:

    • defined in a job container within a diagnostic class
    • includes
      • input and output parameters (data objects) and
      • one or multiple functions (multiple functions: for different runtime systems)
    • has some properties in common with a service.

  • Function [JOB-R300]:

    • references a job file
    • optionally specifies an entry point in the job file

  • Job file [JOB-R400]:

    • file (program, macro, sequence) to be executed by a tester (runtime system)
    • embedded in the CANdela document
    • written in a specific programming language (e.g. Java, CANapeScript, CAPL...), and therefore...
    • specific to a runtime system (ODX 3-D Server, Vector CANape, Vector CANoe...)
    • CANdela stores job files on the document level, which allows reuse of a job file (reducing the overall size of the document).

  • Procedure Data Type [DTPROC-R010]:

    • a CANdela data type
    • includes
      • one input parameter,
      • one result value and
      • a function
    • a tester may use the function and its job file embedded in the CANdela document to convert a raw value to a physical value, or vice versa.

Containers for Jobs

  • [JOB-R100] A Job can be contained in a Diagnostic Class with diagnostic instances and services,
    • i.e. in a Diagnostic Class...
    • based on a Diagnostic Class Template...
    • that contains at least one Used ProtocolService [DCLT-R305].
    • [JOB-R110] In such a diagnostic instance,
      • each Job must have the same name and qualifier as a Used ProtocolService.
      • I.e. there will be Jobs like "Read", "Write" etc.
      • The Job Container must contain at most one Job for a given Used ProtocolService.
  • [JCNR-R110] A Job can be contained in a top-level Job container...
    • that cannot contain diagnostic instances and services, see [DCLT-R210].

Job

[JOB-R200] A job has one or multiple functions (see below).

In the GUI, the check box “Supports several runtime systems” allows toggling between single function mode and multiple functions mode:

  • Single function mode provides a combo box where users can select a job file for exactly one function. This is the 80% use case.
  • Multiple functions mode provides a table where users can create several Functions, each with another job file and runtime system.

[JOB-R210] A job has input parameters and output parameters.

  • These are data objects or gaps (but no bit fields).
  • There is no restriction for the datatypes of such a data object (bits are allowed, byte order is not significant).

The handling of bit data objects as parameters depends on the test system for which the job is destined:

  • one test system may support passing individual bit data objects without padding
  • another test system may require padding bit data objects (i.e. user must add a 7-bit gap behind a 1-bit data object)
  • another test system may implicitly pad bit data objects (which we assume e.g. for Java – a test system may dynamically build a parameter list containing individual bits, the memory layout of those parameters is hidden by the virtual machine. Assumedly.)

A job has attributes [ATTR-R050].

The authorization flags of the Job Container take effect on the Job.

A job can have state transitions [STTR-R020].

A job can be de-activated (CDS-17293 7.0).

Function

[JOB-R300] A function references a job file.

[JOB-R320] A function has an entry point. For compatibility, it is required for syntax “fm”, optional otherwise.

Job File (CDS-6307 5.5)

CANdelaStudio cannot create a job file from scratch. A job file comes from an existing external file always, which CANdelaStudio just provides for use by the respective application.

[JOB-R400] A job file has a version string.

  • [JOB-R400-Check] CANdelaStudio does not check the format of the version string.
  • [JOB-R400-Required] For compatibility, the version string is required for syntax “fm”, optional otherwise.

[JOB-R410] A job file has a free-text runtime system (also called syntax).

CANdelaStudio provides predefined runtime systems:

Runtime system Description
AutomationSequenceMacro [JOB-R410-AutomationSequenceMacro], see Jobs in Test Systems (CDS-69204 9.1)
CANapeScript for Vector CANape
CAPL for the Vector CANoe Communication Access Programming Language
class compiled Java
dll Windows library
fm [JOB-R410-fm] OEM specific
jar Java archive
java source Java
OTX Open Test sequence eXchange
VectorDiagnosticScript also called "VDS", for use in Vector diagnostic test systems

[JOB-R420] A job file optionally has “additional files” (CDS-2251 3.0).

[JOB-R430] Job files are stored on the document level and must be unique.

[JOB-R440] Equality of job files is defined by comparison of the properties “Version”, “Syntax” and a binary comparison of the file contents: two job files x and y are equal, iff.

     x.version == y.version
 AND x.syntax  == y.syntax
 AND (
       (file_size > 0  AND binary_equal(x.file_content, y.file_content))
     OR
       (file_size == 0 AND x.file_name == y.file_name)
     )

(for file size 0, see the next chapter)

External References (Late Binding)

[JOB-R450] For a job file with size 0, ODX Export references a dummy file.

Semantics: the dummy file is to be replaced later (after the ODX export) by a real file ("late binding").

For this reason, the job file comparison [JOB-R440] (above) checks the name for job files of size 0.

Procedure Data Type

A Procedure Data Type (Procedural Conversion) is like a job: it has several functions attached.

Selection List for Entry Points (CDS-8276 7.0 SP1)

[JOB-R460] For a .jar file, CANdelaStudio lists the class names in the "Entry points" list in the Job property dialog.

These are the real entry points listed in the JAR manifest, behind the parameter Job-Entry-Points (CDS-22803 8.0 SP2).

Special handling for entry point longer than 72 bytes (CDS-36869 8.2 SP3):

  • If...
    • the class name including the package name extends a line length of 72 bytes,
    • the name contains a line break.
  • This is a restriction of the MANIFEST.MF file;
  • see the JAR File Specification at http://docs.oracle.com/javase/6/docs/technotes/guides/jar/jar.html#Notes%20on%20Manifest%20and%20Signature%20Files (as of 2017-02):

No line may be longer than 72 bytes (not characters), in its UTF8-encoded form. If a value would make the initial line longer than this, it should be continued on extra lines (each starting with a single SPACE).

Reading Version (CDS-8276 7.0 SP1)

[JOB-R470] For an .fm file, CANdelaStudio reads the version and enters it as a default in the Job File Manager dialog.
