State Dependency (CDS-543)

State Dependency Diagram

For the user interface, see the "States" Tree Chapter.

Use-cases

  • Sessions: some extended services may only be executed in a certain diagnostic session.
  • Security Access: some writing services may only be executed when the ECU is unlocked (security access).
  • Authorization: user-role based access to services, requires authentication (new ca. 2017) (Authorization).

State Groups

State Groups and States

CANdelaStudio handles these use-cases in a generalized way:

  • both sessions and security access are described by a state group;
  • each state group contains states, like...
    • for Sessions: Default, Programming, Extended...
    • for Security Access: Locked, Unlocked
  • you can define additional state groups
  • you can define additional states within a state group
  • typically, the state groups and states are predefined in the template.

For details, see State Group and State.

Introduction to State Transitions

For details, see State Transitions.

Blocking Service Execution

State groups and states allow to block the execution of services ([STTR-R020-no]):

Execution of Services Depending on Session (in Tree Node States/Dependencies)

In the example, ...

  • the "(no)" shows that service FaultMemory/ReportSupportedDTCs 19 0A cannot be executed (is blocked) in the "Programming" session
    • you will get a negative response code
  • it can be executed in the other sessions
  • service Diagnostic Identification/Read 22 F1 10 can be executed in all sessions.

This shows which services are available in the boot loader of the ECU: all services that have "(yes)" in the programming session.

Execution of Services Depending on Security Access

In this example, ...

  • service FaultMemory/ReportSupportedDTCs 19 0A can be executed when the ECU is "Locked" or "Unlocked #L2 (Extended)"
  • it cannot be executed when the ECU is "Unlocked #L3 (Programming)".
  • service Diagnostic Identification/Read 22 F1 10 can be executed always, independent of the Security Access state.

Changing State

There must be some services that change the session (i.e. cause a "state transition", [STTR-R020-transition]):

Change of Session State

  • in Default mode, service Programming/Start 10 02 enters Programming mode
  • in Programming mode, service EcuReset 11 01 goes back to Default mode

Most other services do not change the session:

  • in Default mode, service Programming/Default 10 01 can be executed but stays in Default mode

Some other services cannot be executed (as described above):

  • in Default mode, service EcuReset 11 01 cannot be executed.

Change of Security Access State

In this example, ...

  • service Key Level #1/Send 27 02 "unlocks" the ECU (changes state from "Locked" to "Unlocked L1")

... as opposed to...

  • service EnableRxAndEnableTx/Control 28 which does not change the state.

Interaction between Session and Security State Groups

All state groups (session, security access, ...) apply in parallel:

  • for a service to be blocked, it is enough that it cannot be executed (is blocked) in one state group
  • in principle, a service may cause a state change in multiple state groups
    • e.g. both in session and security access;
  • but note: UDS provides different services for different state groups:
    • service 0x10 for Session,
    • service 0x27 for Security Access.

State Transitions Based on Automata Theory

The concept of states and state transitions in CANdela is based on the concept of a deterministic finite state automaton (DFA):

  • the ECU is considered to have a state;
  • a service can be blocked (= have no state transition)
  • ... or change the state (= cause a state transition);

See the next chapter for some automata theory background.

In CANdela, states are partitioned into state groups, typically “Session” and “Security”:

  • States are typically defined in the template in an ordered collection, e.g. "DS_None", "DS_Default", "DS_EndOfLine".
  • The input alphabet consists of services (to be precise: the successful execution of a service), e.g. "Default session/Start", " End-of-line session/Start".
  • initial state: the first state of a state group, e.g. "DS_None".
  • final states: the initial state. At least one transition to this final state is required, it must be triggered by the same service in all automata (this is a simple part of the consistency condition "the compound automaton must not contain dead ends".)
  • state transitions are defined at the service, e.g. for " Default session/Start", there may be two transitions ("DS_None", "DS_Default") and ("DS_EndOfLine", "DS_Default").
  • "transition loop" = "self-transition"

Only executive self transitions are modeled as transitions (CDS-2721). An ECU application may perform operations ("actions") when the ECU enters a state (even the same state). Therefore it makes a difference whether a service...

  • may be executed but has no transition, or...
  • may be executed and has a transition (= a "reentering self transition").

This means only self transitions which are having a real state entering action are modeled as a transition.

The “transition function” of automata theory actually covers two aspects of diagnostics:

  • precondition/blocking: whether execution of a certain service is allowed in some state (the ECU must check this for each service execution), and
  • transition: the result state (typically only few services actually cause a transition to another state)

The compound automaton is the combination of all automata, operating in parallel on the same input alphabet (successful service executions). Successful execution of a service means a transition in the compound automaton. The transition is possible if in each automaton (i.e. for each state group), there is an edge for the service given (either to the same or to another state). If in any automaton there is no edge for the service given, then execution of the service is blocked.

Background: Automata Theory

Each state group represents a deterministic finite state automaton (DFA).

In automata theory, a DFA is defined by (Q, S, d, q0, F) where

  • Q is a set of states
  • S is an input alphabet
  • q0 IN Q is the initial state
  • F <= Q is a set of final states, and
  • d: Q x S -> Q is the transition function.

The transition function may be written...

  • as a relation like "(q, s, r) IN d", or
  • as a function like "d(q, s) = r":
    • for a source state q and an input symbol s, the function defines the target state r.
    • There is no or exactly one transition (target state) for a given source state and input symbol.
    • In other words: in a DFA, for any q and s, there is at most one (q, s, r) in the transition function.

In a state q, the input symbol s is allowed...

  • if there is a transition for s.
  • The target state r may be the same state q, or a different state.

Use of State Transitions in Different Tools

The information from the CANdela state transitions is used as follows:

AUTOSAR Diagnostic Extract

The AUTOSAR Diagnostic Extract uses...

  • for Session and Security only:
    • for a service in a given state: whether it can be executed (yes/no)
    • it does not use the information about the target state
  • it ignores all other state groups

CANdesc

CANdesc 6 (as of 2016) uses...

  • for Session, Security and other state groups:
    • for a service in a given state: whether it can be executed (yes/no/is there a self-transition)
    • for a service: the target state (a service must lead to the same target state for all states; the code generator checks this)
    • Example: service 0x19 0x01 ("Default Session/Start") must lead to the same state "Default" if executed in the states "Default", "Programming" or "Extended".

Relevance of a Service in a State Group

Most services in most states...

  • do not cause a transition and
  • are not blocked.

For such states, CANdelaStudio calls the service irrelevant.

In other words, a service is relevant in a state group if in at least one of the states,

  • the service causes a transition, or
  • is not allowed.

If a service is irrelevant for all states of a state group, the CANdelaStudio service property dialog shows the state transitions read-only.
