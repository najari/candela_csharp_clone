State Transitions

State Dependency Diagram

CANdelaStudio describes the executability of services using the concept of a deterministic finite state automaton (DFA), see the State Dependency feature description.

A State Transition is a relationship between a state and a service or job:

  • [STTR-R020] the state transition describes whether in a given source state, the service or job...
    • [STTR-R020-no] is blocked = cannot be executed, shown as (no) in CANdelaStudio; or
    • [STTR-R020-yes] can be executed, shown as (yes); or
    • [STTR-R020-transition] can be executed and (re-) initializes the state (see below), shown as name of the target state.

See the introduction in the State Dependency chapter.

Note: State Transitions apply within one State Group only:

  • "Lock" or "Unlock" for State Group "Security Access"...
  • has no effect for the State Group "Session".

Re-Initialize State

According with UDS 2013 (chapter 9.2.1 for Diagnostic Session Control 0x10), re-initialize covers...

  • stopping events
  • relocking security
    • reset of diagnostic functionality depending on unlocked security (like active IO Control)

Yes vs. Same State

For the transition, you can...

  • specify "(yes)" , but you can also
  • select the same state (i.e. the source state) as target state for the transition:

For source state "Programming", same state "Programming" selected

For both cases, ...

  • the service can be executed
  • afterwards, the state is the same state as before

but the difference is:

Use in Code Generation

CANdesc: Same Target State

[STTR-R025] In CANdesc, a service or job...

  • is either blocked [STTR-R020-no],
  • or has a transition [STTR-R020-transition] to the same target state for all source states.

AUTOSAR: Unlocking Service not Blocked

Service Blocked in State "Unlocked L1" - not in DEXT

[STTR-R028] In DEXT and AUTOSAR DCM, ...

  • a RequestSeed or SendKey service must not be blocked in any unlocked state.
    • e.g. if the service SendKey has a transition in state "Locked" of state group "Security Access",
    • then it must not have "(no)" in any other state.
    • This is required by UDS: for RequestSeed in an already unlocked security level, the ECU shall send a positive response, with the seed set to zero. RequestSeed and SendKey behave identically with respect to blocking.

Usage in Tools:

  • In CANdela, the restriction does not hold
    • the generic data model of state transitions allows the constellation.
  • In DEXT, the restriction holds:
    • export adapts data [DEXT-R410].
  • In Vector MICROSAR DCM, the restriction does not hold:
    • a service with a transition in state "Locked" can be blocked in another state.

Write-Protection

Use Case

  • the manufacturer has set the Default Session 0x10 0x01 write protected
  • the supplier has created an own state "Production Mode"

In this situation, CANdelaStudio shall allow the supplier to specify the state transition from supplier state "Production Mode" to "Default" state.

Conditions for Modification of State Transitions

Diagram for Conditions for Write-Protection of State Transitions

[STTR-R030] The transition for a service from a given state is read-only in Standard View (CDS-38199 8.5) if

  • the diagnostic instance which contains the service has "primary properties modifiable" = false [DIA-R040], and
  • the state has "mayBeModified" = false [ST-R050].

Therefore, ...

  • in a diagnostic instance that has "primary properties modifiable" = true, all state transitions are modifiable.
  • to protect a transition against changes in Standard View, the diagnostic instance must have "primary properties modifiable" = false, and the state must have "mayBeModified" = false.

Note: in CANdelaStudio 8.0 - 8.2, the transition was read-only if the Diagnostic Instance had "Primary properties modifiable" = false (CDS-19301 8.0). Therefore a supplier could not modify the state transition for their supplier state.

In order to prevent the supplier from modifying state transitions for states already created by the manufacturer (e.g. "Default State"), the manufacturer needs to set these states write-protected.

Consistency Conditions

[STTR-R200] the consistency check shall report an error (hinder exports) (CDS-8150 6.0) ...

  • [STTR-R200-Act] in an activated diagnostic instance (CDC-41895 8.5 SP3)
  • for each service S
  • and state group SG with semantics not "Authorization" [STG-R050-Authorization] (CDC-43864 9.1 SP1)
  • where for all states of SG,
  • S "may be executed" == no
  • i.e. the service is blocked in all states of SG

[STTR-R200-Auth] (CDC-43864 9.1 SP1) the consistency shall report a status message only (not hinder exports)...

  • in the same constellation,
  • except the state group having semantics "Authorization".

See also the above consistency condition in CANdesc [STTR-R025] (not checked by CANdelaStudio).

Note: up to CDS-10402 6.0, such a data constellation was reset on loading.

Note: jobs are not checked (RDPDU-42771).
