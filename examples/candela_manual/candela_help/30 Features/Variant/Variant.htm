Variant

Introduction

[VAR-R001] A CANdela document can contain multiple variants. A CANdela template contains a base variant only.

Each variant describes either

  • a feature variation (optional, model series), or
  • development progress over time.

The first variant ("Base Variant", "Common Diagnostics") may be used to store a common subset or a superset of diagnostic functionality for all variants. See the Base Variant feature.

You always create a new variant based on an existing variant, with the possibility to reference (share) data which shall be common to both variants.

A variant can contain “Identifying Features”. When a tester communicates with an instance of an ECU, the Identifying Features allow the tester to automatically detect with which variant of the ECU it communicates.

A variant can be locked for editing. The lock can be broken in expert view only.

Variants in the CANdelaStudio Tree

CANdelaStudio shows...

  • the Base Variant in a separate top-level tree chapter
  • all other variants ("extended variants") in a tree chapter called "Variants" (not shown in a document template).

Data Model

A variant contains diagnostic classes.

Some diagnostic classes may occur only once per variant (e.g. "Fault Memory"), diagnostic instances of these classes are contained directly in the variant.

Some classes may have several instances, their diagnostic instances are grouped in folders (called "diagnostic classes" in user interface). Examples: "Normal/Default Session", "Stand By Session", "Serial Number", ...).

  • Identifying Feature
  • Identifying Pattern
  • Optionally: revision history.

Bootloader

How to describe the bootloader services and maybe specific service execution restrictions?

Motivation:

  • when there is an external reprogramming request on power on or reset of an ECU, it enters a programming session;

  • when the application is not valid on power on or reset of an ECU, it enters a default session in the bootloader, from which it also may enter an extended and programming session;

  • services may transport different data (e.g. extended fingerprint) in bootloader

Separate “Boot Variant”

Add a separate variant in the CANdela document, let it contain only the services available in the bootloader, and adapt the service execution description.

This solution helps to describe specific data in bootloader services.

The solution does not help for code generation (actually, the bootloader is not generated, it is constant - almost).

The solution does not help for a CANdela based Vector tester. Actually, vFlash contains an internal CDD based description of the bootloader behavior. So there is no need to explicitly describe it in the CDD for an ECU project.

The solution may help for a generic tester e.g. based on ODX exported from the CDD. But this effort makes sense only if the services actually behave different.

Separate Session States

As special behaviour of the bootloader may show up in the service execution in Default and Extended Session, a more light-weight description may add two special “states” (like “Bootloader default session”, “Bootloader extended session”) to the regular application service description.

Textual Description

If there is no tool that uses the formal data description, it may suffice to describe the bootloader behavior in a description field. You can even add diagrams there.
