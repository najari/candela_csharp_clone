Suppress Positive Response Message Indication Bit (SPRMIB)

In UDS (ISO 14229-1), about half of the ProtocolServices has a bit (MSB) in the "subfunction" message parameter, indicating that an ECU should not send a response for the given request.

  • If the bit is set (e.g. 0x81), the ECU shall suppress a positive response message.
  • If the bit is not set (e.g. 0x01), the ECU shall send a positive response message.
  • Negative response messages shall be sent independently of the bit (cf. CDS-2585).

In CANdela, ...

  • whether a Protocol Service supports the SPRMIB is defined at the Protocol Service component that represents the subfunction (Constant or Variable Value Component; default false)
  • ... and is also shown read-only in the property dialog of the Protocol Service itself.
  • If a Protocol Service supports the SPRMIB, the bit 7 of the subfunction value specified in a diagnostic instance at authoring time does not matter, since it must be specified at runtime in the test system.
  • [PS-R710] In order to define the SPRMIB value at authoring time already, CANdela supports a Protocol Service property "Test system sets SPRMIB" (see below).
    • [PS-R710-All] The property applies to all services based on the Protocol Service (there is no choice).

Note about using the SPRMIB with specific services

  • According with UDS 2013, services with subfunction support the SPRMIB
  • therefore, e.g. the 0x19 0x04 and 0x19 0x06 services support the SPRMIB
    • UDS 2013 explicitly mentions the SPRMIB in the 0x19 context as follows:
    • "Explanations and usage of the possible levels are detailed below (suppressPosRspMsgIndicationBit (bit 7) not shown)"
    • "For all examples the client requests to have a response message by setting the suppressPosRspMsgIndicationBit (bit 7 of the sub-function parameter) to "FALSE" ('0'). "
    • this indicates that 0x19 supports SPRMIB.
  • therefore, Vector testers handle the SPRMIB for these 0x19 services
  • it admittedly does not make sense to send a 0x19 0x04 request with the SPRMIB set,
    • why would you send the request, anyway?
    • ... but it is conforming with UDS
    • and supported by Vector testers.

Recommendation: Use SPRMIB with the following UDS Services

[PS-D700]

  • 0x10 Diagnostic Session Control
  • 0x11 ECU Reset
  • 0x28 Communication Control
  • 0x31 Routine Control
  • 0x3E Tester Present
  • 0x85 Control DTC Setting

Constraints

[PS-R715] Constraints for SPRMIB Usage

  • [PS-715-One] At most one component may have the "supports SPRMIB" bit set.
  • [PS-715-NotFirst] The first component (typically ServiceID) must not have the bit set.
  • [PS-715-Last] It is not necessarily the last Constant or Variable Value Component that has the bit set.
  • [PS-715-Singleton] This applies to Protocol Services in singleton diagnostic classes [DCLT-R150-singleton], too.

Addressing Properties: Default Values for New Services

Protocol Service Property Page "Addressing" for Protocol Service with SPRMIB set

Feature ID Property Description
Physical request
[PS-R740] Test system sends physical request indicates whether the ECU supports physical addressing for the Protocol Service.
Default: true.
[PS-R750] The test system shall set the SPRMIB in the request... indicates whether the test system shall set or reset the SPRMIB in a physical request unconditionally, without user choice.
This property describes behavior of the test system, not of the ECU!
It is up to the individual test system to respect the property.
[PS-R750-Always] ... always The CANdela author decides that the test system shall always set the SPRMIB to 1, to suppress a physical positive response.
[PS-R750-UserDefined] ... user-defined The CANdela author leaves the decision whether to set the SPRMIB to the user of the test system.
This is the default.
[PS-R750-Never] ... never The CANdela author decides that the test system shall always set the SPRMIB to 0, to require a physical positive response.
[PS-R760] ECU sends a response... indicates whether the ECU sends a positive or negative response on a physical request.
If the Protocol Service has no positive and no negative response defined,
the property is false and cannot be changed at the Protocol Service or one of its services.
Otherwise, for UDS, the property is always true ("UDS ECU always supports physical addressing.", CDS-39671 v11).

[PS-R745] Test system sends functional request indicates whether the ECU supports functional addressing for the Protocol Service.
Default: false.
[PS-R755] The test system shall set the SPRMIB in the request... like [PS-R750] above, for the functional request.
[PS-R755-Always] ... always see at the physical request above.
[PS-R755-UserDefined] ... user-defined see at the physical request above.
This is the default.
[PS-R755-Never] ... never see at the physical request above.
[PS-R765] ECU sends a response... indicates whether the ECU sends a positive or negative response on a functional request.
Like the previous property [PS-R760], just for a functional request.

Use in Vector Toolchain

  • CANdesc for UDS 2006:
    • evaluates "ECU sends a response"
    • e.g. you can configure CANdesc to not support a request for a given service.
  • CANdesc for UDS 2012, and
  • DCM:
    • The ECU handles the request according with ISO 14229-1,
    • i.e. ignores the flag "ECU sends a response" for a functional request,
  • CANdesc in general:
    • On CAN, CANdesc assumes a functional request is not longer than 1 CAN frame; it has no special handling for the constellation.
    • Typical use for functional addressing: keep bus traffic low e.g. for flashing, using services 0x20 Communication Control and 0x85 Control DTC Setting.
  • CANoe.DiVa:
    • if the flag "Test system sends functional request" is on,
      • DiVa generates a test,
      • otherwise it does not send the service functioally.
