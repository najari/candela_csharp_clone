AUTOSAR Diagnostic Extract (DEXT Export)

See also the AUTOSAR Diagnostic Workflow.

Note: the application computing the AUTOSAR Diagnostic Extract [IBP-R050] is also called "Diagnostic Data Modifier".

Note: in order to transport AUTOSAR properties in the CANdela document, please create CANdela attributes for AUTOSAR in the dialog of menu File|Properties in page "Document Info".

The Standard

The AUTOSAR Diagnostic Extract (since AUTOSAR 4.2.1) configures the Basic Software Modules DCM and DEM. It may be used to transfer diagnostic demands between an OEM and tier-1 suppliers. For this purpose, ODX or ECU-C have been used in the past, but are not well suited:

  • ODX does not have the necessary details in the Fault Memory description;
  • ECU-C is very generic, therefore it cannot be integrated automatically into an existing configuration.

The Diagnostic Extract format takes a similar role for the configuration of diagnostics which the System Description takes for the configuration of communication.

You can download the standard documents from https://www.autosar.org.

Fundamental Rules

The export maps CANdela objects to the AUTOSAR Diagnostic Extract format.

  • CANdela supports various diagnostic protocols
    • The diagnostic protocol is represented mainly by the template.
    • The template also contains decisions specific for an OEM (process).
  • AUTOSAR is based on UDS.

Therefore the export tries to map...

  • the generic information from the CANdela template and document
  • to the specific AUTOSAR data structure.

If the CANdela document violates fundamental assumptions of the export, the export will stop.

Client/Server Ports for DIDs (CDS-71880 v13)

[DEXT-R2310] DEXT Export supports Client/Server Ports for DIDs.

Benefit of using Client/Server ports (functions) over Sender/Receiver ports (variables):

  • Save ECU memory
    • global memory for S/R port
    • gets allocated even for information that is not needed frequently
  • Save processor utilization
    • use-case: the software component collects Freeze Frame data for many DTCs frequently in a float variable
    • DCM accepts uint16
    • with an S/R port, the software component has to convert the value each time it collects the data.

Data Objects in a DID

  • AUTOSAR 3 represented a whole DID as one Diagnostic Parameter.
  • AUTOSAR 4 supports Diagnostic Parameters for individual CANdela data objects.
  • In R19 (cf. [DEXT-R050])...
    • in general each data object is represented by one Diagnostic Parameter of possibly multiple bytes.
    • some data constellations, e.g. a bitfield with LowHigh (Intel) byte order, are still represented by a single Diagnostic Parameter.
  • The CANdela data type is represented by a byte array (uint8) of the appropriate length.

Bitfields

[DEXT-R215] Export represents a bitfield...

Bitfield with 1 bit text table, 1 reserved

  • with 1 byte size
  • containing only any of
    • a data object with 1..7 bits size, referring a text table,
      • Note: more than 1 bit supported since DDM 15 (CDS-70664 v11 P1, Feat-4168)
    • a reserved object,
    • a bit not covered by an object (i.e. implicitly undefined)

as...

  • a DIAGNOSTIC-DATA-ELEMENT
  • that refers to a COMPU-METHOD with category BITFIELD-TEXTTABLE,
  • i.e. as individual bit data objects.

[DEXT-R218] Otherwise, export represents the bitfield as...

  • a DIAGNOSTIC-DATA-ELEMENT
  • that refers to a COMPU-METHOD with category IDENTICAL, uint8,
  • which represents the entire bitfield.

Events

[DEXT-R308] Data source for AUTOSAR Events in the CANdela document:

  • the Boolean flag "Supports Events" [EV-R010] decides whether DEXT Export uses DTCs or Events:
  • [DEXT-R308-DTC] if the flag is false, DEXT Export uses DTCs (UDS and OBDII, not J1939),
    • manufacturer dependent [DEXT-R060-Events]
    • DTC Columns and Default Attributes used for exported Event properties are defined in the CANdela template
    • Export applies heuristics to add missing information (e.g. operation cycle)
    • see next chapter
  • [DEXT-R308-Events] if the flag is true, DEXT Export uses Events (CDS-42224 v12) from the CANdela document.
    • Event properties as defined by AUTOSAR are hard-coded in the CANdela data model,
      • there are no Default Attributes to define for this purpose.
    • Export applies heuristics to add information which is set undefined in the CANdela Events (e.g. operation cycle)
  • Note: after loading a file with version < 12, the flag is false [EV-R250-Supp].

Using CANdela DTCs for AUTOSAR Events

The following applies when the Boolean flag "Supports Events" is false (see [DEXT-R308-DTC] above).

For a CANdela DTC, export creates...

  • a DTC
    • independent of the DTC format configured in the document, export uses the numeric UDS DTC value;
    • even if DTC format "SAE J2012" [DOC-R400-J2012] has been configured for the document, export does not concatenate the text from the FTB text table to the error text.
  • a DTC-Property
  • an Event
    • with qualifier derived from the DTC, e.g. DTC_0x001314_Event.

The DTC references

  • the DTC-Property,
  • the Event via an Event-to-DTC-Mapping.

A DTC can have one or multiple Memory-Destinations (based on the 0x19 ProtocolServices).

Specific name rule for DTCs (CDS-70015 v10, Feat-3364 DDM 13.0.3)

[DEXT-R045] Manufacturer specific: DEXT Export creates DTC names in DiagnosticTroubleCode derived meta classes (e.g. DiagnosticTroubleCodeUds) like

DTC_<3 byte hex DTC code><DTC error text><FMI text>

Blanks in <DTC error text> and <FMI text> get replaced by underscores.

Example:

  • DTC: 0x1234
  • Name “Some Description”
  • FMI 0x20 “Data Drifted High”
  • Resulting DTC name: DTC_0x123420_Some_Description_Data_Drifted_High

Extended Data Records

  • export creates Extended Data Records only if service 19 06 "Read Extended Record" is activated
  • export uses the number and the qualifier
  • an Extended Data Record must have at least one data object
  • for each data object, export considers the qualifier and the data type (converted to a byte array)
    • for 64-bit, see [DEXT-R203].
  • the data is stored at the AUTOSAR DTC Property

Freeze Frames

  • export creates Freeze Frames only if...
    • service 19 04 "Read Snapshot Record" is activated, and
    • at least one DTC contains a DID.
  • [DEXT-R335] Each DID must be specified either...
    • by a DID Reference [DID-R180] (created in the telegram table using the context menu)
    • or by two data objects in sequence:
      • 1 data object for the DID Identifier, with the Identifier specified in the column "Default";
      • 1 data object as DID Data.
      • In order to specify DID Data consisting of multiple data objects, either define them in a Packet Data Type, or use a DID Reference (see above).
      • If the data objects are not defined pair-wise, DEXT Export will skip them!
  • Export uses the number and generates the name using the pattern SnapshotRec_<number>
  • [DEXT-R330] Export includes time series snapshot parameters (9.1 SP1, Feat-2808).
    • Note: these are not part of the AUTOSAR standard 4.3.0.
    • Export transports them in SDGs which Vector daVinci Configurator processes on import.
  • [DEXT-R340] (CDS-70959 v11 P1, Feat-4959)
    • If a CANdela diagnostic instance in Primary Fault Memory
    • contains the service 0x19 0x04
    • and the attribute "Snapshot Record Numeration Type" [SR-R023],
    • then Export derives the value of the DEM property DemTypeOfFreezeFrameRecordNumeration (arxml TYPE-OF-FREEZE-FRAME-RECORD-NUMERATION) from the attribute value:
      • "Calculated": DEM_FF_RECNUM_CALCULATED (arxml: CALCULATED)
      • "Configured": DEM_FF_RECNUM_CONFIGURED (arxml: CONFIGURED)
      • Note that export checks the multi-language enumeration symbol [ATTR-R020-enum], not the numeric ID.

Note:

[DEXT-D330] Vector MICROSAR DEM does not support different DID lists per Snapshot Record.

  • Example: if the template contains 4 Protocol Services,
    • one Protocol Service for Snapshot Record 0x10, 0x11, 0x12 and 0x13 respectively,
    • and in a specific variant, you add a DID for Snapshot Record 0x10 only,
    • the DEM configuration in daVinci Configurator will be invalid.
  • Workaround:
    • keep the Snapshot Records identical in CANdelaStudio,
    • export DEXT from CANdelaStudio,
    • import into Configurator,
    • in the desired variants, for the respective DTC, manually add individual DIDs in the freeze frame layout (DemFreezeFrameClass).

Enable Conditions

[DEXT-R3200] If the DEXT export is based on v12 Events [EV-R010], ...

  • export uses the Event properties "Enable Conditions" [EV-R200] and "Storage Conditions" [EV-R210].
  • [EV-R700] describes Conditions, [EV-R800] describes Condition Groups in the v12 Events data model.

Otherwise:

  • a CANdela DTC can have multiple enable conditions
  • AUTOSAR stores these as Enable-Condition-Groups
  • the data is stored at the AUTOSAR Event, via an Event-To-Enable-Condition-Group-Mapping
  • each Event can have at most one Enable-Condition-Group
  • [DEXT-R320] Export merges multiple identical enable condition groups into a single one (9.1 SP1)

Diagnostic Sessions

  • AUTOSAR export for sessions requires a CANdela state group "Session" with semantics "session".
  • it uses the diagnostic instances for Protocol Service 0x10.
  • export associates a session with a diagnostic instance if...

    • no other session is used as a target state.

Security Levels

  • AUTOSAR export for security levels requires a CANdela state group "Security" with semantics "security".
  • it uses the pairs of diagnostic instances for Protocol Service 0x27: "Request Seed" and "Send Key".
  • export associates a security level with a diagnostic instance "Send Key" if...
    • the security level is the target state for at least one state transition
    • no other security level is used as a target state.
  • export suppresses (does not write) the first (default) security level
  • see also Diagnostic-Security-Access (0x27).

AUTOSAR: Service Executable in State "Locked":

  • [STTR-R028] If a service has a transition in state "Locked" of state group "Security Access", then it must not be blocked in any other state.
  • Motivation: in AUTOSAR, the other security levels...
    • must allow execution of more services than the first one,
    • i.e. they add functionality.
  • Note: use Sessions in order to...
    • allow execution of fewer services,
    • i.e. to restrict functionality,
  • [DEXT-R410] DEXT Export Behavior:
    • if a service is executable in the state "Locked", but not in another level, then DEXT Export...
    • before R21:
      • writes the service as not executable in the state "Locked", either;
    • in R21 or newer:
      • writes the service as executable in all levels.

Dynamically-Defined-Data-Identifiers

  • In CANdela, a diagnostic instance contains diagnostic instances for Protocol Service 0x2C that refer to the same data identier.
  • export creates a Diagnostic-Dynamic-Data-Identifier for each such data identifier,
  • it uses the name and the DID identifier.
  • [DEXT-R520] For dynamically defined data identifiers without a read service (0x22), export does not set read-access automatically, but logs a warning. (Escan-99659 DDM 14.0.0)
  • [DEXT-R530] Export skips dynamically defined data identifiers used in DEM (Escan-99656 DDM 14.0.0)
    • These are identifiers that have a service 0x2C.
    • Reason: the DEM cannot handle dynamically defined data identifiers.
  • [DEXT-R540] Export skips IO control functionality for dynamically defined data identifiers (Escan-100180 DDM 14.0.0)
    • The DCM module issues warnings or errors if IO control functionality is defined for dynamically defined DIDs.
    • Reason: dynamically defined DIDs must not have IO-control functionality.

Routines

  • Diagnostic routines instances for Protocol Service 0x31 have three services Start, Stop, Request Routine Results.
  • Export uses the combined name of the diagnostic instance and the service.
  • routine parameters (data objects) are represented as Diagnostic-Parameter, the names get an indication of the direction (input/output parameter)
  • the data type is preserved (e.g. uint32) and not converted to a byte array.
    • for 64-bit, see [DEXT-R203].

Diagnostic-Service-Table

  • Export fills the table from all services of the extract.

Diagnostic-Access-Permissions

  • CANdela state transitions control whether a service can be executed in a given (e.g. session or security) state.
  • export creates a Diagnostic-Access-Permission for each combination of CANdela state transitions,
  • ... and additional one named AP_ALL which represents "no access restriction".

Diagnostic Service Classes

Export creates a service class (e.g. Diagnostic-Session-Control-Class 0x10) if at least one corresponding CANdela diagnostic instance exists.

Export applies the following special rules:

Diagnostic-Control-DTC-Setting-Class (0x85)

  • Export sets controlOptionRecordPresent if the request contains a DTCSettingControlOptionRecord.

Diagnostic-Read-Data-By-Identifier-Class (0x22)

  • if the respective Protocol Service has the property may be combined set,
  • export sets maxDidToRead to the value specified at Maximum Number of Identifiers,
  • otherwise to 1.

See also [DEXT-R207] for combining DID data.

Diagnostic-Read-Data-By-Periodic-Id-Class (0x2A)

  • if the respective Protocol Service has the property may be combined set,
  • export sets maxPeriodicDidToRead to the value specified at Maximum Number of Identifiers,
  • otherwise to 1.
  • export sets schedulerMaxNumber to the value specified at Maximum Number of Identifiers in ECU Scheduler.
  • [DEXT-R505] export creates a Diagnostic-Periodic-Rate for each used transmission rate (slow, medium, fast),
  • it uses the timing from the ECU attributes, e.g. the value PERIODIC_RATE_SLOW:
  • the attributes are:
    • "Periodic Rate (Slow) in ms" [ASR-D001_Periodic_Rate_Slow_in_ms]
    • "Periodic Rate (Medium) in ms" [ASR-D001_Periodic_Rate_Medium_in_ms]
    • "Periodic Rate (Fast) in ms" [ASR-D001_Periodic_Rate_Fast_in_ms]

Diagnostic-Dynamically-Define-Data-Identifier-Class (0x2C)

  • Export sets configurationHandling fixed to volatile.

Diagnostic Service Instances

In general, ...

  • export uses name and description of the diagnostic instance
  • and the state transitions.

The following describes special data constellations.

Request Onboard Monitoring Test Result (0x06)

[DEXT-R510] Export creates a diagnostic service instance (0x06) for each referenced test result.

Note:

  • AUTOSAR 4.3 incorrectly allows diagnostic service 0x06 to reference only one test result.
  • Therefore export duplicates the 0x06 diagnostic service instances for each referenced test result.
  • AUTOSAR 4.4 plans to allow 0x06 to reference multiple test results.

Constant Values

Export can only include the service 0x06 if the data elements have a constant value, otherwise it skips the service.

Example:

  • Diagnostic Instance "Misfire Cylinder 1 Data"
    • Data byte 1: "Measured O2 ratio...", HexDump (1 Byte), constant value 0x85
    • Data byte 2: "Unit and Scaling TID 85", Unit and Scaling OBDMID, constant value 0x36 (= decimal 54)
    • Data byte 3+4: "Test Value TID 85", Test Value OBDMID (2 Byte), no constant value

Routines

Definition: a "linked routine" is a routine where the attribute defined in [ASR-D030] exists and has got a value.

If at least one linked routine exists, the exported DIAG-EX shall contain a package Diagnostics/…/Mapping".

For each linked routine, the "Mapping" package shall contain a DIAGNOSTIC-SERVICE-SW-MAPPING element, where...

  • SERVICE-INSTANCE-REF references the SERVICE-INSTANCE created for the routine, and
  • MAPPED-SWC-SERVICE-DEPENDENCY-IREF contains the AUTOSAR instance ref coded within the attribute value.

Data Objects

Definition: a "linked data object" is a data object, where the attribute defined in [ASR-D040] exists and has got a value.

Candidates are all data objects which will be exported as DIAGNOSTIC-DATA-ELEMENT in the DIAG-EX, namely the following:

  • Data objects of DIDs
  • Data objects passed as routine parameters
  • Data objects passed within an IO control state

If at least one linked data object exists, the exported DIAG-EX shall contain a package /Diagnostics/…/Mapping

For each linked data object, the "Mapping" package shall contain a DIAGNOSTIC-SERVICE-DATA-MAPPING element, where

  • DIAGNOSTIC-DATA-ELEMENT-REF references the DIAGNOSTIC-DATA-ELEMENT created for the linked data object, and
  • MAPPED-DATA-ELEMENT-IREF contains the AUTOSAR instance reference coded within the attribute value.

The SW-DATA-DEF-PROPS element of a DIAGNOSTIC-DATA-ELEMENT that represents a linked data object...

  • shall not contain a COMPU-METHOD-REF and
  • shall not contain a DATA-CONSTR-REF.

Note:

  • Only the BASE-TYPE-REF is relevant,
  • it references a SW-BASE-TYPE within the DIAG-EX,
    • which includes the BYTE-ORDER (e.g. "uint16_mot").
  • This is according to the current implementation in MSR4-R15.
  • The COMPU-METHOD and the DATA-CONSTR are implicitly given via the DIAGNOSTIC-SERVICE-DATA-MAPPING.
