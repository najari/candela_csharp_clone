A2L DID Creator (CDS-31541 8.1)

The CANdelaStudio A2L Import fills the import pool with data objects from the a2l file. The plugin "Import Pool DID Creator" shall create diagnostic instances for the UDS 0x22/0x2E services from the import pool.

Terms

RDBI Read Data By Identifier (UDS 0x22)
WDBI Write Data By Identifier (UDS 0x2E)

User Requirements

A2L DID Creator Use Case View

A2L DID Creator Example DID

U090.0 The plugin shall map A2L labels from the CANdelaStudio Import pool to new diagnostic instances for RDBI/WDBI classes.

A2L DID Creator Mapping GUI

U010.0 A GUI for mapping A2L label(s) to a DID shall be provided

U020.0 Provide a feature to import a mapping list (import button on GUI)

U030.0 Provide a feature to export the current mapping in a file (export button on GUI)

U210.0 The mapping GUI shall allow combination of multiple A2L labels to one DID. Mapped Labels share a multi-line cell.

U220.0 The mapping GUI shall allow to release an A2L Label from a combined set of labels.

U230.0 If used from plugin, the GUI shall allow selection of one or more target variants.

U250.0 If used from plugin, the GUI shall allow selection of one target diagnostic class (only diagnostic classes with RDBI/WDBI are shown, no selection allowed if only one such class is present)

U240.0 DID numbers that are already used in the current selected diagnostic class (in the document) are shown in a different color.

Integration into CANdelaStudio

R020.0 The A2L DID creator feature shall be realized as a plugin.

Basic Operation

R040.0 For selected DID/Label mappings, create new DID diagnostic instances

R120.0 Create the DID diagnostic instances for selected variants.

R125.0 Support multiple variants, created diagnostic instances shall be shared over the variants.

R130.0 Import into one selected target diagnostic class. The GUI shall propose all the diagnostic classes that are possible targets for DID creation (which have a service 0x22 or 0x2E). If only one diagnostic class is available, no selection is required, the target diagnostic class shall be shown in any case.

For the use case “import of measurement and characteristics” the user has to import the DIDs in 2 steps. First, import only measurements into the import pool, apply the algorithm. Clear the import pool, import the characteristics and import the data again.

R140.0 DIDs must be unique. Provide a check for duplicate assigned DIDs and do not allow the user to create them.

R150.0 Apply check for duplicate DIDs while importing a mapping file. If duplicate DIDs are imported, issue a warning and leave the DID field blank for the latest imported items.

R170.0 Provide a feature to automatically assign DID numbers to DIDs. Start with a provided start number and iterative assign and increase the number. The GUI shall propose a default value.

R180.0 The default value (see R170.0) is calculated by the start index of the largest free interval in the current diagnostic class (rationale: DID classes are usually sparsely filled. ISO reserved DIDs are often in the range of 0xFxxx, user DIDs are usually in lower ranges. Seeking the largest free interval will provide more probably a desired start index).

R100.0 If the attribute “A2LDidNumberMapping” is set to a value > 0, this attribute defines the mapped DID number [DID-R025]. (The attribute is generated from A2L Import if the A2L label has the annotation “DidNumberMapping”.)

R220.0 If the attribute “A2LPositionInMappedDidRecord” is present, it defines the position of the A2L label in the DID Data. This allows to order a set of A2L labels into a DID. No duplicate values in one DID are allowed.

R290.0 While creating diagnostic instances, it shall be checked for new created instance, if the DID (name or number) is already present in this diagnostic class. If this is the case, the plugin shall show a dialog telling the user about the conflict. The user can select a) skip b)overwrite c) create a copy. Furthermore a flag: "Use this option for all other occurrences" shall be available (like in Windows file copy operations).

A2L DID Creator Attributes from A2L Import

Read/Write Services

R110.0 Create (activate) only read services for Measurements. Measurements are read-only. The write service shall be disabled.

R115.0 Create and activate read and write services for Characteristics.

Bit Gaps

A2L labels might describe only a few bits. Diagnostics is byte oriented. Read and write services for those labels will always read or write entire bytes. This fact brings up the following situations:

Byte Fully Specified

Holes in Byte

  1. All Bits of one or more bytes are fully described
  2. Holes in the description of one or more bytes

R060.0 Create (activate) only read services if all bits of all the byte from the DID are described. Write services are dangerous as undescribed bits would be written with an arbitrary default value.

Combining Multiple Labels

DIDs can contain more than one A2L label. There are multiple reasons, e.g.:

  • A single byte is used within two or more labels
  • Related measurements are required in one DID (e.g. requesting the speed of all wheels in one DID)

R070.0 Allow combination of multiple A2L Labels into one DID.

R080.0 Provide possibility to assign a new name to the DID. As default, combine the names of the A2L labels (Also it is known that this is most likely not the desired name, e.g. DoorFRState, DoorFLState, DoorRLState, DoortRRState: shall get DoorStates instead of DoorFRState_DoorFLState_DoorRLState_DoortRRState. There is currently no simple solution for finding a reasonable default name.)

R190.0 The GUI shall not allow DID names that exceed the maximum Qualifier size of the document (see document settings).

Each of the proposed labels can be assigned to a DID by dragging it on the grid.

R010.0 The grid shall show combined A2L labels by combining the cell for the DID over the cells of the A2L.

R210.0 Allow to remove an A2L label from a combined DID by right clicking on the A2L label and selecting “Separate”.

Generating Diagnostic Instances

Basic Operation

This chapter describes how the data objects (A2L labels) are inserted into the DID diagnostic instance.

R300.0 For each mapping, a diagnostic instance in the selected variant and diagnostic class is created

R310.0 The new diagnostic instance gets the identifier set to the DID identifier of the mapping

R320.0 The new diagnostic instance gets the name and qualifier of the DID name of the mapping

R390.0 If used with CANdelaStudio 8.1 or higher, the plugin shall create DID objects and reference them from the diagnostic instance.

Layout Of The Generated Data List

R330.0 For each label name of the mapping, the plugin shall insert a data object into the diagnostic instance.

R340.0 The order of the data objects in the diagnostic instance shall be the order of the data objects in the mapping. This is the same order as the labels appear in the mapping (CSV) file.

This chapter describes how data objects are inserted into the telegram table.

R340.0 Every data object whose size is byte aligned will be stored as data object on top level of the telegram table.

R350.0 Every data object whose size is not byte aligned is wrapped into a bit field.

R360.0 A bit field wrapper collects all consecutive data objects that are not byte aligned and of the same byte order.

R370.0 The maximum length for Intel bit fields is 32 bits. Larger Intel bit fields are only supported if the document template supports it.

R380.0 If a bit field contains multiple Intel data objects, a new bit field shall be started whenever the size of 32 bit is exceeded.

The following table gives an overview of the different types of supported bitfields and the quantity [DT-R310] of their assigned data types.

Length (in Bits) Byte order Data Type Supported
<= 32 Intel/Motorola Atom Yes
>32 Intel Field Only if the document template supports it
any Motorola Field Yes

Persisting The Mapping Label / DID

CSV File Format

R230.0 The CSV Mapping file shall have the first line with the header information:

DidName;DidNumber;DataObjects,DataTypes

R400.0 The column “DataTypes” shall be optional.

R410.0 The column “DataObjects” may be also named “A2lLabels”.

R240.0 The CSV Mapping file may have an optional line directly after the header, defining the target diagnostic class. Only the line after the header (second line) is allowed to have this information. The supported format is:

:TargetDiagClasses="<DiagClassQualifier>"

e.g.

:TargetDiagClasses="DynamicData"

R250.0 The CSV Mapping file shall contain one mapping (DID -> multiple A2L Labels) per line in the following lines (after the header and optional target diagnostic class).

R260.0 A mapping of a DID to A2L labels shall be (as defined by the header)

<DidName>;<DidNumber>;<Data Object List(comma separated)>,<Data Type List(comma separated)>

e.g

Ventil.Druck; 0x1000; Ventile_Druck_B2_BR,Ventile_Druck_B3;Pressure[mBar],Pressure[mBar]

R270.0 The DID number shall be in hexadecimal format only, having a leading “0x”.
