Import Pool

See also the Import Pool User Interface.

Introduction

The Import Pool (since 6.0, CDS-11531) contains

  • imported data objects
  • with related data types

When you import a data object, CANdelaStudio automatically puts the referenced data type into the data types list.

The contents of the Import Pool is not stored in the CANdela document and will therefore be lost when you close the document!

Use e.g. ODX Import [MENU-R210] or Import from CDI [MENU-R220] to fill the Import Pool.

Use-case

Create or synchronize diagnostic objects in a CANdela document

  • from data of an external source (like a database for modelling data types),
  • transported in an ODX or CDI file.

In detail:

  • Add a data object to a diagnostic service (no reserved objects, no bit fields);
  • synchronize default or constant values;
  • synchronize the data type for an existing data object.

Importing data objects

On importing data objects (from ODX or CDI) via the “Import of selected parts” function,

  1. The data objects in the Import Pool may carry a CANdela data object attribute value read from the source media. The attribute values are not required. The existing attribute values shall be unique within the Import Pool.

  2. The Import Pool contains all data objects from the source media, but for data objects with an identifying attribute value, only unique ones with respect to 1 will be imported.

The data constellation may be one of the following:

A: Data object in Import Pool and in ECU: automatic update
B1: Data object in Import Pool, not in ECU: manual insertion
B1: Data object in Import Pool, not in ECU: Setting identifying attribute value at existing data object manually
C: Data object not in Import Pool, but in ECU: automatic reset of identifying attribute value
D: Data object not in Import Pool, not in ECU: Not relevant for use case

Cases A/C: Update data objects automatically

The user shall have the possibility to synchronize all data objects (carrying an identifying attribute value) specified within the ECU description with all data objects (carrying an identifying attribute value) within the Import Pool. (No support for selection in Import Pool) This means:

  • A) Update existing data objects from out of the Import-Pool. The target object will be replaced by the object from the Import Pool. CANdela OID and TextId will be taken from the Import Pool

  • C) Deleting identifying attribute values (cf. User Interface [IPUI-R024]) of all data objects where the current identifying attribute values is not available in Import Pool. Note: Not the data object will be deleted, but its identifying attribute value.

Note: OID can’t be used as an identifying attribute as the data object may be inserted more than once.

Note: Data objects with same value for identifying attribute may have different qualifiers/names.

Case B: Inserting data objects

On inserting (pasting/dropping) the data object, the identifying attribute value of the data object shall not get lost.

The data object may by be inserted multiple times in the ECU description. Note: the attribute values will not be unique within the ECU description.

Detailed Requirements

General requirements

[IP-R010] The Import Pool synchronization is only available, if an ECU non translatable String attribute with Qualifier “SynchronizationAttribute” exists and its effective (default or overwritten) value is the qualifier of a data object attribute with the following specification: the Attribute is of type String (default value is empty string “”).

Note: It is up to the template owner to set write protection for the synchronization attribute so that the Standard User can not overwrite the value.

On executing “Synchronize data objects in ECU description”

[IP-R030.1 Synchronize] For each data object in the Import Pool with a non empty value of the identifying attribute, search all data objects with the same value in the data type list and in all variants.

Replace the target object with the object from the Import Pool. (Default values, constants, … are also available in Import Pool) if

  1. the authorization of the diagnostic instance allows the modification of the properties, and

  2. the update of the data type does not violate any maximum size restrictions of a telegram table (component).

Note: DIDs (DID Referencer) constraints violations and loss of environment data (multiplexer cases) as a consequence of an update of data objects are not checked.

Note: the synchronization uses the same requirements ID as the requirements feature [RQ-R110].

[IP-R030-Nonunique] CANdelaStudio (after confirmation) allows the synchronization even if elements with ambiguous identification exist (CDS-69197 9.1).

  • Such elements can occur after import of bitfields, where every bit becomes a dataobject with the same identification attribute value.

These bits shall be ignored. Today, all elements with ambiguous identification attribute need to be deleted before synchronization can be performed.

R031.1: Depending on the check box of [IPUI-R024] reset all identifying attribute values (set attribute value to empty string or drop overridden value) in data objects as of R030.0 if this value is not contained in the Import Pool.

R032.0: Identifying attribute value uniqueness: if the import pool contains data objects with the same value for the synchronisation attribute, only show a user error message and do not synchronize.

Import of selected parts (ODX 2.0.1 Crumbs Import):

R040.0 On importing selected parts into the CANdelaStudio Import Pool the “identifying attribute values” of all data objects (PARAMs) shall be read from ODX model.

R041.0 The “identifying attribute values” will be read from a processing instruction directly at the PARAM.

R042.0 The processing instruction has the following specification:


<?CANdelaStudio SynchronizationId=SomeIdentifier ?>

Sample code for Import Pool SynchronizationId:


<PARAM SEMANTIC="DATA" xsi:type="VALUE">
  <?CANdelaStudio SynchronizationId=_0815?>
  <SHORT-NAME>Original_Odometer_Value</SHORT-NAME>
  <LONG-NAME>Odometer value first occurance</LONG-NAME>
  <BYTE-POSITION>2</BYTE-POSITION>
  <DOP-REF ID-REF="_261"/>
</PARAM>

Import of selected parts (ODX 2.2.0 Crumbs Import):

R050.0 On importing selected parts into the CANdelaStudio Import Pool the “identifying attribute values” of all data objects (PARAMs) shall be read from ODX model.

R051.0 The “identifying attribute values” will be read from a SDG structure directly at a PARAM.

R052.0 The SDG structure shall have the following specification:

Synchronization State (CDS-18753 in 7.0)

Purpose of the Function, Use Cases and Application-Domain Analysis

The feature: CDS-11531 “Feature: Support of Import Pool synchronization” allows to synchronize changes to diagnostic data objects described e.g. in DOORS with data objects in a CANdela document.

The process is described in the Vector application note AN-IDG-1-014 “CDS-18753 Extend import pool synchronization”.

A common scenario is: the user modifies details of a datatype in DOORS, and then synchronizes the modifications to the CANdela document:

Scenario of Data Type Synchronization

CANdelaStudio detects the data type differences and informs the user (in the import pool table) that the respective data object(s) are not up-to-date. But CANdelaStudio does not show detail differences. The existing and the modified datatype have the same qualifier, therefore during synchronization one of them must get a suffix (like “_1”). If the data type which will be imported gets the suffix, the import pool still detects a difference of the synchronized data object in the document and the import pool and shows “synchronization not up to date” due to the different qualifier.

General Functional Requirements (optional)

Improve data exchange from DOORS to CANdelaStudio:

  • give the user more information about the status of datatypes in the import pool

  • give the user a chance to conveniently adapt datatypes so that synchronization leads to the desired results

Functional Requirements

Import Pool: Column "Synchronization State"

R001.0: in Import Pool datatypes list, add a column “” right to “Description”. The column represents the relation of the datatype in the import pool to datatypes in the datatypes list of the document.

Possible values (cf. the respective values for the data object column in CDS-11531 R023):

Value Description
“Not used” The qualifier of the datatype does not occur in the document, or a data type exists with the same qualifier but is not referenced by any data object.
“In Use (up to date)” The document contains a datatype with the same qualifier and identical properties.
“In Use (ready for synchronize)” The document contains a data type with the same qualifier and different properties. The data type is either not used by any data object in the document or all data objects that reference the data type will be updated during synchronization.
“In Use (conflict)”
- to be shown e.g. red		 The document contains a datatype with the same qualifier and different properties, and it contains data objects that refer the datatype that a) must be synchronized to the new datatype in the import pool, and some that b) will not be synchronized to this datatype. Just overwriting the existing datatype properties would implicitly change the data objects b).
“Not relevant for synchronization“ The data type is not referenced by any data object which will be synchronized, for either its synchronization attribute is not set or its value does not match any data object’s attribute value.

R010.0: in Import Pool datatypes list, for all datatypes which also exist in the document. except those with states “Not used” and “In Use (up to date)” or “Not relevant…”, through context menu provide a Diff to the respective datatype in the document.

R015.0: in Import Pool datatypes list, through context menu provide a way to inspect the references of the respective datatype in the document (for a datatype with state “Not used”, the references list will be empty).

R020.0: Resolving data type conflicts for data types with “” = “In Use (conflict)”:

Rename the data type in the document to a new unique name in the data type list. Thus, all data objects continue to reference the existing data type.

Example result:

Import Pool Example Result

On synchronization the data type of the import pool is inserted into the document’s data type collection and the data objects will have the new data type reference set.

R030.2: in Import Pool data objects list, if user starts synchronization, and there are data types in Import Pool in state “In Use (conflict)”, show confirmation like:

“Some of the data types that will be synchronized are in conflict. The document already contains one or more data types with identical qualifiers but different properties which are used by data objects that are not subject of synchronization. The name and qualifier of the existing data type which will be referenced by all non synchronized data objects in the document will be changed during synchronization.

The data types list in the import pool shows more details.

Do you want to proceed?” If yes, just update the data types. If no, stop.
