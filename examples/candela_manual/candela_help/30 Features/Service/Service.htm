Service

Introduction

A service is the basic mechanism in diagnostic communication with an ECU.

In a CANdela document, a service is always based on the structure defined in the document template in a Protocol Service. You cannot specify a service containing an arbitry Service ID or byte sequence.

CANdela services are one part of a diagnostic instance, the other part being the telegram tables with data objects.

Physical Addressing and Functional Addressing

You can control for each individual service whether it supports

  • physical and/or
  • functional addressing.

Defaults are taken from the Protocol Service Addressing.

The CAN-IDs are specified as Communication Parameters on document level.

See the Service property dialog Addressing.

Semantics (CDS-10449 6.0)

[SVC-R200] Semantics is a non-translatable string property. It may be empty. Is is used for export to ODX.

Before 6.0, it could be represented as a service attribute with Qualifier "Semantic", Category "ODX".

The default for the property is taken from the semantics at the Used Protocol Service [DCLT-R320].

Activated (CDS-30340 8.2 SP2)

[SVC-R300 Service Activated]

  • CANdelaStudio supports an "activated" flag at a service.
  • Default: true (e.g. when creating a diagnostic instance).
  • It is valid to have a de-activated diagnostic instance that contains an activated service. Motivation: if user temporarily de-activates a diagnostic instance and activates it again, the activation of services shall be as before (it would be bad to have all services de-activated, too).
  • It is valid to have no activated service in a diagnostic instance.
  • data that belongs to de-activated services only is implicitly also "de-activated".
  • It is invalid to have a service de-activated if the "Used ProtocolService" has convention "required", see [SVC-R350].
  • It is valid to have a service de-activated if the diagnostic instance is required. Motivation: it is valid to delete a service if the diagnostic instance is required.

[SVC-R320] Authorization for modifying the "activated" flag shall be as for create/delete of the service.

[SVC-R325] Any functionality that uses the service shall handle the flag like it handles activation at a diagnostic instance.

[SVC-R328]

  • compare shall compare the flag.
  • update shall transport the flag value "true".
  • if the "Used ProtocolService" has convention != "required",
    • update shall transport the flag value "false",
    • otherwise debug message like "Can't remove service 'xxx' in target document -> it is required"

[SVC-R340 Migration]

  • when loading a file from pre 8.2, CANdelaStudio shall set the flag to true.
  • when saving a file to pre 8.2, CANdelaStudio shall drop a service that has the flag = false.
    • when all existing services of a diagnostic instance are de-activated, CANdelaStudio shall skip the diagnostic instance.
    • when a telegram table is used by de-activated services only, CANdelaStudio shall drop it, too.

[SVC-R350]: if a service is de-activated, but its "Used ProtocolService" has convention "required", then constraints check shall report an error and prevent from exports, like

Service "Read" in diagnostic instance "A/D Values" must not be de-activated,
since in the template, its Used ProtocolService has convention "required".

[SVC-R360] If a service is de-activated, but it is referenced by a variant identification feature, the feature shall be reported as invalid.
