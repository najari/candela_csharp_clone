Diagnostic Instance

CANdelaStudio Tree and Diagnostic Instance in Right Side

Introduction

[DI-D100] The diagnostic instance is a core concept of the CANdela data model. It combines...

  • services (to be executed, e.g. “Start” on top in the screenshot) with...
  • data (to be transported, e.g. list with “P2”, “P2Ex” at the bottom in the screenshot)

This structure is predefined in the Diagnostic Class Template.

[DI-D010] You can reuse (called "reference" or "share") a diagnostic instance in multiple variants or libraries. This...

  • reduces the size of the CANdela document and
  • ensures that modifications consistently take effect in multiple variants.

See Sharing Diagnostic Instances.

The Diagnostic Class Template controls the number of diagnostic instances in a variant:

  • only one diagnostic instance [DCLT-R150-singleton],
    • e.g. for Fault Memory
    • the CANdelaStudio tree shows such a diagnostic instance directly in the chapter "Supported diagnostic classes" of the variant.
  • multiple diagnostic instances [DCLT-R150-multiple],
    • distinguished by the Identifier
    • e.g. for Stored Data
    • the CANdelaStudio tree shows these diagnostic instance below the diagnostic class.

Identifier

Diagnostic Instance Identifier

[DI-R100] The Identifier distinguishes multiple diagnostic instances.

  • Its presence and position in the request or response is defined in the Protocol Service by a Variable Value component.
  • As a default, the Identifier must be unique (but see [DIUI-R200]).
  • A Variable Value component represents one type of Variable Value [PS-R400-Specification], e.g.
    • "ID" (Identifier) or
    • "Subfunction".
  • The set of available Identifiers is restricted by a Text Table [DCLT-R400].

See also

  • Check for Identifier Uniqueness
    • in the user interface [DIUI-R200]
    • feature
  • Identifiers in UDS and OBD Services

Diagnostic Instance as a "DID Definition"

For a DID object from UDS, CANdela describes...

  • ... the data objects: in a DID object,
  • ... but the communication: in a diagnostic instance.

see the overview diagram.

[DI-D110 Diagnostic Instance as DID Definition] A diagnostic instance is a "DID Definition" if...

  • there is a DID D, and
  • the diagnostic instance contains a telegram table with a DID Data Reference [DID-R160] referring to D;
  • without respect to...
    • the services of the diagnostic instance,
    • the number of DID Data References in the telegram table,
    • the qualifiers and names,
    • the identifier values.
  • Note: this definition differs from...
    • ... that of a "DID Enabled" diagnostic class [DCL-D001] in that it does not consider services and the number of objects.
    • ... the consistency condition [TT-R240] for the “DID Data Reference” semantics.

Note: CANdelaStudio may show the DID Contents directly in the Diagnostic Instance [DIUI-R310].

Activation

Use-case: Some manufacturer specific information (diagnostic instance) is predefined in the template but optional to support for a concrete ECU document. When you delete such a predefined diagnostic instance in CANdelaStudio, all information is lost. If you decide later that the diagnostic instance should be supported by the ECU, you have to re-enter the content manually.

Example: some data package with a fix local identifier contains serial number information. If an ECU contains a serial number, it must support exactly this service.

Solution: The “activation” feature allows de-activating a diagnostic instance or job container. The user can always decide to re-activate this piece of information.

Details:

[DI-R150] Each diagnostic instance (or job container, also in the following) may be activated or deactivated. Changing this activation state property is called to activate and deactivate. The property is persistent (i.e. remains the same when the file is saved and opened again).

A new diagnostic instance is always activated.

When copying a diagnostic instance, its activation gets copied, too.

  • E.g. copying a deactivated diagnostic instance results in a new deactivated diagnostic instance.

Deactivating diagnostic instances referenced in multiple variants or libraries takes effect at all references.

Changing activation state requires the special authorization [DIA-R030].

Semantics: a de-activated diagnostic instance or job container is no more valid for the ECU document:

  • it is displayed greyed-out
  • it does not appear in the report
  • it does not appear in data oriented exports (e.g. ODX, Diogenes)
  • it is ignored by Vector testers (i.e. by the DTL)

Consistency Conditions

Combined Components

Within one DiagInstance, there is at most one telegram table for a combined component in the associated DiagClassTemplate (the telegram table may be missing because a service may be missing if the Convention of the Used Protocol Service is not "required").

Within one DiagInstance, there is at most one Identifier for a combined variable value in the associated DiagClassTemplate.

The list of telegram tables must reference all combined components of the Used Protocol Services, and only those ones. Analogous for the Identifier .

Negative Response

The data object in the negative response must have at least one entry in the text table if the respective proxy component is mandatory.

Data Objects and Proxy Component

Data Objects that belong to a proxy component which

  1. is not the last component, or
  2. is the last component within an iterative,

must not have a datatype without length information. This holds in request and posResponse.

Motivation: allow only objects that allow e.g. the tester library to associate posResponse data with the CANdela objects. That means:

Not allowed: an Ascii or Unicode field datatype with no termination, or a numeric field (that never has termination).

Allowed at any proxy: a datatype with fixed length (e.g. atom or fixed length field), or Ascii/Unicode field with leading size info or zero-termination.

v3.0.3 (CDS-3241): variable length datatypes with length info are forbidden at a non-last proxy.

Target Groups (Audience) at a Diagnostic Instance

See also the property page for target groups.

[DI-R200] Each diagnostic instance can be relevant for an n-of-m subset of the entire set of target groups, an audience, with 0 <= n <= m.

An empty audience is valid (the object is never exported).

For new diagnostic instances, all target groups are in the audience.

Copying corresponding diagnostics objects copies their audience.

The audience at a diagnostic instance governs the audience at a service:

  • If a diagnostic instance is not relevant for a target group, all contained services are automatically not relevant for this target group, too.
  • If a diagnostic instance is relevant for a target group, the individual contained services may or may not be relevant for this target group.

I.e. the relevance at a service is variable only if the target group is relevant for the diagnostic instance.

Modification of audience is controlled by authorization.

DTC Status Bits

See the definition of DTC Status Bits at Protocol Services.

In a diagnostic instance, the CANdela data model holds a DTC Status Data Object for each combined DTC Status Bits proxy component of the Diagnostic Class Template.

The DTC Status Data Object defines

  • the bits available in this Fault Memory instance
  • optional request default values for a test system

ODX ECU-SHARED-DATA

[DIATTR-R100] A Diagnostic Instance originates from ODX ECU-SHARED-DATA if the following three special attributes are set (CDS-25736):

  • [DIATTR-R100-DOCTYPE] DOCTYPE
  • [DIATTR-R100-DOCREF] DOCREF
  • [DIATTR-R100-ID_REF] ID_REF

Such a diagnostic instance...

  • will be shown with a special icon in the tree and in the diagnostic instance list
  • if the user starts editing such a diagnostic instance, CANdelaStudio shows a popup dialog:

This diagnostic instance is a reference from an ECU-SHARED-DATA. Editing this diagnostic instance will break the link to the ECU-SHARED-DATA. Do you want to continue?

  • if the user edits such a diagnostic instance, CANdelaStudio resets the special attributes.
  • See CDS-71837 for resetting the attributes on copy [DIOP-R025].
