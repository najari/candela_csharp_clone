Vector UDS Template - Protocol Services

Protocol Service 01 ReadPIDData

Service 4F External Test Equipment Configuration #1

The positive response of PID 4F has 4 bytes...

  • Maximum value for Equivalence Ratio
  • Maximum value for Oxygen Sensor Voltage
  • Maximum value for Oxygen Sensor Current
  • Maximum value for Intake Manifold Absolut Pressure

... that - if greater than 0x00 - are used to calculate the scaling of other PIDs.

Example: the 4th value ("Byte D") from PID 0x4F is used in the other PID 0x0B "Intake Manifold Absolute Pressure":

"Byte D" of PID 0x4F Scaling for Value of 0x0B
0x00 1 kPa per bit
> 0x00 Byte D * 10/255 kPa per bit

The CANdela data model does not describe this dependency of a conversion (data type) on the return value of another PID (neither has the standardized ODX data model).

CANoe.DiVa (as of 2018) does not support this dependency, either:

  • DiVa checks positive or negative responses of the respective PIDs,
  • but evaluation of concrete values needs human interaction, anyway,
    • DiVa does not use the variable scaling.

Protocol Service 19 05

[VUDS-D1905] In v13.0 (CDS-72038 2020-02), 19 05 has been dropped.

Motivation

  • UDS defines this service as 19 05 <SnapshotRecordNumber>.
  • The template contained 19 05 00 (it set <SnapshotRecordNumber> to constant 0x00).
  • SnapshotRecordNumber 0x00 reads the OBD Freeze Frame.
  • The AUTOSAR DEM Specification limits the value to 0x00 (chapter 4.1 "Limitations" as of AUTOSAR 4.3.1)
  • From Vector experience, other values are not relevant in practice for this service.
  • MICROSAR code generation assumes the value 0x00 (it does not support 19 05 <SnapshotRecordNumber>).
  • The service may become obsolete with the new OBDonUDS (to come).

Protocol Service 0x28 CommunicationControl - EnhancedAddressInformation

With UDS 2013, 0x28 has an optional Request parameter nodeIdentificationNumber (2 bytes), for the following values of the control type (subfunction) parameter:

  • 0x04 enableRxAndDisableTxWithEnhancedAddressInformation
  • 0x05 enableRxAndTxWithEnhancedAddressInformation

The number identifies a node on a sub-network, e.g. a LIN node. The value 0x0000 is reserved.

Protocol Service 0x2C

[VUDS-R850] Functional addressing for Protocol Service and Service 0x2C is off by default (CDS-40743 8.5 SP2).

[VUDS-R855] The "Identifier" Component has a text table [PS-R450] "Short Identifier" with range 0x00 .. 0xFF assigned.

  • the same text table is also assigned [DCLT-R400] in the Diagnostic Class Templates that use the Procotol Service, see [VUDS-R540].

Trade-off for the text table:

  • Use a single open range, like 0x00 .. 0xFF
    • Benefit: at service tool run-time, the user/tool is able to select any 1-byte value as the identifier
  • Use few entries only, like 0x00, 0x01, 0x02, 0x03
    • Benefit: this reduces the ROM size in the AUTOSAR DCM implementation
      • the DCM requires that each supported dynamic DID in the F2xx range is configured and marked as dynamic DID.

Protocol Service 0x34

  • The Request uses a Multiplexer to handle variable sizes of the parameters:
    • Data Format Identifier (describes compression and encryption)
    • Address and Length Format Identifier (the Selector)
      • bits 7-4 define the number of bytes of the Memory Size parameter
      • bits 3-0 define the number of bytes of the Memory Address parameter
    • Memory Address and Size (the Multiplexer)
    • Effect in a Diagnostic Instance:
      • you have to specify a data object and the constant value for the Data Format Identifier,
      • you cannot specify the value for the Address and Length Format Identifier (since it is defined in the Fixed Data Component in the template).
  • The Positive Response contains two independent Proxy Components:
    • Length Format Identifier (bits 7-4 define the number of bytes of the following parameter)
    • Maximum Number of Block Length
    • Effect in a Diagnostic Instance:
      • you have to specify a data object (1 byte) and the constant value for the Length Format Identifier,
      • as well as for the Maximum Number of Block length.
      • E.g. if Maximum Number of Block length is a data object that refers a 2 Byte data type, the Length Format Identifier must be (2 << 4) = 32.

Protocol Service 0x36

One Combined Protocol Service

The Protocol Service 0x36 is used after either of two other Protocol Services:

Initiating Protocol Service Direction Data in 0x36 Request Data in 0x36 Positive Response
0x34 Request Download to the ECU transfer data optional checksum
0x35 Request Upload from the ECU optional memory range transfer data

Note: the optional data may be required by manufacturer specifications. If they were not actually used, two separate 0x36 Protocol Services would make sense:

  • one for download, with data in the request only
  • one for upload, with data in the positive response only

Parameters

Request and positive response contain separate components for the parameters from the UDS Spec (CDS-42470 8.5 SP3):

  • #2 Block Sequence Counter (1 byte)
  • #3 Transfer Request / Response Parameter Record (0..n bytes)

Both parameters are described using a proxy component with semantics "any" (i.e. do not define the structure).

Diagnostic Class Template "File Transfer"

[VUDS-R860-DClT] In the diagnostic class template, components that describe the same data in multiple Protocol Services are combined (as listed in chapter above):

0x38 Combined Components in the Diagnostic Class Template

[VUDS-R860-Transfer] The Diagnostic Class Template additionally contains Protocol Services 0x36 (Transmit) and 0x37 (Stop).

  • Note:
    • Service "Stop" for Protocol Service 0x37 "Request TransferExit" occurs in both Upload/Download and File Transfer.
    • You can check the "Stop" service only once within a variant.
  • Reason:
    • in the template, 0x37 "Request TransferExit" contains a data proxy component
    • ... but no identifier component.
    • When sent over the line, the byte sequence before the proxy component must uniquely identify the proxy component.
    • With multiple 0x37 within a variant, that prefix byte sequence would be non-unique.
  • Then why can I have multiple services for 0x36?
    • In the template, 0x36 "TransferData" only has proxies with semantics "any" (shown as "x"), for which CANdelaStudio does not provide a telegram table in the diagnostic instance.

Diagnostic Instance "File Transfer"

  • [VUDS-R860-DiagInst] As a default, the File Transfer diagnostic instance does not exist in the base variant.
  • In order to use it, check it in the "Supported Diagnostic Classes" section.
  • The diagnostic instance contains multiple telegram tables for the respective 0x38 parameters
    • more will be shown when you check the respective service:

0x38 in Diagnostic Instance

  • for parameter "File Path and Name",
    • you may use the data type "String (2 Byte Size Info)"
  • for parameter "Data Format Identifier",
    • you may use a bitfield with 2 data objects,
    • each using data type "Unsigned (4 Bit)".

Code Generation for File Transfer

Vector code generation supports 0x38 only as callout into the application (custom service processor), there is no more specific support (as of 2018).

Protocol Service 0x86 Subfunction 0x04 reportActivatedEvents

If in service 0x86 the subfunction 0x04 is activated, the service 0x86 has to be implemented completely by the application.
