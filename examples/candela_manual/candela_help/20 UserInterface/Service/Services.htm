Services

This page describes the services list in the Diagnostic Instance page.

Right Side of a Diagnostic Instance in Tree

Under "Service:", you can create or delete services for the diagnostic instances.

The total set of services available is predefined in the diagnostic class template and cannot be modified in the document.

Each row shows from left to right:

Checkbox

[SVUI-R400] The checkbox allows to create, de-activate and delete a service.

[SVUI-R400-Display] CANdelaStudio shows the checkbox...

  • for an activated service: checked;
  • for a de-activated service: checked, with a red cross overlay (like for a de-activated diagnostic instance);
  • for a deleted service: unchecked.

[SVUI-R400-Activated]

  • if a service is activated, and you click the service existence checkbox
    • (note: this is only possible if the Used ProtocolService has convention != "required"),
  • then CANdelaStudio shows a confirmation dialog that lets you
    • leave the service activated,
    • de-activate the service or
    • delete the service.
  • If you select "de-activate", CANdelaStudio shall set the flag [SVC-R300] to false.
  • If you select "No", CANdelaStudio changes nothing.
  • Note: if you select to delete the service, CANdelaStudio actually
    • deletes the service from the diagnostic instance,
    • including all data objects belonging to the service.

[SVUI-R400-Deactivated]

  • if a service is de-activated, and you click the service existence checkbox,
  • then CANdelaStudio sets the service activated.

[SVUI-R400-Deleted]

  • if a service is deleted (does not exist), and you click the service existence checkbox,
  • then CANdelaStudio creates the service and sets it activated.

Service Name

The "Service" name is given in the diagnostic class template, e.g. "Read", "Write".

Service Properties

The properties button to the far right of the service name opens the properties dialog for the service.

Note: the button is near the next column "Protocol Service", but applies to the service:

Service Name, Properties Button and and Protocol Service

See also the description of the service icons.

Protocol Service

The Protocol Service name is shown as a hyperlink, e.g. "(0x22) ReadDataByIdentifier".

Clicking the hyperlink opens the property dialog for the Protocol Service. Since the Protocol Service is predefined in the template, its data cannot be modified.

Request, Pos.Resp. and Neg.Resp (Service Abstract)

Structure of a Protocol Service ("Service Abstract")

The columns "Request:", "Pos.Resp.:" and "Neg.Resp:" show the structure of the Protocol Service.

See the service signature in the user interface.

Abbreviations zz, yy...

The abbreviations "zz", "xx" etc. represent the proxy components defined in the Protocol Service.

Proxy components that have been combined in the diagnostic class template are shown with the same abbreviation.

These "Combined Components" are "docking points" for data defined in the individual diagnostic instance, in the telegram tables shown at the bottom. The tab card of each telegram table shows the respective abbreviation.

If you click on an abbreviation, the relevant telegram table is shown at the bottom.

The combined components are named in descending order starting with "zz". The letters themselves have no meaning except to uniquely identify the combined component within this dialog.

Square Brackets

Square brackets around the abbreviation indicate that the proxy is included in an iteration, i.e. that it occurs several times in the telegram.

An asterisk "*" to the left of the first square bracket indicates that the data can be repeated on the line.

Abbreviation x

A single "x" represents a proxy component that has no information about the individual data object it represents (neither directly in the Protocol Service nor in the diagnostic instance). .

Abbreviation rc

The abbreviation "rc" represents a special proxy component that contains the "Negative response codes" of the service.

Abbreviation fd

The abbreviation "fd" represents a special proxy component that contains "fixed data", i.e. data objects predefined in the Protocol Service. The data objects cannot be modified in the diagnostic instance.

Tooltip

[SVUI-R500 Tooltip]

The tooltip (mouse-over) of the "Request, Pos.Resp. and Neg.Resp" ("Service Abstract") region informs about addressing and the possible request bytes and their responses (in the order of the following definitions):

Service Abstract with SPRMIB

[SVUI-R500-SPRMIB Hint about SPRMIB]:

  • Conditions:
    • SPRMIB supported
  1. text "Supports 'Suppress Positive Response Message Indication Bit' (SPRMIB)"

[SVUI-R500-PhysNormal No SPRMIB]:

  • Example Line: phys 0x22 0x40 x10 xx
  • Conditions:
    • SPRMIB not supported
    • ECU supports physical request
  1. prefix "phys"
  2. request (like in services list, no italics, unmodified ID)
  3. positive response (like in services list, no italics)
  4. negative response (like in services list)

[SVUI-R500-PhysSPRMIB0 SPRMIB 0]:

  • Example Line: phys 0x22 0x40 x10 xx
  • Conditions:
    • SPRMIB supported
    • ECU supports physical request
    • "Test System Sets SPRMIB" = don't care or never
  1. prefix "phys"
  2. request: SID, ID, ... (like in services list, no italics, but with MSB of ID := 0)
  3. positive response (iff. "ECU answers... request" = true): SID + 0x40, ID, ... (like in services list, no italics, but with MSB of ID := 0)
  4. negative response (like in services list)

[SVUI-R500-PhysSPRMIB1 SPRMIB 1]:

  • Example Line: phys 0x22 0xC0 x10 xx
  • Conditions:
    • SPRMIB supported
    • ECU supports physical request
    • no positive response exists, or "ECU answers physical request" = false
    • "Test System Sets SPRMIB" = always or don't care
  • dito with MSB of ID := 1

[SVUI-R500-DIAG_LAYER DIAG_LAYER Attribute]:

  • Example Line: DIAG_LAYER: FUNCTIONAL_GROUP
  • Conditions:
    • the service attribute DIAG_LAYER exists and has a value != “unspecified”
  1. prefix "DIAG_LAYER: "
  2. the value of the service attribute DIAG_LAYER

[SVUI-R500-Func Dito functional addressing]:

  • Show the [SVUI-R500-PhysNormal], [SVUI-R500-PhysSPRMIB0] and [SVUI-R500-PhysSPRMIB1] dito for functional addressing (if supported).

Example Tooltip

Assume the service has the settings:

  • SPRMIB supported
  • DIAG_LAYER = “PROTOCOL_LAYER”
  • “ECU supports physical request” = true
  • “ECU answers physical request” = true
  • “Test system sets SPRMIB” = user-defined
  • “ECU supports functional request” = true
  • “ECU answers functional request” = false
  • “Test system sets SPRMIB” = always

Button ">>"

When you enter the diagnostic instance dialog, CANdelaStudio shows only the telegram tables for the "Request" and "Positive Response" (depending on an option).

The buttons >> / << to the right toggle display of the negative response codes (see below).

Clicking on the abbreviation "rc" has the same effect.
