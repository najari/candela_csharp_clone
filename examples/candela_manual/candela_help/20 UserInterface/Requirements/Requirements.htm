Requirements Pool

R010.1: the top-level tree node “Requirements” (in a CANdela document and template) shows requirement data which is persistent (saved to and loaded from a document or template).

The right side (requirements area) supports multiple layouts, see [RQUI-R012] below.

  • side by side

Requirements

R015.5: the requirements pool shall contain a list on top-level. Each is either a terminal requirement, or a hierarchy of headings and of structured requirements of various sub-types which may contain terminal requirements (see the Requirements Element Types [RQ-R012]). The pool cannot contain the same element at multiple places.

For simplicity, in the following the pool list of hierarchies is called a “tree” (the pool may be handled like a tree whose root is ignored).

The requirements tree (as well as the tree in the diagnostic objects pane) is optional, toggled by a toolbar button: .

The trees shall support navigation only (no editing, no status info).

The requirements tree shall not show terminal elements (Data, DTC, Text).

It shall contain a first element . The requirements list shall show

  • … for “(all)”: all requirements, as a tree view
  • … for another selected element: the child elements of the selected element, as a list

List View

Headings and requirements are created only in the list, not in the tree.

[RQUI-R040] The column headings are localized property names.

[RQUI-R050] The list shall not show columns of properties that are not supported in the currently selected tree node. E.g. if the user selects a DiagInstance Requirement which is not FaultMemory, specific DTC columns [RQ-R040-ForType] shall not be shown.

[RQUI-R060] For a property that does not exist at the selected requirement, i.e. ...

  • either a Specific Property [RQ-R030],
  • or a User-Defined Property restricted to exist at DTC Requirements [RQ-R040-ForType],

the list shall...

  • show "-" as a value
  • not allow editing.

[RQUI-R070] The list shall provide a magic line.

  • [RQUI-R070-Type] The magic line shall intelligently create one of the types Data, DTC or Text: if the current parent allows creation of the type created the last time (via menu, toolbar or magic line), then the magic line shall create an element of that type.
  • [RQUI-R070-Text] Otherwise, it shall create a text requirement.

Compare State

[RQUI-R080] CANdelaStudio shows each requirement with a special symbol left to the requirement icon:

Requirements Synchronization State

  • green box: a diagnostic object exists and is up-to-date
  • yellow box: no diagnostic object exists
  • red box: a diagnostic object exists with differing properties

Update Diagnostic Objects

R561.0: provide update of diagnostic objects [RQOP-R500] for 1..n selected (“locally”) or for all requirements.

If executed locally:

  • recursively process all requirements contained in the selected ones;
  • update any associated diagnostic objects without regard of the diagnostic object selection in the diagnostic object tree.

Indent/Outdent

The list shall provide commands to move an element (with its subtree) up/down in the tree hierarchy. Cf. the commands to indent a paragraph (and vice versa) in MS Powerpoint.

Move left (oudent) of a child object can only performed for the “last” Children of a node. This Object will then become the next sibling of its former parent. Moving e.g. (See Example “Not possible”) the second of 3 siblings would lead to that H1 loses its child H4, therefore allow only for “last“ children.

The Indent/Outdent operation can only performed if the list view shows the requirements in recursive mode and no filter is active. Reason: If a filter is active or only the children are displayed in the list view, the hierarchy is not visible and the changes cannot be seen.

Requirements can also not be moved up to a higher hierarchy than the displayed ones.

Properties Bar

At the right side the properties of the requirement selected in the list view are displayed.

All properties of the requirement are displayed in a list of properties. (Like a property grid.)

Localized Property Names (Columns)

The names of...

  • general properties [RQ-R020] and
  • specific properties [RQ-R030]

are represented by localized names...

  • in the requirements list and
  • in the Settings property page.

Example:

  • the name "DiagClass" from the data model
  • is shown as "Diagnostic Class" (English) or "Diagnoseklasse" (German).

Note: the exported CSV file shows the original names from the data model.

Note: user-defined properties [RQ-R040] have no localized representation.
